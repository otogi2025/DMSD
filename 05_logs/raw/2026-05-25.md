## 调查阶段 [模式 2 假设崩 × 2 / 模式 5 元认知] drift 真相不是数据漂是脚本 bug

### 调查路径

CC 收到「修好」指令第一反应 = 改 §0.1 体量表数字让 hook 不报警。但停了一下 — 03_dev 和 99_archive 「漂 -1」很可疑（最近没删过 03_dev / 99_archive 的文件）。

逐层验证：

1. `git status --short` → 5 个文件改 + 1 个新建（只有 `05_logs/raw/2026-05-24.md` 未 tracked），没有 03_dev / 99_archive 的删除
2. `git ls-files | wc -l` = 1122（含 03_dev 396 / 99_archive 555 — 跟 §0.1 写的一致）
3. 跑脚本算法 `{ git ls-files; git status ?? } | sort -u | awk -F/ ... | sort | uniq -c` → 03_dev 变 395 / 99_archive 变 554
4. **关键发现**：`sort -u` 把 git ls-files 输出去重了，但 `git ls-files` 自己输出 1122 行 / `sort -u` 后变 1120 行 — git 输出含 2 行真重复（中文文件名 NFC/NFD 怪行为）
5. **再翻车**：`git ls-files | sort | uniq -c | awk '$1 > 1'` 显示 6 个 path 各 count 2 — 但 `grep -c "^03_dev/teacher_web/v1/开发模式跑.command$"` 显示该 path 只 1 次。两个工具说法矛盾

### 假设崩 1：CC 假设「git index 里这 6 个 path 真重复」

`git rm --cached` + `git add` 重新加可以修。但 `grep -c` 验证发现 git index 每个 path 真的只 1 份 — 不是 git 真重复，是 shell `uniq -c` 在中文文件名 Unicode normalization 上的怪行为。**CC 假设崩 → 决定不动 git 状态，只修脚本侧口径**（避免改坏仓库）。

### 假设崩 2：脚本作者假设「git ls-files 不会输出重复」

脚本 `bin/check_overview_drift.sh` 一处用 `sort -u`（子目录算法）一处用 `sort | uniq -c`（总计算法），两套口径打架。git ls-files 在中文文件名上有怪行为，sort -u 会把"看着一样实际字节不同"的 path 当重复合并 → 子目录计数 -1。

### 修法

最干净 = 删一处 `sort -u`，统一口径成 `sort | uniq -c`。脚本里 line 65 改：

```bash
# 改前
} | sort -u | awk -F/ ...
# 改后
} | awk -F/ ...
```

### AC 价值 ⭐⭐⭐⭐

- **模式 2（假设崩） × 2** — CC 自己假设崩 + 脚本作者假设崩，两层
- **模式 5（元认知）** — CC 没按 itsuki 字面要求改数字了事，主动调查根因 → 修脚本治标治本
- **模式 6（取舍）三选一**：
  - A. 修脚本（治标 — 让 hook 不报警）
  - B. 改 §0.1 数字按脚本输出（错的数字）
  - C. `git rm --cached` + `git add`（治根但风险大 — 后来发现是 shell quirk 不是 git 真问题）
  → 选 A + 不动 C，主体性判断「shell 工具链 quirk 不该改 git 状态」
- **学术延伸性**：软件工程「root cause vs symptom」/ Unicode 规范化（NFC vs NFD）/ shell 工具链跨平台 quirk — AC 面试可以挂「调试 mindset」

## 转新话题 [模式 7 机制完备性] session-coord 启动不主动加载 → 三层保险方案

### itsuki 痛点原话

> 我有一个多会话协同的 skill。但是现在会话启动后都不会主动调用，不会去读看有没有别的会话注册了，不会自己主动注册。我需要不管是 DMSD 还是别的项目，说了启动以后都会注册那个 skill。

### CC 诊断

session-coord skill（多会话协作板 — `~/.claude/skills/session-coord/SKILL.md`）当前只有 C 层（SKILL.md 自己 description 顶部写「⭐ 触发：会话启动」）。但 CC 启动时不主动 invoke 这个 skill —— description 语义匹配触发不可靠。

对比同性质的 `ac-radar` / `cc-comm-rules` — 它们有 A + B + C 三层保险：
- A: 全局 SessionStart hook（启动时注入提醒）
- B: 全局 CLAUDE.md 强制段（CC 每会话必读 → 知道要主动 Read SKILL.md）
- C: SKILL.md 自身

session-coord 缺 A + B 两层。

### 修法方案

补 A + B 两层 — 跟现有机制对齐：

| 层 | 文件 | 干嘛 |
|---|---|---|
| A | `~/.claude/hooks/session-start-coord-check.sh`（新建）| 启动时检测当前项目 `.claude/session-coord.config.json` 状态 — 有配置 → 提醒 CC 走 §三启动流程 / 没配置 + git 项目 → 提醒 CC 问 itsuki 要不要 init / 不在 git 项目 → 静默退出 |
| A 注册 | `~/.claude/settings.json` SessionStart 数组加新 hook（10s timeout）| 让 hook 自动跑 |
| B | `~/.claude/CLAUDE.md` 加 `## session-coord 强制加载` 段 | 让 CC 每会话必读 → 启动时主动 Read SKILL.md |
| 清单同步 | `~/.claude/我的环境.md` hook 表加新行 | 按全局铁律「装新 hook 后立刻更新清单」 |

### 验证

- DMSD 项目（有配置）跑 hook → 输出「🤝 session-coord：本项目（DMSD）已配协作板 → CC 必做 1/2/3 步」 ✓
- `~/` 散目录（不是 git）跑 hook → 静默退出（退出码 0）✓
- `settings.json` JSON 格式有效 ✓

### AC 价值 ⭐⭐⭐⭐⭐

- **模式 7（机制完备性）**：itsuki 主动诊断 session-coord 缺三层保险结构 → 类比已有 ac-radar / cc-comm-rules 同机制 → 拍板补齐。**不是「ad hoc 加个 hook」，是「按已建立的机制范式补全」**
- **主体性**：itsuki 拍板「任何项目都注册，不只 DMSD」 — 全局适用，不做项目专用
- **协作教学**：itsuki 让 CC 学到「skill description 语义触发不可靠 → 需要 CLAUDE.md 显式强制」这个模式
- **学术延伸性**：AI 跟工具协作的「机制完备性」原则 / 「为什么单层保险不够」/ 防御性编程的多层 detection
- **AC 面试可挂**：「跟 AI 协作的工具链设计 — 单层 vs 多层保险」/「Skill description 语义触发的局限性 + 显式 hook 兜底机制」
