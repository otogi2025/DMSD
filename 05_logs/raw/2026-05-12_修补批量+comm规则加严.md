## §C destructive bash hook 改造（block → warn）

### itsuki 拍板原话

> "我有一个 hook 是专门阻止 Claude 去改文件，也不是说改文件，就是做出毁灭性动作的。我发现那个 hook 管得有点严了，我希望你帮我把这个 hook 改成：在 Claude 在 Cici 做出删文件或者之前会被拦的操作的时候，强制让 Cici 去思考一下，这个真的没问题吗？反正就是提醒一下 Cici。然后让 Cici 不是那么就直接去做了，而是去思考下能不能做，然后再去做，而不是把他拦着不让他做。"

### 旧行为（2026-05-04 → 2026-05-12）

8 个破坏性命令模式 → `exit 2`（退出码 2 = block 拦死，命令不让跑） + stderr（standard error — 标准错误流）报错 → CC 看到只能改方案或问 itsuki 授权。

### 新行为（2026-05-12 起）

8 个模式不变 → `exit 0`（退出码 0 = 成功，不阻断） + JSON `additionalContext`（hook 协议字段 — 把额外提示注入 CC 上下文） → CC 看到警告 **应该** 自觉停下问 itsuki，**技术上**可以直接跑（hook 不再阻断）。

### dry-run 测试结果（验证机制走通）

```
echo '{"tool_input":{"command":"git reset --hard"}}' | bash hook.sh
# 输出: {"hookSpecificOutput":{"hookEventName":"PreToolUse","additionalContext":"⚠️ destructive-bash-WARN ..."}}
# exit code = 0
```

→ 直接证据：测试时 hook 命中了它自己的 dry-run 命令（因为命令字符串包含 "git reset --hard"），CC 端真的收到了一段 `<system-reminder>` 注入的警告。**机制走通**。

### 联动同步

`00_admin/hooks/README.md §F` 段已同步：明示 "2026-05-12 itsuki 拍板 block → warn" + 文件名保留（避免改名引发多处联动）+ "CC 应该自觉停下问 itsuki" 自觉性提醒。

### I.5 ⭐⭐⭐⭐⭐ AC 价值 — 规则演化反思

**核心模式**：
1. **模式 2 假设崩塌 × 4** — v0.1 / v0.2 都假设 CC 自觉性够，每次被 itsuki 怒怼推翻。最后 v0.4.0 接受根本现实：靠自觉性不行，**改方向**而不是再加严同方向
2. **模式 5 元规则验证 × 5** — itsuki 持续验证规则执行（怒怼 5 次 = 5 次验证），每次都让 CC 当下改文本（不靠 memory）
3. **模式 6 取舍 × 1** — 翻译密度 vs 不用英文，选不用英文（更彻底的方向）

**工程意义**：
- 规则不是定义出来的，是**怒怼出来的**（rules emerge from enforcement, not declaration）
- 同方向加严失败 N 次后，应该**改方向**而不是 N+1 次加严
- LLM 自觉性是工程不可靠组件 — 设计规则时不要假设 CC 一定做到
