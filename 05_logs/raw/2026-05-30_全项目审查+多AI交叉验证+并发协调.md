## [审查方法] 多 AI 交叉验证三层

### 背景 / 触发
itsuki 开 ultracode，要求「读每个文件、找所有 bug/漏洞/不正确/架构问题」。项目 1229 文件、5 端联动。

### 经过
- 第一批 workflow：17 审查单元并行 + 高危发现对抗性验证。54 分钟，只成功后端 5 单元（63 条），iOS/Android/文档 12 单元卡死（子代理读完不调结构化输出工具）。
- 第二批 workflow：拆小单元、去掉容易超时的验证环节，16 单元 10 成功（112 条）。
- 补审 + Codex 复核：3 个轻量子代理补 6 个失败单元 + Codex 独立复核 45 条 critical/high。
- 合计 175 条（12 致命 / 33 高危 / 63 中 / 67 低）。

### 关键判断 / 学到的东西
- **三层交叉验证互相纠错，价值远超单跑**：① 4 个 AI 一度集体误报「teachers.py 缺 import 会崩」——实际已被 /goal 修好；② 第二批说「iOS 全假数据」过度悲观，补审纠正「申请/登录其实真接了后端，只点呼+6类申请是假」；③ Codex 揪出 1 个误报（老师网页登录锁定其实后端有真锁定）。
- **不盲信 AI 清单，逐条核实再动手**：开修第一下就发现「误报」混在里面，立规矩——每条修前先自己 Read 核实当前代码状态。

### AC 价值
模式 4（多 AI 交叉验证 + 不盲信单点结论）+ 模式 2（假设崩了继续追）。可挂「我不是让 AI 跑完就信，而是设计了 workflow + Codex + 补审三层互相证伪，最后自己逐条核实」的工程判断力。

## [认知改变] 两个 Claude Code 会话并发改同一仓库会互相覆盖

### 背景 / 触发
审查到一半发现 git 工作区有我没改过的文件也变了 + 冒出新提交 `d9e65f1`。itsuki 澄清：那是他用 `/goal` 启动的「teacher_web v1.0 上线施工」自主会话，还在跑。

### 经过 / 关键判断
- 两个会话共享同一 git 工作区 + 同一 .git。我的 `schemas.py` dorm_unit 修复被 /goal 提交时改写（它用 `Literal[1,2,4]` 替代我的 validator，更优 — 但若它没看到我的改动就是直接覆盖丢失）。
- **原来「不 push 不等于安全」**：本地未提交改动会被另一个会话的提交/覆写吞掉。唯一保护方式 = 自己先 commit 固化（commit 进历史后工作区覆盖不影响）。
- 处理：iOS（/goal 不碰）安全修 + 自己 commit 固化；后端是 /goal 战场，我碰被覆盖，交给它系统性修。

### itsuki 原话 ⭐
「goal 不用你接手，你就去做你该做的就好」「只要不 push，其他的都可以，后期再改再修都无所谓」

### AC 价值
模式 5（认知改变：并发协作的工作区冲突，原来共享文件系统下「分工」不够、要么串行要么隔离工作区）。
