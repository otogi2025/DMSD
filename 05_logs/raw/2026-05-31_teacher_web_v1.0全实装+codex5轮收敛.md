## AC 价值点

**模式 6（多 AI 协作）顶级 —— 但核心是「不盲信 agent 自报」**
全程编排 20+ 个子代理 + codex 独立复审。关键不是「派活」，是**每次都独立验证 agent 的自报**：
- B3 修生产 alembic：sonnet 子代理说「改好了读 DATABASE_URL」，我去读 env.py 发现它**只改了用不到的 offline 路径，真正部署用的 online 路径没改** → 自己补上 + 用临时库真跑 `alembic upgrade head` 验证才确认。
- codex 第一轮抓出我修生产配置时**漏 import StaticFiles**（sonnet 子代理写了用法没写 import，配了就启动崩）。
- device_token 两个修复**互相打架**（一个加唯一约束、一个撤旧插新撞约束）——codex 抓的。
教训：agent 经常「只修一半 / 漏依赖 / 声称修对实际没」，CC 派活后必须自己核实，不能当二传手。

**模式 5（元认知）顶级 —— 多轮对抗复审才挖得到深层问题**
codex 5 轮，每轮都比上轮挖得深：第 1 轮表层 13 个 → 第 2 轮 3 个互相打架的 → 第 3 轮 2 个边界 → 第 4 轮发现**寮边界缺失是系统性的**（又揪 6 处「老师能跨寮操作学生」）→ 第 5 轮确认系统性关闭。单轮审查只能找表层，对抗性多轮才逼出「整类问题」。itsuki 的「审到没 bug 为止」不是口号，是真需要循环到 AI 自己说收敛。

**模式 2（主体性）—— 诚实划边界，不假装全做完**
NFC 防代刷后端零实装是核心安全缺口，但它属学生端 NFC 流程、不在网页范围。我没假装做完，明确标成 C 类「超范围 / 需单独立项」并写了立项计划。「可上线」我也诚实拆成「网页+后端达标」vs「NFC 防代刷 / push 投递 / 部署 ops 是另外的事」。没有用「全部搞定了」糊弄。

**操作教训：子代理在巨型单文件（25000 行 index.html）的删除/定位操作上反复卡壳**
前端子代理多次「调查完就停、不动手」。最后前端的精细删除（demo 组件 678 行 / 假数据 365 行）改成我自己写带边界断言的脚本删 —— 断言救过一次（行号因之前删 DEMO_MODE 上移了 3 行，断言检测到中止没删，文件没坏）。
