## 17:57 [方法论][反思] "100 次修改还是 v0.1" 不是错——错在媒介

### 起因

读完 17:56 的审查后 itsuki 问：

> "我从最开始跟 ai 讨论这个项目，在没有任何文档记录和实际动作的情况下，讨论了十几种方案然后才开始写最初的文档，这个最初的文档虽然还没写完但是也改了上百次，但版本还是最初的 0.1，你觉得这样正确吗？我应该从更早开始就进行迭代吗？"

### CC 的回答

**前两件事都对**：
- "先口头讨论 10+ 方案再落笔" = 专业工程师的习惯。早期"廉价探索"避免纸面惯性
- "v0.1 改 100 次不 bump 版本号" = SemVer 的本意就是"0.x 不稳定，什么都能改"。Rust 在 0.x 呆了好几年

**但丢了最重要的东西：迭代的痕迹**。

"改 100 次"有两种方式：
- (a) 每次改动都是一次 `git commit` → git log 里完整保留迭代轨迹，3 年后都能讲
- (b) 改动发生在 `.pages` 文件内部 → Git 只看到"文件变了"，不知道变了什么（二进制不可 diff）。100 次对外等于 1 个黑盒

**itsuki 的做法是 (b)**：git log 显示 `RollCall_Spec_v0.1.pages` 从 2026-03-08 到 2026-04-17 几乎没单独 commit——大部分改动在 Pages app 里直接发生，4-17 复制成 .md 才第一次让内容进 Git 可追溯。

→ **AC 入試 最想看"推翻了什么、为什么推翻"的证据，这些证据全丢在 .pages 黑盒里了**。

### 正确做法（未来或下一个项目）

1. Day 1 开一个 `.md` 草稿，哪怕粗糙三行笔记也行
2. 每次讨论后立刻 commit，message 写清楚"新增方案 D"、"推翻方案 A，理由 Y"
3. `.pages` 只用来排版出好看的 PDF 给老师看，不用来编辑内容

### 和 17:56 审查的同根

- 17:56 的批评：文档过度完美，代码零进展
- 现在的问题：前期讨论很多但没落笔，迭代不可见

**底层是同一件事**：思考和"物质化的产物（代码/commit）"之间脱节。
**修复也是一个**：把思考尽可能频繁地变成小的、可追踪的 commit。**频率本身比内容质量更重要**。

### 结论（给 itsuki 的一句话）

> 你做错的不是"该更早开始迭代"——你一直在迭代。
> 错的是"该从第一次讨论起就用 Git 可追踪的媒介（.md + 频繁 commit）记录"。
> 100 次修改如果在 .pages 里发生，对外等于 0 次；如果每次都 commit，对外就是 100 次。
> **AC 评委只能相信看得见的证据**。
