### H.1 模式分类

- **模式 1（派生痛点）× 1**：itsuki 修完 9 处后回头问「为什么会漂」— 把单次修复升级成系统诊断
- **模式 2（假设崩）× 2**：

  - CC 以为「文件名在 = OK」→ 实际行数 / 数字漂了 hook 检测不到
- **模式 5（元认知）× 3**：
  - 诊断时引用 §7.5.4 自己写的「LLM 自觉性 = 工程不可靠组件」反讽自己的项 8 设计
  - CC 自己改 hook 时 hook 自己触发 — 自指验证机制生效
  - CC 给 itsuki 改造「一眼看明白」的同时自己介绍新机制堆术语让 itsuki 看不懂（反讽）
- **模式 6（取舍）× 2**：
  - itsuki 选「覆盖整个项目」比 CC 提议的「扩白名单」更激进
  - 选 C 方案（双层）不选单层 A 或 B
- **主体性 5/5**：itsuki 5 次明确拍板（B 边改 / 全部修 / 全部修对账漂移 / C 方案 / 简单介绍）

### H.2 学术延伸性

- **软件工程方法论**：白名单 vs 全覆盖 — 哪个反模式 / 哪个更稳？
  - 白名单 = 性能优 / 维护成本高（每加新目录类型要加白名单）
  - 全覆盖 = 性能略损 / 维护成本低 + 不漏
  - 安全攸关场景倾向全覆盖（漏一个就出事）
- **机制设计**：「依赖 CC 自觉」是反模式 — 应该用「自动跑脚本」替代「人工填 checklist」
- **错误处理哲学**：itsuki 不修单 bug 升级成机制 — 「为什么会漂」比「漂了哪些」更重要
- AC 面试可挂：软件设计原则 / 工程治理思维 / 元规则演化
