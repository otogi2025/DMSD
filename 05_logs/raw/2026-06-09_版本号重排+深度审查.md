## 21:xx [认知改变][分歧][方法论] itsuki 纠正 CC 的版本号习惯 — 「一个 bug 一个补丁号」

### 背景 / 触发

itsuki 让 CC 审查 v0.15.0（上次发版本）之后攒的 95 个 commit，并「看能不能迭代版本」。CC 摸底后发现：本地比远程 `origin` 领先 423 个 commit，远程最后 push 停在 v0.8.0，v0.8.1 起全是本地标签。

### 经过（itsuki 三轮纠正，一轮比一轮深）

**第一轮**：CC 第一版方案给了「3 个次版本号」（把 bug 跟功能打包）。itsuki 否决：「拆开呀，不要全部归到一个里面来。我修 bug 类型，你都不帮我打最小的一个版本号吗？我之前的版本号有一堆问题。能不能区分出哪些是 bug 哪些是新功能？把我的版本号重新规划一下。」

**第二轮**：CC 又把审查找到的 bug 做成「要不要现在修」的三选一问题，还是把多个 bug 打包成一个补丁号。itsuki 怒怼：「我他妈的什么时候让你去找 bug 了？我说的是审查 + 帮我分版本号。我从 0.8 之后最后一次 push 是 0.8，我之后的版本号都是可以修改的。我每次都是直接 0.13 0.14 0.15 都不管就堆上来，没有 0.13.1、0.14.2 之类的堆叠，显得很单调。把单独修 bug 的找出来，重新给版本号建议。审查出来的 bug 直接放 TODO。」

**第三轮（认知突破）**：CC 还是把 11 个 bug 打包成一个 v0.16.1。itsuki 连环追问：「我 0.15 的时候就只修过一次 bug 吗？所以 0.15.1 然后 0.16.0，一次 bug 都没有吗？能不能不要算一起啊？**只需要每一个版本号都能对得齐就行了呀。还是说每个版本号都要有对应的 commit 记录，要不然不能算？**为什么你非得这么快就迭代中间的版本号，死活不给我迭代有 bug 修 bug 的这个版本号？」

### 关键判断 / 谁对谁错

**itsuki 是对的，CC 在套错习惯**：
- CC 默认套了软件界「一次发布打包多个 bug 修复」的惯例 —— 但那是给有真实用户的已发布软件用的。itsuki 的项目没 push、是自己留痕 + AC 叙事用，**根本不需要打包**。
- itsuki 自己推导出了语义化版本号（SemVer）的正确用法：**修一个 bug = 升一个补丁号（第三位），新功能批次才升次版本号（第二位）**。他甚至自己问出了底层规则「每个版本号是不是都要对应一个 commit」——这正是版本标签的本质（标签 = 钉在某一个 commit 上的标记）。
- CC 核实后发现：v0.15.0 之后的 29 个修 bug **每个都是独立 commit**，所以「一个 bug 一个补丁号」完全做得到，CC 之前说「散落的 bug 抠不出来」是想复杂了（那只在「硬凑不连续的 bug 成一组」时才成立）。

最终重排：32 个版本号（4 个功能里程碑次版本号 + 28 个一 bug 一个的补丁号），当前 v0.19.3。

## 21:xx [问题解决][方法论] 多代理深度审查 95 个 commit

### 经过

CC 派多代理工作流（6 个维度并行：演示账号隔离 / 时区根治 / 跨端字段对齐 / iOS 接线 / 3 个未提交改动 / 老师网页）审查 v0.15.0..HEAD 累积改动 + 3 个未提交改动，每条 finding 再派独立子代理对抗验证真假。共 29 个子代理。

结果：raise 23 条 → 对抗验证确认 19 条（0 阻塞 / 2 重大 / 12 次要 / 5 小）。后端 pytest 373 全过 + iOS 正式版/演示版双编译过。

itsuki 拍板：审查找到的 bug 全部丢 `TODO.md`，不在本次重排里修（审查 = 找问题，不是当场修）。

### AC 价值

- 对应核心问题：#1 問題発見、#3 問題解決
- 模式：模式 2/6（多 AI 对抗审查 + 不盲信，逐条独立验证）
- 展示：用多代理并行 + 对抗验证的工程方法找跨会话集成问题（codex 逐会话审过、但从没把整块累积改动当整体审过）
