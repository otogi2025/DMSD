## §18:45 · ⭐⭐ itsuki 一次指令推翻 4-tab 旧架构

### 问题发现 → 问题解决的过程

**itsuki 的重构方案**（一次性给出，无分步）:

1. **底部 nav 改 3 按钮**（不是 4 tab）:
   - 左：✉ 申し込み
   - **中：⭐ 点呼**（action button，徽章型大按钮，**不是 tab**）
   - 右：✦ マイページ
2. **Home omnibus**：主页承载"除 申し込み 和 マイページ 外的一切"（Community 全量 + 扣分 + 快递 + 遗失物 + 点歌 + 通知 + 活动 + 巴士 + 匿名建议）
3. **中央点呼按钮流程**：

   - 扫到 NFC → 绿色大勾 + 判定 badge + 3 秒自动退场
4. **注册 flow**（首次启动）：
   - 4 step：基本情报（氏名/生日/性别 自动分寮/头像）+ 学生区分（一般寮生/サッカー部）+ 联络先（邮箱/电话，不验证）+ 密码 ×2 确认

   - 账号 ID = 系统自动分配 2 位数字（00 为 demo seed，01+ 真实学生）
   - 登录 = 号码 + 密码，永久保持 session
5. **密码锁定升级策略**（全新设计）：
   - 连错 3 次 → 锁 30 秒 + 通报老师
   - 解锁后再错 1 次 → 锁 1 分钟
   - 再错 → 5 分 → 30 分 → 1 小时 → **永久锁死**（找宿管重置）
6. **iOS 26 Liquid Glass**：毛玻璃效果全 App 使用（Sheet / Top bar / Modal）— 因为 itsuki 的 iPhone 17 Pro 刚好是 iOS 26
7. **持续顶部点呼 bar**（全 App 常驻）：
   - 日常态：时间 + 下次点呼预告
   - 点呼中：倒计时"あと X 分で遅刻判定"
   - 已签到：绿色满 bar
   - 可点击 → 反馈 sheet（体调 / 请假 / 其他问题）
8. **导航规则**：

   - Level 2+ 左上 ← 返回

9. **个人主页真·记录深度**：マイページ 才是真看点呼履歴 / 扣分明细 / 处分历史 / 个人信息的地方。Home 只是"快速预览"。

## §19:00 · ⭐⭐ 00 号测试账户 "seed 魔法" 设计

**标签**：`#demo4-28 #ios #product-thinking #demo-engineering #AC候选🌟`
**对应 AC 核心问题**：#3 問題解決 · #4 自己認識

### 背景

注册 flow 拍板后的直接问题：**demo 当天 itsuki 当众走一遍注册，新建的账户就没有扣分历史、没有点呼记录、没有任何"使用过"的痕迹** —— 管理员看的是空账户，完全体现不出"这个系统运营起来长什么样"。

传统解法两种:

- A) **注册完 → 真的登入新建账户（空数据） + 额外切到 seed 账户演示** → 要多一步切换，管理员会看出来是假的 + 场面不流畅
- B) **跳过注册 → 直接登录 seed 账户** → 管理员看不到注册 flow，不知道新学生入住时怎么办

itsuki 的答案：**C) Demo 魔法 —— 注册流程演示 + 实际登入预 seed 00 号**。

### 设计

- Claude Design 必须默认 seed 一个 `00 号` 账户:
  - 氏名: **リュウ イヒ**（itsuki 本人的日语名）
  - 生日: 2006-10-14（19 岁）
  - 性别: 女 → 自动分配女寮 W101
  - 类别: 一般寮生
  - 当月扣分: **4 分**（迟到 2 + 缺席 3 = 0.5×2 + 1×3）→ 主页显示 🟡 "来月清掃罰則予定"
  - 30 日点呼历史 + 体调报告 2 件 + 扫除提交 2 件 + 快递领取 3 件已 seed
- Demo 流程:
  - itsuki 当众走注册 4 step，输入 リュウ イヒ / 2006-10-14 / 女 / 一般生 / 邮箱 / 电话 / 密码
  - 点击"アカウント作成完了" → **不真创建新账户**
  - App 检测到"输入值匹配已 seed 00 号" → 自动登入 00 号
  - Home 显示 4 分扣分 + 历史记录 → 管理员惊讶"已经有这么多数据了"
- 管理员看到的叙事: "从学生下载 App 到入住注册到使用半月到看到扣分提醒" 全流程闭环

### 为什么值得记 🌟

**这是 demo engineering 的高级技巧** —— 既展示"完整生命周期"又不污染 seed 数据。典型的 **product thinking**（以 demo 管理员为观众设计 experience） vs engineering thinking（按真实系统行为实现）。

AC 面试可以说:
> "Demo の時、新規学生が登録してから扣分が発生するまでの流れを全部見せたかったので、登録画面で入力した内容が既に seed している 00 号アカウントと一致すれば、自動的にそのアカウントにログインするという仕掛けを作りました。これで管理者には『完全なユーザーライフサイクル』が見えますが、実際に汚いテストデータを作ることもない。Demo 用の演出と技術実装を両立させた一つの工夫です。"

**AI 生成的方案很少想到"demo 专用魔法"** — 因为 AI 默认按"产品应该怎么运行"来推理，不考虑"场面效果"。这种**讲故事的能力** = itsuki 对"给谁看 × 展示什么 × 怎么让 ta 信"的敏感度。

### itsuki 原话

> "注册 flow 假装，创建一个 00 号，名字叫リュウイヒ，然后因为到了 4 分要罚扫，主页显示要罚扫，生日是 20061014，我到时候自己输入，但是实际上就是已经有的账户，只是走一遍注册流程"

"实际上就是已经有的账户，只是走一遍注册流程" —— 这句话准确描述了 **UI 骗过观众 + data 真实** 的两面。
