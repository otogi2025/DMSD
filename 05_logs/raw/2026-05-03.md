## §4 emulator click 卡住 → LaunchedEffect bypass

走完 Account 4 step → Welcome → Login。Login 屏 ログイン 按钮 input tap 540,1700/1750/1820 都没命中（系统 nav bar / status bar offset 导致 Y 坐标偏差）。试了 6 个 Y 坐标 + dismiss 键盘 + force-stop restart 都没用。

最终方案：在 LoginScreen 加一个 `LaunchedEffect(state.user.email)` — 注册完回到 Login 后 1.5 秒自动 submit 登入 → 跳 Home。这是 **demo 阶段合理的 bypass**，对应 iOS「アカウント作成完了 → 自動ログイン」体验。后续 production 阶段移除。

### 一段叙述

「私は AI と協働するときに、Tomoshibi Android アプリの 22 画面を実装する判断で、まず 4 セッション並行（git worktree × 4 + コントラクトファースト設計）を選びました。**理由は速度** — 一晩で 23 画面を 0 conflict で merge するため。実際 6000 行のコードが 1 日で書けて、技術的にはこのアーキテクチャは成功しました。

## §11 ⭐⭐⭐ #AC候選 — App Store 公開リスクに自分で気づいて「教師発行の登録コード」で塞いだ（問題発見 + 問題解決）

### 11.1 きっかけ（症状の発見）

5-03 上午、Android 整改が落ち着いた後、自分で次のことに思い至った：

> **「ちょっと待って — システムを App Store に出したら、世界中の誰でもダウンロードできる。誰でもダウンロードできるってことは、誰でも『寮生』として登録できるってこと？それは絶対ダメじゃない？」**

これは誰にも指摘されていない自分自身の気づき。CC が「セキュリティ的にどうですか」と問うたわけでもなく、お師匠先生が指摘したわけでもなく、ただ「App Store に出す」という工程を頭の中でシミュレーションしていたら、自然に出てきた疑問だった。

### 11.2 自分の元の思考の誤り（自己認識）

私は元々「App Store に出す」を **配布の利便性の話**としてだけ考えていた：
- 学生が **TestFlight や ad-hoc 配布より楽にインストールできる**
- iOS 26 の Liquid Glass / NFC など全部正規ルートで使える
- 学校の IT 担当が「個人の Mac から ipa 配ってます」と説明しなくて済む

つまり「上架 = 良いこと」と単純化していた。**ところが「上架 = 全人類に対して app を公開する」という側面を完全に見落としていた**。

ここで気づいたこと（自己認識として AC 価値高）:
> 「便利さ」と「公開範囲」は **同じコイン の表裏**で、片方だけ見ると判断ミスする。
> App Store に上架した瞬間、**配布チャネル = 学校内** から **配布チャネル = 全世界** に切り替わる。
> 学校内向け業務システムなのに、配布チャネルだけ全世界に広げてしまうのは、**鍵のかかっていない倉庫を駅前に置く**ようなもの。

### 11.3 問題を構造化する

この視点で問題を分解した：

| 観点 | App Store に出す前（TestFlight / ad-hoc） | App Store に出した後（対策なし） |
|---|---|---|
| ダウンロード可能な人 | 寮監が招待した端末のみ | 全 iPhone ユーザー（数億人）|
| 登録可能な人 | ダウンロードできた人のみ | 全人類 |
| 誰が「寮生」になれるか | 寮監 / 寮務が認知済の学生のみ | **任意の他人** |
| 結果 | 安全 | DB に偽寮生 / 部外者が混入する |

**「DB に偽寮生が混入する」** がなぜ深刻か：
- 点呼 dashboard に存在しない学生が現れる → 寮監が混乱
- 帰省届の chain に偽学生が紛れる → 教師が承認 / 不承認の作業を強いられる
- 規律スコアの集計が汚染される
- 最悪：偽学生が学生指導履歴に書き込まれて、**実在の生徒の評価データを破壊する**可能性

### 11.4 解法を考える（問題解決）

私の最初の解法案は **「教師発行の登録コード制」**：

> 「学生が App をダウンロードするのは自由。でも **登録の最後の step でコードを入力させる**。コードは **教師が Web 管理画面でボタンを 1 回押すと生成される**。コードはリアルタイムで更新される（時間で expire するか、教師が次のボタンを押すと前のコードは無効になる）。学生がそのコードを入れないと登録は完了しない。」

これは **シンプルだけど効果は大きい解** だと自己評価した。理由：

1. **コストが小さい** — 教師の負担は「ボタンを 1 回押す」だけ。コードは音声 / LINE / 教室の白板で学生に伝えられる
2. **学生の負担も小さい** — 学生が登録するのは入寮時の **1 回だけ**。一度登録すれば永久 session（既に決定済 §6.1）。だから「教師に毎回お願いする」状況は起きない
3. **物理的な信頼を保つ** — 「教師が今、目の前で / LINE で生徒に伝えたコード」を入れた人だけ登録可。**App Store の公開性 ≠ 登録の公開性** に分離できる
4. **既存の権限モデルと整合する** — 「寮務管理」権限を持つ教師だけがコードを生成可能（§3.4 教師権限モデル）。新しい権限階層を作らずに済む

代替案として考えた / 却下した案：
- ❌ **「学校公式名簿に名前があるか check する」** → 名簿の電子化が前提。当校は名簿が紙 + 各教師の Excel に散在しているので前提が成立しない
- ❌ **「メールアドレスのドメインで filter（例：tsukuba-koukou.ed.jp のみ）」** → 学生のメアドは個人 gmail / docomo 等 free address なのでドメイン filter が機能しない
- ❌ **「ad-hoc 配布のままにする / App Store に出さない」** → 配布の利便性を捨てる。せっかく Apple Developer Program 99USD/年 を払ったメリットが消える
- ❌ **「教師が学生 1 人 1 人に個別の登録コードを LINE で送る」** → 教師の手間が爆発する。一斉登録（入寮日に新入生 30 人）の場面で詰む

→ 結論：「**教師が 1 つのコードを生成 → 同時間帯の生徒は全員そのコードで登録**」が一番バランスが良い。

### 11.5 実装の細部（自分で考えた仕様）

CC と相談しながら以下の実装仕様を確定：

| 項目 | 決定 |
|---|---|
| コード形式 | 6 桁数字（例 `483271`）— 短く、口頭で伝えやすい |
| 有効期限 | 5 分間（短すぎず長すぎず、新入生説明会など集団登録で十分）|
| 同時有効コード数 | システム全体で **1 個のみ**（運用シンプル化、教師が新コード生成すると古いコードは即無効）|
| 生成権限 | 「寮務管理」権限を持つ教師のみ |
| 生成 UI | 教師 Web 後台「学生登録コード」パネル — 「生成」ボタン + 現在のコードを大きく表示 + カウントダウン |
| 学生側 UI | 登録 flow の **最終 step**（パスワード設定の次）に「教師に発行された登録コードを入力してください」screen 追加 |
| 失敗時 | 「コードが正しくないか、有効期限が切れています。教師に再発行を依頼してください」エラー |
| 監査 | 各コード生成 / 使用イベントを audit log に残す（誰が何時に生成 / 誰が何時に使用） |

**「実時間更新」の意味について自分で決めたこと**：
- 学生が登録 page を開いている間、教師が新しいコードを生成すると、学生側は古いコードを入れても通らない
- これは **意図的な設計**（教師が「次のグループの登録を始めます」と言って新コード生成 → 前のグループは登録完了済 / 後のグループは新コードで登録、という時間的分離が可能）

### 11.6 trade-off の整理

「教師の手間 vs 安全性」のバランスを書き出した：

| 観点 | コスト |
|---|---|
| 教師：ボタン押す回数 | 入寮シーズン（4 月）に集中 / 集団登録 1 セッションで 1 回押せば済む |
| 学生：1 step 増える | 登録時の 1 回のみ（永久 session なので再登録なし） |
| 部外者：登録できる確率 | コードを物理的に知っていない限り 0（5 分後には期限切れ）|
| 教師：忘れた / 誤って共有 | コードはすぐ無効化できる（次のボタン押下で古いコード即死）|

→ **「教師に 4 月の入寮シーズンに数回ボタンを押してもらう」という小さなコスト** で、**「全人類を対象にした登録口を実質的に閉じる」という大きな効果** が得られる。明らかに割に合う。

## §12 真机装机 codesign 死锁全过程

### 12.1 我发现的问题

我已经付了 99 美元 Apple Developer Program 一年的费用，理论上能装 app 到我的 iPhone 17 Pro。但是 Xcode 顶部一直报 Build Failed。

最初我连 Xcode 的 Run 按钮在哪都不知道（在最顶部 toolbar 第 6 个图标），找了一会才点到（情绪：初学者烦躁 — 我说"他妈的哪里有 run 这个按钮？"）。CC 教我：「**`⌘R` = Command + R 快捷键就是 Run，不用找按钮**。如果 ⌘R 没反应是因为焦点不在 Xcode，先点一下窗口任意位置再按。」

学到：iOS app 开发里 ⌘R 是最高频快捷键 — 编译 + 装到选中 device + 启动 app，一气呵成。专业开发者基本不点那个三角按钮。

然后点击之后弹出窗口说：

> The executable is not codesigned.

我不知道这是什么意思，于是问 CC。

### 12.2 我学到的概念：代码签名（code signing）

CC 教我：

> Code signing = 苹果的"身份证盖章"制度。任何 app 装到真机前，必须用一个"开发者证书"在 app 上盖一个数字章，证明"这个 app 是某个注册过的开发者做的，不是病毒"。如果 app 没盖章，iPhone 拒绝安装。

我之前不知道苹果有这个机制 — 我以为我付了钱就能直接装。原来还要 app 本身被"盖章"才行。

附带学的：

- **Developer Program 99 美元** = 让我在苹果服务器有"开发者身份"
- **证书（certificate）** = 苹果发给我的"私钥"，用来给 app 盖章
- **Provisioning Profile** = 苹果发的"哪些设备允许装我的 app"的许可证
- **Bundle Identifier** = app 的唯一 ID（我的是 `com.itsuki.tomoshibi.demo`）

### 12.3 排错过程

CC 让我先去看 Xcode 的 Signing & Capabilities 面板，截图发给它看。

我截图后 CC 说：所有签名配置都是对的（"Automatically manage signing" 打勾、Team 是 LIU YIFEI、证书是 Apple Development）。但 build 出来还是没盖章 — 这说明配置看起来对，但底层有什么东西"覆盖"了配置。

CC 然后用命令行直接检查 build 出来的 .app 文件，发现「code object is not signed at all」+ `_CodeSignature` 文件夹根本不存在 — 验证 app 真的没盖章。

接着 CC 用 grep 搜了项目文件 `project.pbxproj`，找到 3 处被显式写了：

```
CODE_SIGNING_ALLOWED = NO;     ← 不许签名
CODE_SIGNING_REQUIRED = NO;    ← 不要求签名
```

这 3 行就是罪魁祸首 — 不知道是之前哪个 agent 为了让模拟器跑得快加的（模拟器不需要签名），但这把真机部署也堵死了。

### 12.4 期间还有一个 distraction：苹果发邮件说取消我的证书

排错过程中我的邮箱收到苹果邮件：「您的证书已被撤销」。我担心账号被入侵，问 CC。

CC 解释：

> 大概率是 **Xcode 自动证书轮换**（cert rotation）— 这通常正常。Automatic signing 模式下 Xcode 会自动管理证书，发现旧证书状态不一致时自动 revoke 旧的 + 创建新的。苹果会发邮件告知，这是安全通知机制（每次有证书操作都发邮件）。
>
> **判断**：如果 GUI 当前显示的证书是有效的（Apple Development: LIU YIFEI），那邮件说取消的应该是某个旧的，不是当前正在用的。如果短时间内连续收到多封"取消"邮件 + 自己没动，才要警惕账号被入侵。

学到：苹果有完整的安全通知系统，开发者每次证书操作（创建 / 撤销 / 续期）都会收邮件 — 跟银行交易通知一样。

### 12.5 学习要点：GUI 配置 vs 底层 build setting 的不一致

我学到一个重要的工程概念：**Xcode 的 GUI 显示的设置只是装饰，真正生效的是 .pbxproj 文件里的 build setting**。如果 GUI 显示"Automatically manage signing 打勾"但 .pbxproj 里写了 `CODE_SIGNING_ALLOWED = NO`，**底层禁止签名优先**。

也就是 GUI 给的是"看起来对的假象"，真相在文本配置文件里。这种"两层之间不一致"是工程里很常见的 bug 来源 — 比如 docker compose 配置 vs runtime env、git 配置 vs hooks 行为、CSS class vs inline style…

CC 直接帮我删掉 3 处 `CODE_SIGNING_ALLOWED = NO`，备份了原文件到 `.bak2`。Clean Build Folder + 重 build → 装机成功。

### 12.6 还学了：xcodebuild 命令行 build vs Xcode GUI build

后来 CC 用 `xcodebuild -sdk iphonesimulator -configuration Debug build` 命令验证代码能不能编译（用模拟器 SDK，不需要 codesign）。我学到：

- **xcodebuild** = Xcode 的命令行版本
- **`-sdk iphonesimulator`** = 用模拟器 SDK（绕过 codesign，因为模拟器不需要签名）
- **跟 GUI 的 ⌘B 区别** = 命令行可以脚本化、可以在 background 跑、可以 grep 输出找错

这个工具后来帮我们多次确认"SourceKit 报错是误报"（命令行 build 通过 = 代码真的 OK，SourceKit 只是 lint 误判）。

### 12.7 AC 价值

完整 troubleshoot cycle：错误信息读取 → 假设(缓存)→ 排除假设 → 检查项目文件底层 → 定位禁用签名 → 修复 → 装机成功。

5 大 AC 问题对应：
- **#3 問題解決**: 完整的从症状到根因的诊断方法（不停留在"按 build 看输出"，而是钻到底层文件检查实际配置）
- **#4 自己認識**: 学到了"GUI vs 底层配置不一致"是常见工程 bug 模式 + 学到 ⌘R / xcodebuild / GUI vs CLI 几个重要概念
- **#1 問題発見**: 自己装机时主动注意到错误信息，没忽略

## §13 SwiftUI bottom sheet 学习：ignoresSafeArea

### 13.1 我发现的问题

装机成功后，我点击 app 里的"点呼"按钮，弹出 NFC 扫描准备 sheet。但发现：sheet 弹出后**底部到 home indicator（屏幕底部小横条）之间留了一段灰色空白**。明显不好看。

### 13.2 CC 教我的概念

CC 让我看了项目里自研的 `GlassSheet.swift`（项目用了自研的 bottom sheet 而不是 SwiftUI 原生 `.sheet()`，因为原生的有些限制）。

CC 解释：

> SwiftUI 默认所有 view 会"避开"屏幕底部的 home indicator 安全区（safe area）。所以 sheet 容器停在 safe area 边界上方，下面留了一段"让出来"的灰色。如果想让 sheet 物理延伸到屏幕底部，要在 view 上加 `.ignoresSafeArea(edges: .bottom)`。

修法只有一行：在 GlassSheet 外层 VStack 加 `.ignoresSafeArea(edges: .bottom)`。这样 sheet 圆角白色背景延伸到屏幕物理底部，"取消"按钮 padding 控制在 home indicator 上方约 6pt 处 — 这正是 iOS 标准 bottom sheet 视觉规范。

### 13.3 福利

修这个 GlassSheet 同时影响**所有用 GlassSheet 的弹窗**（点呼 / 体调报告 / 缺勤届 / 其他届 / FeedbackSheet）— 一处修，处处修好。这是"封装的力量" — 我自己设计 app 也要尽量把重复元素封装成 component，改一次到处生效。

### 13.4 AC 价值

- **#4 自己認識**: 学到了 SwiftUI safe area 概念 + ignoresSafeArea modifier + "封装的力量"
- **#3 問題解決**: 一行代码解决全 app 的 sheet 视觉一致性

## §14 Apple Image Playground 5 秒延迟 + perceived performance 策略

### 14.1 我发现的问题

装机后我去注册流程第 1 步，点"AI で生成"按钮想生成头像。但点击后**等了 5 秒**画图工具才弹出来。我觉得太慢，问 CC 能不能优化。

### 14.2 CC 教我的概念

CC 解释：

> Apple Image Playground 第一次打开时要把 ~3GB 的 Apple Intelligence 模型从硬盘加载到 RAM。这是「cold start」（冷启动）。第二次会快（模型已 cached）。**但苹果没有暴露 public API 让开发者直接 prewarm**，所以无法真正消除这 5 秒。

### 14.3 解决思路：perceived performance（感知性能）

CC 教我一个 UX 工程概念 — **perceived performance（用户感知的性能）**：

> 既然我们没法真正加速，至少让用户**不觉得 app 死了**。点击按钮后**立刻**显示 loading 反馈 — 按钮变 disabled、文字变"準備中…"、加 spinner。这样：
> - 实际：还是 5 秒
> - 感知：用户知道 app 在响应，焦虑感大幅降低
>
> 这是工业里的经典做法：Apple App Store 下载用 progress bar + "残り 30 秒" 文案、YouTube 加载用 skeleton screen、网页用骨架屏 — 都是 perceived performance。

### 14.4 学习要点

我学到一个重要思维：**当无法解决底层性能问题时，改用 UX 技巧管理用户期待**。这跟我之前以为"慢就要变快"的想法不一样 — 实际上很多时候"慢"是物理限制（网络 / 模型加载 / 数据库 query），但用户的"觉得慢"可以被引导。

CC 推荐我用 A 方案（极简 loading state），我决定采纳。

CC 改了 `AuthStubs.swift`：加了 `@State isLoadingImagePlayground`、按钮点击立刻 set loading = true + 触发 sheet、5.5 秒后兜底复位（覆盖最长 cold start）、按钮 label 在 loading 时切换、按钮 disabled。

### 14.5 AC 价值

- **#4 自己認識**: 学到 perceived performance 概念（一种"绕过物理限制的 UX 思维"）
- **#1 問題発見**: 自己注意到性能问题
- **#3 問題解決**: 接受"无法直接修，但可以改 UX 管理感知"的方案

## §15 ⭐⭐⭐ 老师公告（お知らせ）功能拍板 + Apple Intelligence 平台姿态决策

**对应 5 大 AC 问题：#1 問題発見 + #2 問題意識 + #5 志望動機**

### 15.1 我发现的需求

之前的 app 设计里没有"老师群发通知"的功能。我突然意识到 — 我们宿舍管理员经常要通知活动 / 时间变更（比如"明天点呼时间临时改成 8:30"），现有 app 里没有地方做这件事。

我跟 CC 说：要做一个类似 Google Classroom 那种功能 — 老师可以发消息，学生在主页能看到，可以点开看详细，可以回复，可以看日期。

### 15.2 命名小插曲：「お知らせ」vs「社区中心」

我一开始用了"社区中心"这个词，CC 误以为我想重启之前 4-29 砍掉的 Community 整体功能（学生互动板）。我后来澄清"我说的不是社区中心，就是类似 Classroom 一样老师通知的页面，反正你自己用日语命名"。

CC 推荐用「お知らせ」(中文意思：通知 / 公告) — 这是 Apple iOS 系统通知中心、Google Classroom 日文版、LINE 公告、各日本 app 都在用的最标准日语词。我同意。

学到：跟 CC 沟通需求时**避免歧义命名** — "社区中心"在我脑子里是"老师发通知"，在 CC 脑子里是"学生互动板"。两个完全不同的功能，差异点在"谁发 / 谁互动"。

### 15.3 CC 跟我确认细节

CC 帮我把模糊需求拆成具体决策点：

| 决策点 | 我拍板 |
|---|---|
| 范围 | 全宿舍 / 男生限定 / 女生限定 三档（不细分到楼层 / 学年）|
| 通知方式 | iOS push + app 内红点 badge 都要 |
| 学生回复可见性 | 所有学生都能看（透明 + Classroom 同等氛围）|
| Home 入口位置 | 主页顶部第 2 块（挨拶 + 减点 Card 之下）|
| AI 总结 | 加（用 Apple Intelligence 总结公告 + 回复）|
| 翻译 | 加（日 ⇄ 中，方便我和其他留学生）|

CC 帮我把这些都写到了 `system_features.md §7.15`，12 个子节，包括数据模型、API、v1.0 vs v1.1 拆分。

### 15.4 ⭐ 我的体系化决策：Apple Intelligence on-device 推理路线统一

CC 提出几个技术选择：
- AI 总结可以用 ChatGPT API / Gemini API / Claude API（云端）
- 也可以用 iOS 26 自带的 Foundation Models framework（设备本地推理）
- 翻译可以用 Google Translate API / DeepL API（云端）
- 也可以用 iOS 17.4+ 自带的 Translation framework（设备本地）

我决定：**全部用 Apple 平台原生 framework**，不用任何云端 AI API。理由 5 条：

1. **运营成本 0**：不用付 API 费用、不用管 API key
2. **学生隐私完全保护**：宿舍生的回复不会出现在第三方公司的服务器上
3. **离线可用**：宿舍 wifi 出问题时也能用
4. **Apple Intelligence 非对应设备就 hide 这些按钮**：UX 一致，没有错误信息
5. **跟 Image Playground 同套理念**：app 整体押注 Apple 平台原生 AI 能力

### 15.5 AC 叙事价值（这是最重要的部分）

CC 帮我看到了这个决策的 AC 价值 — 这不是单纯的"功能怎么做"，而是**体系化的技术哲学决策**。

AC 评委如果问"为什么不用 ChatGPT API 这种最流行的"，我能用 5 个维度系统地回答：成本 / 隐私 / 离线 / UX / 平台一致性。这种"看到表面选择背后的体系化思考"是 AC 评委最关心的"思考力"。

而且这串决策不是孤立的：
- Image Playground 头像（5-03 早些时候已实装）
- Foundation Models 公告 AI 总结（5-03 spec 决策）
- Translation framework 翻译（5-03 spec 决策）
- 三个一起 → "Apple Intelligence on-device 路线统一"

这个故事我能在自我推荐书里写一整段。

### 15.6 一个我学到的元教训

CC 告诉我一件事我以前没意识到的：**CC 推荐了技术选型 + 我决定采纳/拒绝 = 算我的判断**，不是 CC 的判断。AC 评委关心的是"判断力 + 推动事情成形的能力"，不是"我自己写了多少代码"。所以下次写 AC 素材时我要直接写"我决定采用 Apple Intelligence 原生路线 because XYZ"，不是"CC 提议我同意"。

### 19.2 CC 的失误集合（重要 — 体现真实协作）

我应该记 CC 不是完美的，犯了几次错：

#### 19.2.1 CC 用术语没解释（违反 feedback_explain_terms_to_itsuki）

## §20 ⭐⭐ #AC候选 — Apple 风格 App 图标 v2 全平台同步替换（自己認識 + 問題解決）

### 20.1 起因

5-03 晚 19:10 左右，我意识到 v0.5 阶段已经把 README public 化了，但仓库里用的还是早期一张「红黑描边贴纸风」的 tomoshibi_flame_color.png — AC 评委来看 GitHub 的话，第一眼看到的是这张 sticker 风图标，跟我整个项目的「日本宿舍 + 灯火守护」叙事调性不搭。

我决定升级图标到 Apple HIG 风格（Liquid Glass / 玻璃质感 / 渐变背景），并且**全平台同步替换**（iOS / Android / Web / GitHub README）。

### 20.2 我学到的概念（CC 教 + 我学会的）

**(a) 「贴纸风 vs Apple 风」的本质区别**

我之前不知道为什么市面上 app 图标都没有黑色描边。CC 解释：
- **贴纸风**（Sticker）：黑色硬描边 + 平涂色块 + 白底。靠"轮廓线"撑形状。
- **Apple 风**（Liquid Glass，iOS 26 起）：渐变色块 + 玻璃反射 + 内发光 + 顶部高光。靠"光影"撑立体感。

这两种是**完全不同的设计语言**，不能"加效果转换"，本质上要重画。我现在能向别人解释为什么 Discord / Slack / Notion 的图标都没黑描边了。

**(b) Icon Composer + .icon 文件格式**

Apple 在 WWDC 2025 发布的新工具，把图标做成**多层 .icon 包**（`.icon` 其实是个 macOS bundle，里面是 JSON + PNG 图层）。一个 .icon 文件能自动适配 iOS / iPadOS / macOS / watchOS 4 平台 + Light / Dark / Tinted / Clear 4 种外观模式。

我手动操作流程：
1. Photoshop 里去掉黑描边（Color Range 选黑 → Delete）
2. 导出透明 PNG
3. 拖进 Icon Composer
4. 配 linear-gradient 背景 + 开 Liquid Glass effects
5. 保存为 Tomoshibi.icon

这是我第一次接触 Apple 的官方设计工具，以前一直以为图标都是 Sketch / Photoshop 一条龙做完的。

**(c) Android adaptive icon vs legacy webp**

Android 8.0 (API 26) 起引入 **adaptive icon**：
- `foreground` drawable（前景，火焰本身）
- `background` drawable（背景，渐变色）
- 系统在不同启动器（Samsung / Pixel / 小米）下用不同的 mask 形状（圆 / 方 / 水滴）裁切

API < 26 的旧设备 fallback 到 `mipmap-{密度}/ic_launcher.webp`。所以一套图标要做：
- 5 种密度的 legacy webp（48 / 72 / 96 / 144 / 192 px）
- 5 种密度的 adaptive foreground PNG（108 / 162 / 216 / 324 / 432 px）
- adaptive background drawable XML（用 `<shape>` 的 gradient）

iOS 不需要这么麻烦 — Apple 用 `.icon` 一个文件搞定。

### 20.4 工程方法学到的

**(a) 「单源真值」原则**：所有派生文件都从一个 master 生成，不手动维护多份。

我建立的 master：`06_assets/icons/tomoshibi_app_icon_v2.png`（1024×1024）。
派生：
- iOS Icon-1024.png（直接 copy）
- Web tomoshibi-icon.png × 2（直接 copy）
- Android 5 密度 webp（sips + cwebp 等比缩放）
- Android 5 密度 adaptive PNG（裁切 bbox + 缩放到 67% 安全区）
- README 256 缩略图（PIL thumbnail）

下次要改图标只改 master 一个文件 + 重跑生成脚本。

**(b) 「工具不够就 brew 装」**：

CC 一开始检查工具链发现没有 `cwebp`（Google 的 webp 编码器）和 `Pillow`（Python 图像库）。决策：直接 `brew install webp` + `pip install Pillow`，不绕弯子用其他方法。

我学到：碰到「这个事情现成工具该有但我没装」时，**装就完了**，不要靠不完善的替代方案硬撑。

**(c) 「先做 master，再分发」的顺序**：

不能一上来就替换 iOS 的图标 — 因为还要给 Android / Web 用。先做出统一的 master，再分发到各端，这样所有端视觉一致。

### 20.6 AC 角度可以讲的

1. **跨平台一致性思维**（情報科学類 SWE 基本功）：从一个 master 派生 12+ 个文件，每个目标平台的尺寸 / 格式 / 命名约定都不一样，但视觉一致。这就是工程师做事的方式。
2. **工具识别能力**：从"我不知道有 Icon Composer 这个东西" → "我学会了 .icon 文件格式 + Apple HIG 设计语言演进 (Skeuomorphic → Flat → Liquid Glass)"。这是 AC 评委希望看到的"会主动学习陌生工具"的证据。
3. **"我决定走 AI 协作路线"**：图标设计是专业设计师领域，但我作为零基础高中生，用"AI 辅助 + 工程脚本批量生成"的路径，3 小时做完了通常需要 1-2 天的工作。这是工程判断 — 把时间花在功能上，把"美工"任务交给工具。
