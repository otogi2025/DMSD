# 2026-06-03 版本号回溯规范化（v0.8.1 ~ v0.12.0）

## 起因

itsuki 问「现在整体版本是多少」。CC 查 CHANGELOG + WIP 发现：标记还是 **v0.8.0**（5-02 close），但之后到 6-02 累积了 **236 个 commit 未 bump**，且 **GitHub 远程停在 5-11（last push）**，本地领先 236 commit、三周多没推。

## itsuki 的两个初始想法（都被 CC 拦下并解释）

1. **「把 0.8 之前全部版本号重新分配」** — 重写整个历史编号
2. **「近期 236 commit 直接更新到 v10.0」** — 觉得改动多版本号该跳大

itsuki 自陈：「之前根本是按照感觉更新版本号的，一点都不规范」+ 纠结「之前大版本号跳，现在变小版本号跳」。

## CC 的纠正（教练时刻 — 教 SemVer 规则）

- **v10.0 不行**：语义化版本主版本号 = 重大不兼容改版 / 正式上线代数。项目早定 `v1.0 = 宿舍正式上线`，连第一次上线都没到就跳 v10.0 = 假装迭代了十代，反而最不专业。**commit 数量 ≠ 版本号增量**，SemVer 只看改动性质不看改了多少。
- **重写历史不建议**：① 23 个标签已 push 到 public repo，业界视为不可变；② 那段「不规范」历史（讨论→文档→代码 三段式演变）正是 AC 叙事金矿，重写等于毁证据链。
- **「大跳变小跳」其实是对的**：节奏从次版本号跳变成修订号跳，反映项目从「设计期」进入「实装期」，是版本号忠实反映真实状态。

## itsuki 拍板

- 历史 v0.0.1~v0.8.0 **全部保留不动**
- 近期 236 commit **拆成「它本应该的版本号」**（itsuki 原话，要用上 0.8 后面还没用的数字）

## itsuki 的严谨（不盲信 CC）

CC 给出 6 版本切分方案后，itsuki 主动提醒：**「其中应该也修了很多 bug。你要先确认好了再去做。」**

→ CC 据此对 6 段逐段统计 feat / fix 数量 + 列出每段全部 feat 标题验证定性。关键确认结论：**「修了多少 bug」不影响 minor / patch 判断 —— 只要一段有真新功能就是次版本号（哪怕同时修 30 bug），纯修复 / 工具链才修订号。** v0.12.0 即典型（30 fix vs 8 feat，仍 minor，因 8 feat 是 iOS 接真后端真功能）。
