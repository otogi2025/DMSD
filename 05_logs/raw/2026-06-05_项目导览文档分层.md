## [认知改变][技术判断] itsuki 提出「文档按读取频率分层」的信息架构直觉

### 背景 / 触发
itsuki 开场问：「我这次服务器是不是缺一个可以一下就了解整个项目的文件？」他自己点出关键约束——心智模型（每次会话开局都读的）不能太长，但又需要一个详细的、能让新会话/新人深入理解项目的文件。

### 关键判断
itsuki 不是泛泛要「一个介绍文件」，他清晰地区分了两种文件的**读取频率 × 详细度**：
- 每次都读的 → 必须短（心智模型）
- 需要时才读的 → 可以长、定期更新（深度文档）

排查后发现项目其实已经是三层结构：`项目心智模型.md`（开局必读、1 屏）/ `PROJECT_GUIDE.md`（深度、按需）/ `project-overview`（文件字典）。itsuki 的直觉跟现有设计完全吻合，只是 PROJECT_GUIDE 当时太简单、project-overview 漂移了。

### itsuki 原话 ⭐
> "我现在服务器是不是缺一个可以一下就了解整个项目的文件？心智模型的话是每次都读，所以不能做得太长。如果想要一个新的绘画或者一个新的人非常详细地了解我这整个项目，我是不是还缺文件呢？那个文件不用每次读，只有需要的时候才要读，然后一段时间更新一次，这样的。"

> "这个的话内容太少了。我要迅速地理解，深入理解整个项目。然后也能让 AI 深入理解整个项目。所以不要写得太简单，不要丢失信息。"

### AC 价值
- 对应核心问题：#问題発見 #技術判断
- 展示了什么：信息架构判断力——按「读取频率」给文档分层，而不是把所有信息堆一个文件。这是文档系统设计的核心权衡（常驻成本 vs 信息完整度）。
- 可能用在自我推荐书：「如何管理一个 1396 文件、5 端联动项目的认知负荷」叙事。

## [问题解决][失败与修正] CC 对账时发现两个工具数字打架，查到是多会话暂存区污染

### 背景 / 触发
对账 project-overview 体量表时，CC 用 `git ls-files` 数得 1388 个文件，但项目自带的对账脚本 `check_overview_drift.sh` 报 committed 1396，差 8 个，而且差异方向不一致（有的脚本多、有的 CC 多）。

### 经过 / 关键判断
CC 没有盲信任何一方，而是查 HEAD（已提交快照）vs index（暂存区）：跑 `git ls-tree -r HEAD` 数得 1396，跟脚本一致。真因是——**在 CC 干活这段时间，别的会话动了 git 暂存区**（从 1388 加到 1396）。这正是 itsuki memory 里那个「多会话共用 git 暂存区」的坑实时发生。

判断：体量表应该锚定 HEAD（仓库真实提交状态），不用 index（会被并行会话波动影响）。提交时也用显式文件名只带这两个文件，不碰别会话的改动。

### AC 价值
- 对应核心问题：#問題解決 #失敗と修正
- 展示了什么：转述工具结论前先审前提（不盲信单一数字源）+ 多会话并行协作的工程认知（共享暂存区风险）。这是 CC 主动发现的（§0.3），过程也是 itsuki 的——他建的多会话协作机制 + memory 记的坑发挥了作用。
- 印证已有 memory `feedback_shared_staging_area_commit_contamination`（又一次实测案例）。
