## ~23:30 [版本管理判据] v0.3.1 tag 不等 Tier 1 全完成就发布

### 背景 / 触发

CC 读完版本管理指南后，有一个关键判断需要做：

**v0.3.1 tag 在什么时候打？**

两个候选：
- A. **等 Tier 1 全 11 项闭合才打** —— "完整性优先"
- B. **Batch 1/2/3 CC 侧做完就打，γ 类留 v0.3.2** —— "小步快跑"

### 问题发现 → 问题解决的过程

对照指南 §2 / §3 的明确定义：

**§2 "详细判断表"**：
- 修 bug / 改错别字 / 小优化 → Patch
- 新增门面文档（README）+ 补必要外观（showcase）+ 修正到事实一致 —— 都在 patch 范围

**§3 "什么时候该打版本号"**：
- ✅ "攒了一批小修复，准备发布 → 打 Patch"
- ❌ "每次 commit 都打版本号（太频繁）"

**§5 "文档版本 vs 软件版本"**：
- "0.x 阶段文档规格本身也算项目产出" —— spec 实质变动可 minor bump（v0.2.0 / v0.3.0 的做法）
- 本 v0.3.1 是"文档层 AC readiness 补强"，不涉及 spec 实质内容 → 不是 minor

**§12 DMSD 版本规划（本次发现过时）**：
- 指南写 "0.3 后端骨架 FastAPI"，实际 0.3.0 是 spec 主体 rewrite（零代码）
- 本 v0.3.1 不在指南原规划里 —— 但**项目实际演化可以偏离原规划**，指南应该跟着改（M2 新增）

**结论**：按指南 §3，B 方案（小步快跑）更合语义。**"攒了一批小修复准备发布" = Batch 1 + CC 侧的 Batch 2 / 3 一起发 patch。不必等 itsuki 粘完 draft。**

### 心路历程 / 推测

[CC 自我反思] 如果选 A（等完整），会有什么后果：

- **v0.3.1 拖到 itsuki 有空粘 draft 才打** —— 可能几天甚至一周
- **中间的 commit 全悬空**（既不在 v0.3.0 也不在 v0.3.1） —— 对 "发布视角" 的教授来说是一团乱
- **itsuki 的工作压力变成"必须粘完才发布"** —— 但粘 draft 需要她审核，审核需要脑力，可能今天做不完

选 B（小步快跑）的好处：

- **v0.3.1 立刻封存** "CC 侧的 AC readiness 工作" → 一个清晰的 checkpoint
- **itsuki 的工作完全解耦**：她可以明天、后天、或任何她有精力的时候粘 draft → 粘完立刻 v0.3.2
- **commit log 清晰**：教授读 `git log --oneline` + `git tag` 能看到 "v0.3.0 = spec rewrite / v0.3.1 = AC readiness 文档层 / v0.3.2 = 手笔区合并"

**核心判断**：**"完整性" 不是发布的前提，"可用性" 才是**。v0.3.1 的 CC 侧产出是完整可用的（README 教授能看、原创设计 showcase 能读、backlog 11 ⏳ 的 draft 已 ready）——**不发布等于白做**。

### AC 视角

- **#3 問題解決** — 按指南语义而不是理想化标准打 tag。展示"工程节奏判断"：**小步迭代 > 完美等待**
- **#4 自己認識** — 识别"完整性思维"的局限，承认 "v0.3.1 是阶段 checkpoint 不是终点"
- **版本管理成熟度** — 不每 commit 打 tag（指南 §11 错误 2），也不憋到"全好了"才打（造成悬空 commit）。**取中间节奏 = patch = 攒一批小修复发布**

- **多会话协调边界**：每个会话负责自己的产出的 commit。CC 不代管别人的工作

[CC 自我] 这个判断的关键是**承认"我不是唯一的写手"**。

- 把下午会话的 AC 素材 dump（有 `#AC候选` 标签的素材）混在自己的 commit 里 → **commit attribution 混乱**（看 commit author 只能看到 itsuki，但 dump 是谁起的看不出）

**选 B 的协作意义**：**让下午会话自己的产出保持"待处理"状态 → 触发他们下次开会话补完 WIP 更新 + commit + 对应的 raw append**。是"温柔但坚定"的协作边界。
