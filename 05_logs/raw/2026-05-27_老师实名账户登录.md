## 17:30 [问题发现] itsuki 打开 web 看到 501 错误 — 双服务器分离概念学到

### 背景 / 触发

CC 在前一段会话尾报告 v1.0 frontend 主线完成 + 让 itsuki 自己测，提示「双击 `开发模式跑.command` 打开浏览器到 8787 + 终端跑 backend python 起 8000」。

itsuki 发截图：浏览器打开 `localhost:8000` 看到一行 JSON `{"service":"Tomoshibi Backend v1","version":"0.1.0-v1-skeleton","env":"dev"}` — 以为这就是 web。

### 经过

CC 解释 itsuki 打开错地址了 — `localhost:8000` 是 backend 的「健康检查响应」（backend 跑起来证明自己活着的一行 JSON），没有真正的 web 界面。老师 web 在 `localhost:8787`。

itsuki 跟着双击 `开发模式跑.command` 后再发截图 — LoginScreen 加载出来了（旧版共用密码版），但点登录按钮报「サーバーエラー (501)」红条。

CC 诊断 501 原因：
1. 旧 LoginScreen 调用 `${API_BASE}/sessions/teacher`，但 `window.API_BASE = "/api/v1"`（相对路径）
2. 浏览器在 8787 跑 → 拼成 `http://localhost:8787/api/v1/sessions/teacher`
3. 8787 = Python 静态文件服务器（`python3 -m http.server`），只能发回 HTML/CSS/JS，不认识 `POST /api/v1/...` → 返 501 Not Implemented
4. 真 backend API 在 8000 端口，不在 8787

### 关键判断 / 学到的东西

itsuki 之前不知道 web 项目可能要跑 2 个服务器：
- **前端服务器**（8787）— 发 HTML / CSS / JS 等静态文件给浏览器
- **后端 API 服务器**（8000）— 处理数据库读写 + 业务逻辑

前后端分离时浏览器先从 8787 拿到 HTML（包含 React JSX 内联代码），HTML 里的 JS 再去 8000 调 API 拿数据 / 提交数据。

修法 2 步：
1. `index.html:10039` 改 `window.API_BASE = "http://localhost:8000/api/v1"`（绝对 URL）
2. backend `config.py:56` CORS（跨域许可名单）默认加 `http://localhost:8787`

## 18:30 [技术判断 / 模式6] CC 主动选择「teacher_id (UUID) 登录」而不暴露 login_id 给爬虫

### 背景 / 触发

CC 设计 `GET /teachers/public` 字段时考虑：登录页要列老师卡片 + 点选后输密码登录 — 必须有某个 ID 给前端拿来调 `POST /sessions/teacher`。

第一感觉是 `TeacherPublicOut` 加 `login_id` 字段。但 CC 自查发现：

### 经过

**安全风险分析**：
- 暴露 `login_id` 列表给无认证爬虫 = 攻击者可以拿到所有有效 login_id → 针对性爆破密码（虽然 backend 有 30 分钟锁，但爆破成本降低）
- 同样数据是 `id` (UUID) 时 — 攻击者拿到 UUID 也没用（UUID 不构成攻击向量 + 没法暴力穷举 16^32 空间）

**改造方案**：
1. backend `schemas.py TeacherLoginIn` 把 `login_id` 改 optional + 加 `teacher_id: Optional[UUID]` — 两者至少一个
2. backend `auth.py login_teacher` 改成「优先 teacher_id 查 / fallback login_id」
3. `TeacherPublicOut` 不返 `login_id`（只返 id UUID + name + assigned_dorm + last_login_at）
4. frontend `client.js teacherLogin` 改签名接受 `{teacher_id, password}` body

### 关键判断 / 学到的东西

**取舍三角**：
- 方案 A：暴露 `login_id` 给登录页 — 简单，但泄漏「所有有效 login_id 清单」给爬虫
- 方案 B（采纳）：扩展 backend 接受 `teacher_id` (UUID) 登录 + public 只返 UUID — 多 1 个 backend 接口字段，但 UUID 不构成攻击向量
- 方案 C：让 `/teachers/public` 返一次性短期 token 给登录用 — 太复杂

**为什么选 B**：安全性比简单性优先。UUID 是 128 位（暴力穷举不现实）+ 不暴露 login_id 给爬虫 = 双重保护。

### itsuki 原话 ⭐ 必填

itsuki 没明确拍板这一点（CC 自主判断），但后期 codex 审查肯定了这个选择（codex 报告 ✅ 项: "旧 `login_id + password` 兼容路径保留完整，UUID 登录是新增路径，没有破坏"）。

### AC 价值 ⭐ 必填

- **对应核心问题**：#2（技術判断 — 为什么选 A 不选 B）
- **展示了什么**：**模式 6 取舍三角顶级** — CC 在 itsuki 没明示要求下主动做安全 vs 简单性取舍。itsuki 通过 codex 审查二次验证 = AC 评委关心的「工程方法论 — 多 AI 交叉验证」
- 可能用在自我推荐书的哪个部分：「我怎么和 AI 协作做工程决策」段 — 不是 AI 一句话就听，而是 AI propose + 主动安全审视 + 二次外部验证
