## 15:00 [决策] iPhone 路径方案定型：BTR + Universal Link + AASA

### 背景 / 触发

今天是 2026-04-20 下午会话开工，按昨天 WIP.md 留的 5 议题（A/B/C/D/E）顺序推进，第一个是**议题 A — iPhone tap 贴纸技术细节**。itsuki 的开场指令是"没有新的事，开始"。

议题 A 的起点是 itsuki 昨天原话：「**如果能直接碰一碰，不打开 APP 也可以唤醒的话，那就这么干**」—— 她要的是"iPhone 碰一下贴纸就自动完成签到，不用手动打开 App"的体验。但 spec §5.1.2 只写了"iPhone Core NFC 读到 device_id"，没明确是前台读还是后台读。这一层技术细节需要今天落地。

### 问题发现 → 问题解决的过程

CC 先讲了 iPhone 读 NFC 的两种模式：

**模式 1：Foreground reading（前台读）**
- 学生要先打开 App → 按按钮 → iOS 弹"贴近标签"黑框 → tap
- 技术：Core NFC 框架 `NFCNDEFReaderSession`
- 学生步骤：**7 步**（亮屏 → 解锁 → 找 App → 打开 → 进页面 → 按按钮 → tap）

**模式 2：Background Tag Reading（BTR，后台读）**
- 学生不用打开 App，直接 tap 贴纸 → iOS 自动启动 DMSD App → 自动签到
- 技术：iOS 11+ 系统 BTR + Universal Link（通用链接）
- 学生步骤：**2 步**（拿出手机 → tap）

itsuki 明确选**模式 2**：「模式二更好」。

CC 接着讲 BTR 需要的 3 个关键组件：

1. **NDEF 格式贴纸**：NTAG215 空白贴纸 + 用 NFC Tools 写入 URL（贴纸 = 卡的贴片形态，物理同一种芯片）
2. **Universal Link**：贴纸里写 `https://dmsd.otogi2025.com/checkin?device=DEV001` 这种 URL，配合 iOS AASA 文件（Apple App Site Association）+ App 的 Associated Domains 配置，iOS 能直接启动 DMSD App 对应页面，不经过 Safari
3. **后端要有 HTTPS 域名**：AASA 文件必须托管在 HTTPS 上，对应 Universal Link 的域名

CC 给了 3 个域名方案：
- **A（注册正式域名）**：一年几百日元，简单可靠
- **B（GitHub Pages 免费）**：绑死 `.github.io`，不美观
- **C（Let's Encrypt 自建子域）**：复杂

itsuki 选 **A（注册正式域名）**。

### 心路历程 / 推测

[推测] itsuki 选 BTR + 正式域名，背后的决策逻辑：
- **体验优先**：她从第一天讲点呼机时就反复强调"拥堵时间短（1-2 分钟 120 人）+ 动作越简单越好"。BTR 的 2 步 vs 前台读的 7 步，差 5 步 × 120 人 = 600 步/场 × 每天 2 场 = 1200 步/天的体验差 → **必须是 BTR**
- **愿意付域名年费**：她其他地方很精打细算（卡 ¥3-5 / 贴纸要求"能回收复用"），但对"正式域名几百日元/年"没犹豫 → [推测] 她判断"这是让整个系统看起来真实、可部署的必要基础设施"，不算 overhead
- **拒绝 GitHub Pages 免费方案**：[推测] 可能她本能觉得 `otogi2025.github.io` 作为宿舍系统的域名"不正式"，不符合她对 v1.0 上线的完整性预期

### 遗留问题（待议题 B / 议题 C 解决）

1. iOS 26 BTR 有兼容性 bug 报告（WebSearch 查到 Apple Developer Forum thread/800624）—— 实施时要跟踪苹果修复
2. iPhone 老机型（7/8/X）的 BTR 只能锁屏触发，主屏不响应 —— 需要学生培训
3. 低电量模式会禁用 BTR —— 需要 App 主屏放"手动 tap"兜底按钮（fallback UI 已接受）

### AC 视角

- **#3 问题解决**：在"前台读 vs BTR"之间选择，不是拍脑袋，而是把学生体验步数（2 vs 7）量化成日用量（1200 步/天）来论证
- **#3 问题解决**：域名方案 A/B/C 三选一，选最正式的 A，展示"不为省小钱拖累整个系统"的判断

**itsuki 原话**：
> "模式二更好"
> "选项 α：注册一个正式域名（例如 dmsd.otogi2025.com 或其他，一年几百日元）"（itsuki 指定此项）

**#AC候选**
**核心问题**: #3（问题解决）

## 15:30 [问题发现] URL 复制漏洞 — itsuki 推翻 BTR 方案的"到场证明"有效性

### 背景 / 触发

CC 刚讲完 BTR 方案的完整技术栈（NDEF + Universal Link + AASA + 正式域名），还列了 7 项触发条件 + 5 类失败场景 + 对 spec §5.1.2 的影响 + 3 个待决策点（BTR/域名/fallback），准备让 itsuki 拍板"接受这个方案"。

CC 讲解过程中，潜在假设是："贴纸 URL 是静态的（写一次不改），学生 tap 贴纸 → 后端检查签名 + nonce（spec §5.1.2 已有的防御）→ 通过就签到。" CC 觉得 spec 的签名 + nonce 机制已经够防代签了。

然后 itsuki 抛出了这句话。

### 问题发现（itsuki 的观察）

**itsuki 原话**：
> "这样的话学生把这个 URL 复制了，那不就可以到哪都可以自己碰一下吗？"

**这是一个严重漏洞**，CC 讲 BTR 时完全没提，是 gap。

漏洞的具体机理（CC 讲解 + 补全）：

**攻击场景 α（学生 A 人在房间不在点呼机前，想给自己签到）**：
1. A 用 NFC Tools App 读一次真贴纸 → 拿到 URL 文本（`https://dmsd.../checkin?device=DEV001`）
2. 回房间，把同样 URL 写到一张自己的空白 NTAG215 贴纸上（和真贴纸物理同一种芯片，A 自己也能写）
3. 假贴纸放桌上，人在床上 tap → BTR 唤 DMSD App → App 走 §5.1.2 流程（取 nonce / 签名 / POST）→ 后端返回成功
4. **代签完成**。A 没离开房间。

### 关键发现：spec §5.1.2 的签名 + nonce **防不住这个攻击**

CC 原本以为 spec 的防御链够用：
- 签名用 A 的私钥（注册绑死）
- nonce 一次性 + 服务器下发

但这两层防御的前提都是"学生本人用本人设备发请求"，**不是"学生本人在点呼机物理位置"**。URL 一旦泄漏：
- A 在房间 tap 假贴纸 → A 自己的 iPhone 被 BTR 唤起 → A 的 App 用 A 的私钥签名（合法）→ 向服务器请求 nonce（合法）→ POST（合法）
- **后端唯一能看到的是 `device_id=DEV001`，但 device_id 是公开的（贴纸里可读）**
- 后端没法区分"A 真的在点呼机前" vs "A 在房间 tap 自己复制的假贴纸"

**根因**：URL 是静态的 + 可被任意复制到另一张 NFC 贴纸 / QR 码 / 二维码 / 浏览器书签 → "知道 URL" 不等于"到点呼机前"。

### 问题解决：4 方案对比（CC 提出 → itsuki 选）

CC 列了 4 个缓解方案：

**A — WiFi BSSID 验证**（最便宜）
- 后端校验 App 上报的 WiFi BSSID 必须在宿舍 WiFi 白名单
- ✅ 防校外代签
- ❌ 防不住"宿舍房间内假贴纸"（同一个 BSSID）

**B — 动态 NFC 贴纸 ST25DV**（最安全）
- 贴纸里的 nonce 每 5-10 秒由点呼机通过 I²C 刷新
- 学生复制 URL → 10 秒后作废
- ✅ 真正做到"必须到场"
- ❌ 硬件成本 + 软件复杂度上升；违反"被动标签"原则

**C — 异常检测 + 老师人防兜底**（最省事）
- 不加技术防御，靠老师目视 + 服务器异常检测
- ❌ 依赖人，不是硬防御

**D — QR 码动态扫描**（重来）
- 点呼机屏幕显示动态 QR，学生扫码
- ❌ 失去 BTR 的核心优势（碰一下 vs 扫码多步）

CC 的推荐是 **A + C 组合**（理由：便宜 + 务实 + 学生作弊几率低 + 老师兜底）。但 itsuki 没采纳。

（itsuki 的选择推翻见 16:00 条 [重大架构决策]）

### 心路历程 / 推测

[推测] itsuki 发现这个漏洞的认知路径：

- **她在听 CC 讲 BTR 体验时没打断**，可能当时她想象的是真实使用场景（学生 tap → 手机自动唤起）
- **CC 讲到"贴纸里写 URL"**，她大脑可能出现了一个匹配："URL 是字符串 → 字符串能被复制 → 那学生复制下来到处用不就废了？"
- 这一步的思维跳跃需要两个前置能力：
  1. 对"URL = 可复制文本"的数据属性直觉
  2. 对"静态凭证 vs 动态挑战"的安全概念直觉（虽然她可能没学过这术语）
- [推测] 她可能**没学过安全设计**，但对"物理防御 vs 软件防御"的边界有直觉：**如果一个东西可以被复制，那它就不能当身份证明**

这不是 CC 讲完她顺着推，是她从**第一性原理**推的。CC 讲 BTR 时没提这层，她自己挖出来了。

- **#2 問題意識** — 这是**本会话最典型的"从方案介绍里主动找漏洞"的案例**。AC 考官想看的就是这种不接受表面答案的批判思维。这条和 4-15 "太贵 + 点呼机只搬运数据" 同一类：**从别人给的方案里挖漏洞，回到第一性原理**

**面试回答雏形**：

**itsuki 原话（关键句）**：

## 16:00 [重大架构决策] 方案 B 落地：动态 NFC 贴纸 ST25DV16K — itsuki 选贵但彻底

### 背景 / 触发

15:30 条 itsuki 发现 URL 复制漏洞后，CC 列了 4 方案（A BSSID / B 动态贴纸 / C 人防 / D QR 码），CC 推荐 A+C 组合（最便宜务实）。itsuki 的回复直接是：

（注：当时方案命名用了希腊字母 α/β/γ/δ，itsuki 同一条消息里还反馈了"方案名字不要给这种符号，就普通 ABC 就可以了" — 见 15:35 [feedback] 条）

然后她发了一张淘宝截图：**ST25DV16K I²C RFID 动态标签模块**，¥25/个，已售 200+，菜鸟直邮空运日本 8-13 天，品牌"极客创享"（中国大陆）。

她问：「**我图片发你的那个芯片可以用吗？在中国买很便宜**」

### 问题解决 — 芯片选型验证

CC 分析这张截图（ST25DV16K 的规格）：
- **ST25DV16K**：正是方案 B 需要的 ST25DV 系列，16K = 16Kbit EEPROM（2KB 可写入空间）
- **I²C + Qwiic/STEMMA 接口**：标准 4-pin 即插即用，树莓派通过转接线 ¥10 就能接
- **读取距离**：天线面积 2.5×3cm 目测，典型读取距离 2-5cm → **这正是 DMSD 想要的**（学生手机必须几乎贴上贴纸才能读 → 防远距离代签）
- **容量**：NDEF URL 约 80 字节，2KB 完全够用
- **价格**：¥25/个 × 4 台 = ¥100 人民币 ≈ ¥2000 日元
- **运费**：约 ¥40-60 人民币（4 个一起订摊薄）
- **合计 4 台点呼机的动态标签成本约 ¥3000 日元**（$20 美元）

**这比 CC 原先估的 ¥2000-4000 日元/台便宜 10 倍。方案 B 的"成本障碍"基本消失。**

### 决策

itsuki 直接拍板：
- **B-1**：订购 ST25DV16K × 4 + Qwiic 转杜邦线 × 4（总 ¥140 人民币）
- **B-2**：nonce 刷新周期 **10 秒**（CC 给 5/10/30 秒三档，她选 10 秒 = 平衡点）
- **接法选 1**：Qwiic 转杜邦线直插树莓派 GPIO（不选 ¥200 的扩展 HAT）
- **B-3**：dump 本议题到今天的 raw（即本条）

### 心路历程 / 推测

[推测] itsuki 跳过 CC 推荐的 A+C 组合、直接选最贵彻底方案的决策逻辑：

- **"必须到场"是她的硬设计意图** — 她不接受"技术上能防死 90%，剩 10% 靠老师兜底"。她要 100%。[推测] 这个偏好和她昨天 "v1.0 一次全上" 决策是同一模式：**不接受分阶段凑合，要一次做到位**
- **价格敏感度在"省 100 日元"层次，不在"省 3000 日元"层次** — 她对域名年费没犹豫（见 15:00 条）、对宿舍 WiFi 正式投资愿意（可推测）；但对 Pi 4B 4GB 的过度配置 ¥200 差价敏感（4-15 记录）。她的阈值大约是"¥200-500 能省则省，¥2000-3000 为正确方案值得花"
- **中国购买空运日本** — 展示成本敏感度 + 跨境供应链思维。¥25 人民币 vs 日本本地买（可能 ¥1500-3000 日元/个，10-20 倍价差）→ 她知道哪里便宜

CC 推 A+C 组合时的逻辑是"你一个人做时间紧，最简单能跑起来就行"。但 itsuki 的优先级不是"最简单"，是"**设计完整性**"。这是 AI 推理和主角决策的典型错位 —— AI 想优化"最短路径"，主角想守住"设计原则"。

### spec §5.1.2 的修订要求

原 spec：
> "路径 B 的 device 是**被动 NFC 标签**，仅供 iPhone 读取拿 device_id"

要改成：
> "路径 B 的 device 是**动态 NFC 标签（ST25DV16K）**，由树莓派通过 I²C 每 10 秒刷新 NDEF URL 内容（含时效 10 秒的一次性 nonce），防止 URL 复制作弊"

**架构含义**：路径 B 的 device 从"被动"升级为"半主动" — 树莓派依然不参与签到判定（判定仍在后端），但参与 nonce 刷新。**thin client 原则不变，只是"搬运工"的职责扩大到"维护贴纸动态内容"**。

## 15:35 [feedback] 方案命名只用 A/B/C/D，禁希腊字母 α β γ δ

### 问题解决 — 两层回答

**第一层：物理限制**

CC 讲 NFC 硬件的物理事实：
- **NFC 卡 / NFC 贴纸是被动芯片，不联网**
- 卡里只有 UID（7 字节序列号），贴纸里只有 NDEF 数据
- 它们自己不会连 WiFi、不会发 HTTP
- 它们只有在"读头的电磁场"里被激活才吐出内容

**结论**：**必须有一个"中间设备"** 来做"读 NFC + 发 HTTP + 收 WS + 播声 + 亮灯"这些事。这台中间设备叫什么名字（点呼机 / 搬运工 / Pi / ESP32）不重要，**它的存在是 NFC 物理限制决定的必需**。

类比：ATM 机 —— 银行（后端）说了算余额够不够，但 ATM 机必须存在来读你的卡 + 联网问 + 吐钱 + 打凭条。没有 ATM，你拿不到钱。

**关键概念：thin client ≠ no client**
- ✅ "所有**业务判断**在服务器" — 正确
- ❌ "所以不需要客户端设备" — 错，客户端要**搬运 + 交互**

**第二层：中间设备候选（RPi vs ESP32 vs Pico W）**

CC 列表：
| 候选 | 中国价 | 优缺点 |
|---|---|---|
| Pi 4B 2GB | ¥300 | **新手最友好**，Python 完整生态，GPIO 直插 |
| Pi Zero 2 W | ¥100-150 | GPIO 要焊接，挑战大 |
| Pi Pico W | ¥40 | MicroPython，库少，TTS 跑不动 |
| ESP32-S3 | ¥30-60 | 最便宜但最难，TTS 要外接硬件 |

CC 推荐 B-4-a（保留 4-15 Pi 决策）+ B-5 Pi 4B 2GB。理由：高三一人开发，2027-04 前时间紧，ESP32 的 C++/MicroPython 学习成本会吃掉大量时间 —— **便宜硬件 × 贵学习时间 ≠ 划算**。

- 学生从服务器下 .apk（像从 ATM 取钱）
- 印钞机放央行 ≠ 钱从央行分发

**概念 2：Native App vs Web App 根本区别**

| 项目 | Web App（网站）| Native App（DMSD）|
|---|---|---|
| 代码位置 | 服务器 | 打包成 .apk 装在手机本地 |
| 更新方式 | 改服务器 → 学生刷新就看到 | 打新 .apk → 学生下载 → 手机本地装 |
| 例子 | 淘宝网页 | 微信 / DMSD |

**DMSD 升级流程**：
1. Mac 改代码 + 用 keystore 打包 → 生成 `dmsd-v1.1.apk`
2. 上传 .apk 到服务器
3. 学生 DMSD App 查版本 → 发现 v1.1
4. 弹窗"升级" → 学生手机下载服务器上的 v1.1.apk
5. 手机本地装 v1.1（覆盖 v1.0，签名一致数据保留）
