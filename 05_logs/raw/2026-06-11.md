## 00:xx [自我管理][方法论] 三份索引文档对账校准（多为执行类，一处方法论判断）

### 背景
itsuki 一句「project overview / project guide / 我的环境.md 全都更新」。这三份是项目的「索引/总览类」文档（文件字典 / 新人导览 / 工具清单），不写实际功能，只记「项目里有什么」。这类文档的通病是跟真实状态慢慢漂移——加了文件删了文件，清单没人同步。

### 经过（大部分是执行类）
逐目录用 `git ls-files` 数真实文件数，跟文档写的对比，把漂移的数字 + 新增文件补上。总数从写的 1399 校准到 1450。属于「宁多勿少」里说的「看似没什么大事的日常工作」。

### 一处够得上方法论的判断
对账时撞到一个矛盾：项目自带的漂移检测脚本 `bin/check_overview_drift.sh` 对 `05_logs/` 的 committed 文件数，两次运行报 173、174 跳来跳去。查出根因是中文文件名的 NFC/NFD 归一化 quirk（macOS 和 git 对带中文的文件名编码处理不一致，历史 raw 里 5-25 记过同款问题）。

判断：不去追脚本那个不稳定的数，改用 `git ls-files` 的稳定标准口径（174），并在文档脚注里写清「脚本偶报 173 是已知 quirk，以 ls-files 为准」+「脚本把未提交的 .bak 备份 / itsuki 新加的 icon 也算进『实际』是噪音，本表只记 committed」。即：不让一个会抖动的工具读数污染真值表，而是固定一个可复现的口径 + 把工具的噪音来源标注清楚。

另外发现 `PROJECT_GUIDE.md` §5.1 把 `{ok,data}` 响应包络当事实写，但 6-10 全量审查已证实后端/iOS 两侧代码都没实现它——一份给外部 AI 当「项目老师」的文档里写了不存在的契约。改成标注「与代码不符」，跟心智模型对齐（不是我新发现，是把 6-10 的结论传导到这份漏掉的文档）。
