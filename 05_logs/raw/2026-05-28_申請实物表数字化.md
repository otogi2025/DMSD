## 起因

itsuki 给了一份 iCloud 里的 PDF（`证据截图/届け類.pdf`，10 页扫描件），说「这些才是申请类的完整版」，要求 CC 三步走：① 读懂总结 ② 加进设计规范 ③ 最后实装。并且要求**同时派 codex（OpenAI 命令行 AI）独立读 PDF 做总结**，CC 拿来对比验证。

### 阶段 2 — 派 codex 二审（3 次失败 → 修正 → 成功）

codex 不直接吃 PDF（只吃图片），CC 先把 PDF 转 10 张压缩 JPEG。然后 codex exec 调用**连续 3 次失败**，逐个修：
1. `-i 图片...` 贪婪参数把提示词也吞成图片 → 改提示词走标准输入
2. codex 要求受信任目录 → 加 `--skip-git-repo-check`
3. 用 `-s read-only` 只读沙箱（只读图不写文件）

第 3 次成功，codex（gpt-5.5）独立读 10 图出结构化总结。

**对比结果：CC 与 codex 高度一致** — 9 种表单 / 样式编号 / 审批盖章顺序 / 日本人 vs 留学生差异 全部对上。双读交叉验证提高了抽取准确性。

## 阶段 6 — codex 实装后端 + CC 审查（2026-05-28 续，同会话延续）

itsuki 拍板「申请表改动全都落实做好 → 派 codex gpt-5.5 xhigh 去做、提示词写详细点、codex 负责干活我负责规划、改完我审查」。明确要求「不要出现 codex 了解信息不够全面改错的情况」。

### CC 规划 → codex 实装

CC 先把范围收在**后端**（数据库 + 接口 + 数据校验 = 其他端的地基），理由：iPhone 申请界面要调后端接口才能存数据；5 端一次塞给 codex 容易出错，正踩 itsuki「改错」担忧。CC 读全今天写进规范的内容（§7.2 / §7.3.5 / §7.21 / §8）+ 后端现状（models / schemas / 审批链 / 路由 / 迁移），写了 6 大节自包含提示词（每个字段类型 + 审批链 4 处修正的具体代码 + 硬约束 8 条 + 完成报告要求），派 codex（gpt-5.5、思考等级 xhigh — 先用一字测试确认 banner 真打 `reasoning effort: xhigh`）后台 workspace-write 跑。

codex 报告：70 测试通过 + 迁移正反验证通过。

### CC 审查 — 不盲信，逐个 diff + 独立复验

3 个关键发现：

1. **codex 越界改了 8 个范围外文件** → 但**诊断出不是乱改**：测试套件在 codex 跑之前就坏了（测试引用了根本不存在的类 `StudyAttendanceRoster`，说明别会话重构模型没同步测试），加上项目 `pyproject.toml` 设了「弃用警告 = 直接报错」严格策略。codex 为满足 CC「所有测试必须通过」硬要求，连带修了历史遗留坏测试 + starlette 422 弃用常量 + on_event→lifespan + SQLite 时区 bug + 旧迁移 batch 模式。每处都必要。
2. **codex 自报「干净库迁移验证通过」在默认配置下复现不了** → CC 第一次跑迁移失败（撞 `audit_logs already exists`），查清根因：`alembic.ini` 默认连真实开发库（被 `create_all` 建过表 + 版本标记空），不是真空库。CC 用临时配置指向真正空库重跑 → 10 个迁移全链路 upgrade/downgrade 通过、5 张新表建出 → 才确认 codex 迁移本身正确。
3. **CC 独立重跑测试** → 自己确认 70 passed，不只信 codex 自报。
