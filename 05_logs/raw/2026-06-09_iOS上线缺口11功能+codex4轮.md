## §2 [分歧][技术判断] codex 4 轮对抗复审 + CC 不盲信 ⭐⭐ 模式 2 最高级（教授最爱「假设崩了不放弃」）

### 经过 — codex 逐层挖 NFC 取消竞态
11 功能实装完，CC 派 codex（自报 gpt-5 + 思考等级 high）只读复审本会话 13 个文件改动，跑了 4 轮：

- **三轮**：挖到 M-1 最深层（NFC 会话还没存进实例变量的几行同步代码内的取消空窗）
- **四轮**：核实 CC 自己引入的「锁内启动 NFC 会不会死锁」+ 报 0 阻塞 0 重大收敛

### 关键判断 — CC 不盲信 codex 的三处
1. **二轮指出一轮的 B-2 被 codex 高估**：codex 说「continuation 双重 resume 崩溃」，CC 核实自己的代码用「取一次就置空 + optional chaining」、单线程串行下根本不会双重唤醒，只是跨线程没锁 → 采纳「加锁强化」而非承认「会崩溃」。

3. **四轮自己提风险让 codex 核实**：begin() 挪锁内是 CC 自己改的，可能跟 didInvalidate 死锁。CC 主动在 prompt 里点出来让 codex 查（codex 查了 CoreNFC 头文件确认不死锁），不是等 codex 发现。

## §3 [学习][认知改变] Swift 6 并发模型实战踩坑

### 经过
① 的 NFC 写入层 ST25DVWriter 在 Swift 6 严格并发检查下连环踩坑：
1. async Task 闭包捕获非 Sendable 的 CoreNFC 对象 → 报 'sending' parameter data race → 改用 completion handler 版（非 async 回调）绕开
2. completion 闭包还报「捕获 session/tag/self」warning → 加 `@preconcurrency import CoreNFC`（压模块的 Sendable 告警）+ class 标 `@unchecked Sendable`（自己保证线程安全）
3. continuation 跨线程访问无保护 → 加 NSLock 原子管理
4. Task.cancel 不取消 CoreNFC 系统界面 → 用 `withTaskCancellationHandler`，取消时 invalidate session

### 学到的东西
Swift 6 的「sending / Sendable / 协作式取消」不是语法糖，是真要理解「哪段代码在哪个线程跑、跨线程的可变状态谁来保护」。`@unchecked Sendable` 是「我（程序员）保证线程安全」的承诺，不是免检 —— codex 第二轮就质疑「这个标注当前不成立（没实际锁）」，逼 CC 真加锁。

- 对应核心问题：#3 問題解決 #5 自己認識
- 展示：通过 AI 协作（编译器报错 + codex 复审）学会一套陌生的并发模型，从「报错就绕」升级到「理解线程模型再加锁」
