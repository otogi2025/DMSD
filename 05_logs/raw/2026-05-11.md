## 16:00 [认知改变] [模式 5] itsuki 元认知拍板 — 英文「认得」≠ 日语「说出来」是两个学习目标

### 背景 / 触发

会话启动后 itsuki 主动表达学习焦虑：

> "我意识到我还有很多英语单词都看不懂，包括我项目里的各种文件，还有文件夹的命名我都看不懂。还有日语的单词，我到时候面试的时候，肯定是用日语面试。所以很多句子、单词我都要记住才行。你觉得我应该怎么办？"

itsuki 把 "英语看不懂" + "日语要说出来" 混在一段话里同时讲。CC 一开始解读为「双语都要会」，给了笼统建议（"分两层 / 英文上下文映射 + 日语项目讲法"）+ 建议建术语表。

### 经过

第 1 轮反问，itsuki 问「要不要单独背单词？」 → CC 答「别单独背，做项目语境化术语表」。

第 2 轮反问出现关键澄清。itsuki 担心「文件夹名字自己都不认识，介绍时会不会出丑」，CC 答「AC 是日语面试，不会出丑」。**然后 itsuki 一句话拍板了核心分层：**

> "所以我为什么要在这些文件夹里面加 00 加 01 加 02 这些数字？为什么要用编号？而且我说的背单词，**我又没说我要背读法，我就认得出来就好了。日语的话我必须要说出来。**"

CC 这时才意识到自己之前的方案校准错了 — 把英语和日语放在同一个学习强度上。

### 关键判断 / 学到的东西

itsuki 主动区分了两个目标：

| 语言 | 目标 | 学习难度 | 方法学 |
|---|---|---|---|
| **英语** | passive recognition（认得） | ★（低）| 轻量背 / 看到能反应意思即可 |
| **日语** | active production（说出来） | ★★★★（高）| 必须上下文 + 反复开口讲 |

这是 **passive recognition vs active production** 的认知科学经典分层。意义在于：
- 英语门槛远低于双语都要"会说" — itsuki 不需要练英语口语
- 日语必须开口练 + 在项目语境里讲 — 不是孤立背 N1 词
- ROI 优化：英语轻量扫 / 日语重度练，时间分配科学化

CC 当下校准方案，并在最终的 HTML 顶部「使用方法」框里写明这个原则。

### itsuki 原话 ⭐

> "我又没说我要背读法，我就认得出来就好了。日语的话我必须要说出来。"

### AC 价值 ⭐

- 对应核心问题：#5 自己認識（精准识别自己的能力边界 + 目标分层）
- 模式 5 经典 — itsuki 「以前我以为双语都要练 → 现在我意识到英语只要认得日语必须说」（虽然没显式说"以前"，但拍板瞬间的分层动作本身就是模式 5 的元认知）
- 展示了什么：**目标设定的精准度** — 不盲从「学外语就是要会说」的笼统标签，按面试场景反推「英语 = 看代码工具，日语 = 面试输出工具」差异化对待

## 17:00 [设计决策] [取舍] HTML vs MD — itsuki 主动评估文件格式 + 跨会话拍板「混层方案」

### 关键判断 / 学到的东西

itsuki 主动评估了两个文件格式的根本差异：

| 维度 | MD | HTML |
|---|---|---|
| 信息密度 | ★★★★（高）| ★★ |
| CC 工具链友好 | ★★★★（grep / parse / sync）| ★（结构不规则）|
| 人类视觉可读性 | ★★（纯文本难看）| ★★★★★（排版 / 色彩 / 交互）|
| 维护成本 | ★（git diff 干净）| ★★★（diff 噪音多）|

itsuki 的判断：
- **CC 协作主导文件**（CLAUDE.md / TODO / WIP / hooks 规则 / spec / design log）→ 保 MD，因为整套 sync 机制依赖 MD 可 parse
- **人是最终读者的文件**（AC 叙事 / 面试准备 / 教授会读的东西 / 给老师看的）→ 候选 HTML，视觉体验决定阅读愿望
- **不强制双写**：保持 MD 单源真值，要看 HTML 版让 CC 临时 pandoc 渲染到 /tmp/，永不入 git

5-11 术语表.html 作为试水 → 验证：
- itsuki 看着舒服度 ✅（杂志风 / serif 标题 / 暖色 / ruby 注音 / 学习交互）
- 维护成本可控 ✅（数据是 JS array，扩展只加 entry）
- CC 工具链不依赖（这个文件不会被 hook grep / sync 规则关心）

### itsuki 原话 ⭐

> "用 HTML，不要用 MD。MD 对我来说虽然信息密度更高，但是比较容易，比较难得去理解。很难看。"

### AC 价值 ⭐

- 对应核心问题：#2 技術判断（文件格式取舍）+ #5 自己認識（识别自己的阅读模式）
- 模式 6 取舍三角：信息密度 vs 视觉可读性 vs 维护成本
- 展示了什么：**外部输入（Anthropic 文章）→ 跨会话讨论 → 项目内拍板分层 → 立刻落地试水**的完整链路。不是盲从单一格式，按"谁是最终读者"分层处理

**第四段（21:30）itsuki 反问 — 触发 CC 认知重新校准。**

CC 之前一通行话直接抛过去。itsuki 是日本高中生编程零基础，看到 `As() error() K() i()` 这种压缩后的 JavaScript 函数名第一反应**完全自然**：「我项目的核心真的是这些怪名字函数吗？」

这正是**工具用户在"工具报告" vs "工具背景知识"之间的认知断层**。工具报告假设你懂行话，但 itsuki 不懂。CC 反思 — 给的解释不是 itsuki 能读懂的层级。

CC 重新拆解（按零基础讲）：

1. graphify 用 tree-sitter 给 29 种语言做本地 AST 抽取
2. AST 抽取**不分**"项目自写代码" vs "塞进来的第三方库代码"
3. iOS demo + teacher_web demo 里**塞了** React + Babel 整套压缩库（vendor 进来的，约 1.2MB JS / 每文件几千行混淆代码）
4. React/Babel 库源码为了下载快做了 **minify（压缩）**：把 `setState() renderComponent()` 这种长函数名换成 `a / b / c / aa / ab / ac` 最短字母 — 这就是为什么 god nodes 都长那样
5. 这些压缩库进了图谱 → React 内部几千个互调函数 → 抢走 god nodes 前 35 名 + 377 个 community 里前 36 个全是 vendor

「vendor」在程序员行话里专指"第三方库代码"。「vendor 污染」 = 第三方代码喧宾夺主把真正项目核心节点挤后面。

**修法**：写 `.graphifyignore`（语法跟 `.gitignore` 完全一样）排除 `**/vendor/` / `**/phaseB_src/` / `**/*.min.js` / `**/babel.min.js` / `**/react-dom.development.js` 等模式。下次 `/graphify --update` 重抽就干净。

### 关键判断 / 学到的东西

**模式 2（假设崩 → 真因）**：

第 1 层假设：图谱出来 god nodes 应该是 DMSD 业务核心类（`Student` / `RollCallEvent` / `models.py` 之类）。
真相 1：god nodes 全是 React/Babel 压缩函数 `As() error() K() i()`。

第 2 层假设：所以 DMSD 没有清晰核心 / graphify 是个噪声工具不能用？
真相 2：graphify 没问题，是**输入有 vendor 库污染**。AST 工具的 fundamental limitation 是不分项目代码 vs 第三方库 — 跟人类编程的"代码组织"边界问题是同一回事。

**模式 5（认知改变）**：

itsuki 学到知识图谱（knowledge graph）这类静态分析工具的**通用工程纪律**：跑这种工具前必须有 ignore 文件（类比 `.gitignore`）排除 vendor / build 产物 / 资源文件。**这跟做软件工程的"代码组织"是一样的事** — 项目代码和第三方代码要边界清晰，不只是为了人读，也是为了机器分析。

之前 itsuki 用 `.gitignore` 把它当"不让没用的文件进 git"的局部工具。现在意识到这是个**更普遍的工程概念**：所有"扫整个项目"的工具（git / lint / 知识图谱 / 安全扫描 / 代码搜索）都需要"边界配置文件" — 因为机器没法自己分清哪些是项目自己的、哪些是借来的。

每装一个新工具，**先想这个工具的"ignore 配置"在哪**。这是迁移性极强的工程纪律。

**模式 6（取舍）**：

archive 漂移修不修？三选项：
- **A. 全修**：archive 自包含 — 把所有被引用的活组件也 copy 到 archive。工程量大 + archive 跟活代码冗余 + 改 archive 等于改历史
- **B. 部分修**：在 archive README 加一句"本目录引用现役 components 可能已变更"。低成本但够透明
- **C. 不管**：compose-drafts 已退役 / 不真编译 / 修了反而干扰历史快照。0 成本但出愿叙事可能有破绽

itsuki 选 **C**，理由清晰：archive 死了 / 不影响 build / 修了反而是过度工程。这种"知道存在但故意不修"是成熟工程师的取舍模式 — 跟"什么都修干净"的强迫症路线区分开。**关键是显式记下来 "我知道这个存在但选不修"**，而不是不知道存在。所以这次发现的真正价值是**让漂移从隐性变成显性**。

**工程发现层（vendor 污染 + .beads 副作用）**：

`graphify hook install` 这种第三方工具的安装命令**会动 git config** — 这是个**跨工具污染风险**。如果不是 CC 当场抓到（命令输出路径异常 → 立刻 `git config --get core.hooksPath` 验证），DMSD 的 pre-commit hook 静默失效几天后才发现，版本号 / 联动检查全停摆 → 进 git 的版本一致性漂移就开始了。

修复后沉淀下来的工程纪律：
- 任何第三方工具 install 命令跑完后**立刻 `git config --get core.hooksPath` 验证**
- 第三方 hook 也要 copy 进 DMSD 主 hook 目录，统一 `hooksPath = 00_admin/hooks/`
- 这条已加进 `00_admin/hooks/README.md ⚠️ graphify hook install 漂移注意` 段

**元层：CC 翻译层失职 → 反问触发校准**：

这条不是新模式，是**之前 feedback `feedback_explain_terms_to_itsuki.md`（"跟 itsuki 沟通必须用大白话 — 内部代号 / 日语 / 英文缩写第一次出现就翻译"）的又一次破窗 + 当场修复**。CC 在"急着出报告"时容易丢这条 — 应当在第一次写报告时就翻译一遍 vendor / minify / AST / community 这种词，而不是等用户问。
