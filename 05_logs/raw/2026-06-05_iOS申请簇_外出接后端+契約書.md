## A1 外出申请接 outings 后端（真正的大头）

### 受约束的设计

外出在后端是**独立 outings 表**（不是出寮届 applications），6 接口齐全（POST 提出 / GET mine / GET detail / PATCH confirm / PATCH withdraw / GET pending-for-me）。但 iOS 侧三个硬约束逼出实现方式：

1. **不能加路由**：`Route.swift` 不在白名单 → 外出做不了独立页面，只能复用现有 `.apply` / `.applyDetail`
2. **演示版外出本来就显示在 ApplyListView + 详情 2 步进度里**（SEED.applications 含外出假数据）→ 让生产真数据走同样位置是「对齐演示版」，不是擅自发明架构
3. **外出表单缺后端必填的 `outing_date`**：旧 GenericApplyForm 的 outing 分支日期/时刻字段全被 `!isOuting` 排除 → 补上才能提交

### 5 处改动

- **新建 `OutingsAPI.swift`**：OutingOut/OutingCreateBody 模型 + 4 方法。撤回用 PATCH，但 APIClient 没有 PATCH 便利方法、APIClient.swift 又不可改 → 直接调底层 `request(method:"PATCH",...)`。
- **GenericApplyForm**：外出补外出日(必填)+外出时刻+回寮时刻字段；提交按钮对 outing 分流到 `submitOuting()` 直接 POST（跳过演示用确认页），其他类型不变。
- **ApplyListView.load**：合并拉 `OutingsAPI.listMine()`（外出失败容错、不拖垮出寮届列表），外出 id 加 `outing:` 前缀编码类型。
- **ApplyDetailView**：按 `outing:` 前缀分流到新建 `OutingDetailView`；演示版外出（无前缀）仍走 SEED otherDetailBody，两者隔离。
- **新建 OutingDetailView**：三态映射 2 步进度（pending=先生確認待ち / approved=確認済+确认老师名 / withdrawn=取消），pending 时可撤回，复用同文件的 WorkflowStepsView。

### 真测逮到编译过但运行时会崩的 bug

curl 端到端真测（登录→POST→mine→detail→withdraw 全通，返回 15 字段完全匹配 OutingOut），但发现 `submitted_at = "2026-06-05T13:55:04"` **没有时区后缀**——dev 用 SQLite，`DateTime(timezone=True)` 读回是 naive、序列化成无时区。而 APIClient 的 `decodeISO8601Date` 用 `.withInternetDateTime`（要求带时区），无时区字符串会解析失败 → 整个 OutingOut 解码 fail → GET mine/detail 运行时报错。

这正是归档 handoff §4.2bis 记的「待真后端有日期数据时验证」的隐患，现在验证确实会 fail。`APIClient.swift` 不可改 → 把 OutingOut 的 datetime 字段（submitted_at/withdrawn_at/confirmed_at）也声明成 String（String 不走 decodeISO8601Date），彻底规避。

**AC 价值（模式 2）**：编译绿 ≠ 运行对。光双 scheme BUILD SUCCEEDED 不够，端到端真测才逮到这个潜伏 bug。再次印证「独立验证、别只信编译」。
