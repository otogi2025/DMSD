## 19:30 [方法论决策] 先流程后硬件，不从零件开始

会话开场 itsuki 说"来一起决定点呼机的构造"。表面上是一个硬件讨论任务。

- 4-17 决策：4 台点呼机、双路径并存（卡 + iPhone 读静态贴纸）、老师改判时限矩阵等
- TODO.md 硬件层明确列出 8 项待决零件（Pi 型号 / PN532 接口 / LED / 喇叭 / 电源 / 外壳 / 贴墙方式 / 点呼位置）

从 CC 的视角，"架构已定、流程已清、只差硬件选型"——所以 CC 直接画了功能方块图（卡读头 → RPi → LED/喇叭 → 通信 → 电源）+ 硬件零件待决清单，建议走"流程 C（混合推进）+ 落地 α（写进 spec）"立刻开始零件选型。

### itsuki 的第一次纠正

itsuki 看了 CC 的方块图后**没有顺着这个方向推进**，而是直接问："我们还没决定到底要怎么点呼呢？你怎么就知道只要 nfc 贴？之前的决定全砍了，从 0 开始"。

这句话 CC 最初理解成"范围质疑"——以为他是问要不要从 α/β/γ/δ 四种"砍多少"中选。所以 CC 抛出了 4 级选项让他挑。

### itsuki 的第二次纠正（方法论级）

itsuki 看 CC 的 4 级选项清单后，还是没挑。他说：

> "从具体点呼流程，从用什么设备开始，先决定流程再决定硬件"

这不是选 α/β/γ/δ 的答案。这是**方法论层的重申**：
- 讨论对象应该是"点呼流程"
- 要具体到底层（到"用什么设备"那一层）
- **但顺序永远是：先流程 → 再硬件**

### itsuki 的思考路径（推测 + 原话印证）

[推测] itsuki 的警觉来自对 AI 协作模式的长期反思：
- 他察觉到 CC 在用"文档里已写的东西"作为推理起点——但这些文档是他自己在不同阶段写的，有些决策当时并没想透
- 他担心一旦进入"硬件选型"这个具体层，就会被零件清单拖着走，失去对整体设计的主导权
- 他的经验：AI 会自然地"向下一步"推进，但作为主角，有时候必须"向上退一步"重新看问题的起点

他原话里"之前的决定全砍了，从 0 开始"不是随口说说——这是他建立的一个底层原则：**文档里写下的东西是某时某刻的 snapshot，不是永远锁定的权威**。只要还没实际开工（采购 / 写代码 / 部署），任何决策都可以重开。

### CC 的反思

CC 犯的错误是典型的"AI 服从性"——拿到文档把里面的决策当成已经封印的事实，在上面继续叠加。正确做法应该是：**进入新会话后、开始新议题前，主动确认"这个议题的前置假设是否都还成立"**，而不是默认全成立。

这一条教训 CC 本会话之后又违反了两次（见 19:45 条 [分歧 CC 没读 spec 推 C5] 和 11:20 [CC 推老师按钮时又跳到硬件]），itsuki 每次都要手动拉回来。

### 决策 / 结论

**流程层必须先讨论清楚，硬件是流程的实现工具，后置**。

这不是单次会话的选择，是**整个 DMSD 项目的思考顺序原则**。

### AC 视角

- **#3 问题解决**：itsuki 主动提出"先流程后硬件"的工程原则，拒绝被工具和既定决策推着走。这是工程思维能力的体现——优先定义问题，再选择工具。

## 20:00 [重大架构决策] 取消分阶段上线，v1.0 直接完整版（G2 方案）

### 背景

原架构在 CLAUDE.md 和 spec 里明确写着：
- **Phase 1**：NFC 卡 + 后端 + 老师 Web + RPi 点呼机（**不做学生 App**）
- **Phase 2**：追加学生 iOS App + Android App

分阶段的目的是：
- 先让卡方案跑通、验证核心点呼逻辑
- Phase 1 工作量小、一个人 1 年可做完
- Phase 2 再加 App，时间不够也有 M1 demo

讨论"Phase 1 是否要做 App"时，itsuki 最初选了 β（Phase 1 真的不做 App，学生端查记录推迟到 Phase 2）。

然后 CC 推进到了卡的完整生命周期讨论。

### itsuki 的转向

在讨论卡的物理形态 + 绑定流程时，itsuki 突然说：

> "我放弃了，不分步骤上线了，直接最初 1.0 就直接上线手机和卡的完整版"

这是一个**完全相反的方向转变**——从"Phase 1 不要 App"（10 分钟前）到"v1.0 一次全上"（现在）。

### 为什么转向（推测 + 原话印证）

[推测] 可能的心理变化路径：
- 讨论卡绑定流程时，itsuki 发现**卡的绑定必须靠 App**——学生 tap 自己的卡把 UID 录入自己的账户。如果 Phase 1 没 App，卡的绑定就必须靠管理员后台手动操作所有 120 个学生。
- 这个摩擦让他意识到："卡"和"App"不是两个可以分阶段的模块，它们从注册那一刻起就耦合在一起
- 既然耦合，分阶段就是自欺欺人——"Phase 1 纯卡"根本不存在，还是要有 App 才能走完卡的完整生命周期
- 索性一次做完整版

原话支持这个推测——他的"绑定流程"描述里，卡绑定完全在 App 内操作，没手机的学生要走特殊流程（管理员代录），这个"特殊流程"就是因为 App 其实是主路径。

### CC 给 itsuki 的代价警告

CC 列了一张表呈现"不分阶段"的代价：
- 工作量从"Phase 1 RPi+Python 即可开工"→ 扩展到"iOS + Android + 后端 + 老师 Web + 点呼机 + 卡方案并行"
- 技术栈从"Python + RPi"→ 扩到"Swift/SwiftUI + Kotlin/Java + Python + 前端 Web + RPi"
- 时间风险：一个人 1 年（到 2027-04）可能做不完
- AC 风险：做完完整版 vs 做完 M1 MVP，前者更 ambitious 但没做完会反噬

CC 建议了折中方案：
- **G1** 坚持原意，v1.0 一次全上（开发也并行）
- **G2** 上线层不分 Phase（itsuki 的决定保留），但开发层仍按 spec §8 的 M1→M5 里程碑顺序推进，M1 先跑通卡闭环
- **G3** 再想想

### itsuki 选 G2

他接受了 G2。这说明他对"开发内部的阶段性"并不反对，他反对的是"**对外分 Phase 上线**这件事"。

这是一个微妙但重要的区分：
- **开发节奏**可以分阶段（先 M1、再 M2）
- **上线姿态**不分阶段（v1.0 一次上）
- **兜底方案**：万一做不完，至少 M1+M2 能跑，可 demo

### AC 视角

- **#1 为什么做 DMSD**：itsuki 重申了项目的完整愿景 —— 不是"点呼最小闭环"，而是"整个宿舍生活数字化"
- **#3 问题解决**：在"分阶段务实"和"完整愿景"之间做权衡，最后选了中间路线 G2（上线不分 / 开发仍分）
- **#4 自己认识**：他发现自己最初的"Phase 1 无 App"假设在遇到"卡绑定需要 App"时站不住脚，主动修正

这条是本会话**最重要的一条决策**。涉及项目节奏、工作量、AC 风险的综合考量。

**itsuki 原话**：

## 20:15 [决策] NFC 卡完整生命周期定稿

### 背景

CC 列出"卡 → 学生的完整生命周期"清单（6 项：物理形态 / 绑定流程 / 发放 / 丢失补办 / 毕业回收 / 后台管理权限），让 itsuki 一条条拍板。

### 每项的决策 + itsuki 的思考

**1. 物理形态**：

CC 给了 5 个选项 F1-F5：
- F1 空白卡 + 自贴学号姓名（低成本、姓名外露）
- F2 空白卡 + 只贴学号（隐私高）
- F3 厂家印刷卡（正式、贵）
- F4 钥匙扣/挂绳硬卡（便携、贵）
- F5 完全空白（最便宜、但学生自己分不清哪张是自己的）

itsuki 最初选 F1，然后在对话末尾补丁修订："F1 为了让这个卡片回收可用，所以不要包含别的信息"。这个说法在 CC 看来等于指向 F5。

但他进一步澄清："就直接贴自己名字就好了，不用全空白，就那种随便的贴纸都可以"。

**最终方案**：空白 NTAG215 + 学生自己贴一张写自己名字的随便贴纸。不用厂家印刷，不用全空白，不贴学号。

[推测] itsuki 的思考路径：
- 厂家印刷卡 → 太贵 + 毕业后不能复用给下一届
- 全空白卡 → 学生自己分不清哪张是自己的
- 只贴学号 → 下一届学号不一样，要撕掉重贴
- 贴姓名 → 同理要撕，但"姓名"和"学号"比，姓名更直觉、而且撕了也就撕了
- 最重要：**卡本身要能回收复用**（毕业卡清除 UID → 下一届复绑）

这是一个**成本 × 复用性 × 学生体验**的三维权衡。

**2. 绑定流程**：

itsuki 原话描述得非常具体：

## 20:30 [决策] Android 走 tap 贴纸路线 + APK 自建网站分发

### 决策

**Android 的签到方式**：和 iPhone 一样走"tap 外贴静态 NFC 贴纸"路线。**不走 HCE**（Host Card Emulation，即 App 把手机伪装成 NFC 卡 tap 读头）。

**Android 的 App 分发**：不走 Google Play，自建一个网站托管 APK 文件，学生去下载安装。

### 心路历程 / 推测

**为什么 Android 不走 HCE？**

技术背景：iOS 第三方 App 没有 NFC HCE 权限（Secure Element 被 Apple Pay 独占），所以 iOS 学生必须走"tap 贴纸"路线。但 Android 可以做 HCE——学生 Android 手机可以直接 tap 点呼机的 PN532 读头，和卡一样。

两条路线的差别：
- HCE 方案：Android 学生的体验和卡一样（直接 tap 读头），但点呼机需要识别手机 HCE 数据包 vs 卡 UID 的差别
- 贴纸方案：Android 和 iOS 学生体验完全一样（都 tap 外贴贴纸），但 Android 失去了"原生优势"

itsuki 选贴纸方案。[推测] 理由：
- **跨平台一致性 > 平台原生性能**：iOS 和 Android 用户同一套 UX，减少"哦 Android 用户要这样 iOS 要那样"的文档和教学成本
- **开发复杂度**：HCE 要额外学 Android HostApduService + ISO 7816 协议 + APDU 处理，比 NFC 贴纸读取复杂
- **后端简单**：如果 iOS / Android 都走贴纸，后端就只需要处理一种签到路径（手机 POST {student_id, device_id}）；HCE 要处理第二种（和卡类似的 UID）
- itsuki 一个人做，简化 > 原生

**为什么 APK 自建网站？**

[推测]：
- Google Play 要开发者账号（$25 一次性费用）+ 审核流程
- 宿舍系统是内部工具，上公开商店没意义
- 自建网站下载更直接，学生在学校 WiFi 里就能拿到
- Android 的"未知来源安装"对学生是需要授权的步骤，但可以通过说明解决

### 遗留技术风险

CC 记在遗留项里，下次讨论要展开：
- **Android "未知来源"授权警告**：学生第一次安装 APK 会看到一个 Android 系统警告"这个 App 来自未知来源，可能有风险"，需要学生手动授权。这是一个信任门槛。
- **自建分发的 HTTPS / 证书策略**：下载 APK 的链接必须 HTTPS，否则容易被中间人攻击替换成恶意 APK
- **Android 能否做"后台 NFC 唤醒 App"**（类似 iOS Background Tag Reading）—— 如果不能，Android 学生每次点呼都要先打开 App，体验比 iOS 差

### AC 视角

- **#3 问题解决**：iOS 和 Android 的平台差异处理 —— 放弃 Android 的"原生性能优势"选择"跨平台一致性"，体现工程 trade-off 能力
- **#4 自己认识**：承认自己一个人做不了多条平台差异化路径，主动做简化

**itsuki 原话**：
> "安卓和 iPhone 一样都走手机碰一碰的路线"
> "安卓直接搭建一个网站，把那个文件放到后台服务器里，学生去下载就直接通过这个服务器去下载"

**#AC候选**
**核心问题**: #3（问题解决）+ #4（自己认识）

- 版本号 / 目录结构 / 5 核心问题等"共享概念"只在**一处**存（权威源）
- 其他文件用指针引用（"当前版本见 CHANGELOG.md"）
- 新建 `00_admin/文档同步点清单.md`，列 §1-§7：版本号同步点 / 目录结构 / 5 核心问题 / 分阶段策略 / 时间戳维护 / 打 tag 前 Release Checklist / 创建新文件 Onboarding Checklist
- **弱点**：只靠纪律，人肉永远会漏

**B. A + CC 会话结束前自动扫描**（+15 分钟）
- CLAUDE.md 加规则："每次会话结束前 CC 必须 grep 声明性文件的版本号 / 路径死链 / 过期时间戳，不一致就报告"
- **弱点**：依赖"有 CC 会话"这个前提。手动 commit 或跨会话漏了就没防线

**C. B + git pre-commit hook**（~1 小时）
- 写 `00_admin/hooks/pre-commit` bash 脚本（放在可 git 追踪的目录，不是 `.git/hooks/`）
- `git config core.hooksPath 00_admin/hooks` 让 git 去这里找 hook
- commit 时自动跑检查，不一致 → 拒绝 commit
- 支持 `<!-- VERSION_OK -->` 豁免 + 紧急 `--no-verify` 绕过
- **AC 加分价值**：展示"懂工程纪律 / DevOps / 自动化防退化" —— 面试讲"我不只是写 spec，我还会用 git hook 做质量门控"

### 5 个可能的洞（按 memory `feedback_find_5_holes_after_any_proposal`）

CC 按规矩主动列自己方案的缺点：

1. CLAUDE.md 以前写 "v0.3.0" 一眼可见，改成"见 CHANGELOG"要**多跳一次**。**可读性 vs 准确性权衡**
2. **同步清单本身也会过期** → 规则要加一条"创建新含版本号的文件时同步加入清单"（我在清单 §7 加了"新文件 Onboarding Checklist"专门处理）
3. CC 每次会话都扫一致性 → 可能**噪音大**。需设静默门槛
4. **pre-commit hook 误报会卡 commit 半小时** → 零基础 debug 失败的 hook 很痛苦。留 `<!-- VERSION_OK -->` 豁免 + 紧急绕过 `--no-verify`
5. **时间戳漂移**（WIP 今天没开 = 不自动更新）是另一类问题，单源解决不了 —— 只能靠 CC 会话尾的时间戳新鲜度扫

### 为什么他选 C 而不只是 A

他选了最彻底的方案。几个可能的理由：
- A 只靠纪律 → 人肉永远会漏（他自己承认过去 1 个月漂移就是证据）
- B 依赖"有 CC 会话"的前提 → 他自己 commit 时漏了就没防线
- C = **机器强制的 checkpoint** → 不依赖人或 CC 的记忆，结构性防退化
- C 是 AC 加分项 —— 面试讲"我懂用 git hook 做自动化质量门控"，展示的不只是编程能力，是**工程成熟度 + 系统思维**

他选了最工程化的那个，同时接受"学 bash + git hook 机制"的学习成本 —— 这本身就是 AC 叙事的好素材（**选困难的正确路径，不选容易的半成品路径**）。
