## §1 リクエスト曲管理 — 男女寮分け + 提出順 + 承認/拒否

**Tag**: `#web #demo-sprint #UX-design`
**对应 AC 核心问题**: #3 怎么解决的

itsuki 反馈："音乐播放要按照提交顺序。并且分男寮女寮"。

### 拍板的设计

- **「寮」過滤チップ追加**：男寮 / 女寮 / 両方（件数付き）
- **デフォルト = 担当寮**：男寮老师打开就看男寮请求，不混
- **`#番号` 重计算**：寮 × 朝/晩 4 個組合各自独立编号 — 男寮夜の #1 #2 / 女寮夜の #1 #2 完全分离
- **承認 / 拒否 / 未対応 + 審査取消**：状态机，未対応默认显示，承認後カード枠変緑、拒否半透明
- **古い順 = 提出順 = 放送順**：これを明示するためタブ説明を「提出順に再生」に変更

### 为什么这个值得记

> 这是 itsuki 第一次提出"寮分け"作为权限/可见性边界（不仅是数据 filter）。  
> 后续推论：iOS 学生端只能给自己寮投稿、申請数据按寮自动隔離 — 寮 = 隔离单位 而不是单纯标签。

## §2 主页 ショートカット URL — 自動 IP 検出 + 手動 fallback

**Tag**: `#web #demo-prep`

### 演变三段
1. 第一版：detail 弹窗 + 6 步教程 → itsuki "压缩了主页其他东西" → 不要
2. 第二版：单行 IP 输入 + 学生 select + URL + コピー → itsuki "デフォルト写死 192.168.1.100 麻烦"
3. 第三版（最终）：`fetch('/api/server-info')` → 成功 = 绿色胶囊显示真实 IP（带绿点）/ 失败 = fallback 到手动输入（localStorage 记忆）

- 浏览器封了（mDNS 假地址 `xxx.local`）
- 用 `demo_server.py` 提供 `/api/server-info` 接口才是干净路径

### Demo 当天工作流
```
Mac terminal: python3 demo_server.py → 浏览器: http://localhost:8787/ →
ショートカット URL カード自動表示真实 LAN IP → コピー → iPhone 粘 → 摸卡 →
iPad 座位变绿 + Web Speech API 日语播报
```

## §4 crash bug 2 处 — hardcoded array index 不防御短 roster ⭐

**Tag**: `#bug #defensive-coding #AC候选`
**对应 AC 核心问题**: #2 + #4

### Bug 1：点呼開始按钮按了无反应

```js
// app.jsx startSession（修复前）
seeded[8].status = 'exempt';   // ← 男寮 4 名/女寮 3 名後、seeded[8] = undefined → throw
```

React 整树 unmount → 按钮像没反应一样（实际是组件挂了）。

### Bug 2：通知中心打开就白屏

```js
// pages-records-search-etc.jsx NotificationsPage（修复前）
const sample2 = roster[3][2];  // ← 女寮长度 3、roster[3] = undefined → throw
```

### 修复

```js
// app.jsx
const exemptIdx = Math.min(seeded.length - 1, 3);
if (seeded[exemptIdx] && exemptIdx !== 0 && exemptIdx !== 2) { ... }

// pages-records-search-etc.jsx
const pick = (i) => (roster[i % roster.length] || roster[0])[2];
```

### 留下的 lesson

> demo 数据写多了就忘了**它会被改尺寸** — 12 人变 4 人时，所有"假设 12 个槽都在"的代码都炸了。<br>
> 防御：**任何 hardcoded index 都要 % length 或 if (arr[i])**，不要相信 seed 的数量永远不变。<br>
> 这种 bug 静默：tab 不进去就发现不了 → demo 现场点错地方就崩 → 不可接受。

## §6 行事カレンダー — 升级到 iOS 同型月グリッド ⭐

**Tag**: `#web #UX-parity #AC候选`
**对应 AC 核心问题**: #4 学到了什么 + 跨会话协调

### 触发
itsuki 同时贴 web 截图（3 行简陋列表）+ iOS 截图（漂亮月历 + 选择日列表）→ "手机的做成这样，你 web 也要跟上来"。

### 实施
新组件 `EventCalendar`（pages-records-search-etc.jsx）：
- 左：月グリッド（< 月 >）+ 7×N 单元格 + 周末色（日红 / 土蓝）+ 今日浅蓝底 / 选中 cobalt 实色 / 有事件白圆点
- 右：选中日「4 月 23 日（木）」+ 件数 chip + 「＋ 追加」按钮 + 事件列表（左 70px 时刻 mono cobalt + 标题 + 📍場所）
- 「＋ 追加」modal：日付 / 時刻（任意 = 終日）/ タイトル / 場所 — 复用 `ModalShell` `ModalField` `ModalFooter`

### Bug 修复（同会话内）
第一版的 modal 点击就白屏。原因：复用的 ModalShell / Field / Footer 都需要 `T={T}` prop（它们内部访问 `T.surface`），我没传 → undefined.surface throw → 整树 unmount。

### 反思

> **多个 Babel script 标签 = 多个独立作用域** — `window.X` 全局共享是这个项目唯一的跨文件机制，但 props 不会自动注入。<br>
> 复用别人写的组件时，**先看它的 props signature** 而不是凭直觉传参。

### AC 角度

> 这是我第一次主动把"另一个会话产出"作为参照标准让 web 来追赶 — 不是 itsuki 写需求文档，是 itsuki 截两张图说"对齐" → 我自己读出"iOS 月历更适合"这个判断。<br>
> Cross-session UX consistency 是单人开发不存在的问题；多 agent / 多平台时一定会出现。

## §7 個人番号 6 桁化跟 iOS 对齐 ⭐

**Tag**: `#data-model #AC候选`
**对应 AC 核心问题**: #1 为什么做 + #5 志望理由

### 触发
itsuki: "个人番号这里你跟 ios 对一下设定，我高三 B 班 18 号，我的番号就是 060218，其他几个人都是高三，番号随便给"

### iOS spec（4-23 itsuki 本人定）
6 桁 = 学年(2) + 組(2) + 番号(2)
- 学年: 中1=01〜高3=06（中高一貫 6 年制）
- 組: A=01 / B=02（无 C）
- 番号: 01-99（升年级用最后位+1）

リュウ イヒ = 高3 B 18 号 = **060218**（itsuki demo seed = 自己）

### Web 侧实施
```js
// theme.jsx
window.DEMO_SEED_NO = '060218';  // ⭐ 单源
window.ACCOUNTS = [
  { no: '060218', sid: 'S001', name: 'リュウ イヒ', ... },
  { no: '060103', sid: 'S103', name: '田中 隼人', ... },
  // ...
];

// accounts.jsx
const DEMO_NO = window.DEMO_SEED_NO;
// 判定改为 sid-based（番号变化也不破）
if (a.sid === 'S001') { ... }  // リュウ専用 activity log
```

### 連動修正
- 学生アカウント管理 表番号列：70px → 130px（容纳 6 位）
- 「次の新規番号 07」stat → 「番号フォーマット 06????」（iOS 本人入力，不预测连号）
- 「＋ 新規追加」按钮：alert 文案更新到 6 桁 spec
- ショートカット URL select 默认值：`'00'` → `window.DEMO_SEED_NO`
- activity log 分支 key：`a.no === '00'` → `a.sid === 'S001'`（番号变化也不破）

### AC 角度

> "我自己定义自己的番号格式" — 这件事本身是**学生定义系统**而不是**系统定义学生**的反转。<br>
> 学校给的学籍番号是 4 位连号；我重新设计成"语义化 6 位"（学年/组/号一目了然） — 因为我们这个系统是学生用的，老师查询逻辑也要"高 3 B 班的学生"而不是"S001-S199 这堆数字"。<br>
> 数据模型反映组织结构 — 这是 Conway's Law 的反应用：先有用户视角，才有数据 schema。

itsuki 发现：
- CHANGELOG 顶部 `[0.4.0-wip]` 标在 2026-04-21，**9 天没 close**
- spec / design 文件名 `_v0.1` 但项目实际 v0.3.2 / v0.4.0
- 没有"什么时候 bump、bump 时改哪些文件"的 SOP

### 拍板（4-29 itsuki）

1. **版本边界**：方案 B — 双 minor。v0.4.0（4-21 → 4-22 上）+ v0.5.0（4-22 中 → 4-29）
2. **文件名**：方案 C-2 — 11 个文件去 `_v0.1` 后缀
3. **SOP 位置**：`00_admin/版本管理SOP.md`
4. **追问 3 点**（关键产品思维）：
   - 让不同对话知道现在到了什么版本？
   - 让 Claude 知道去读 SOP？
   - 和 iCloud 既有版本管理实践指南有什么区别？

### 解（4 层叠加机制）

让 Claude 必读 SOP 的 4 层：
1. **CLAUDE.md inline 5 条核心** → 触发条件清单
2. **WIP.md 头部"当前版本"行** → 信息密度
3. **pre-commit hook 提醒** → 改 spec 时强制看到
4. **CLAUDE.md §会话结束 第 4 项** → 30 秒判断

iCloud `版本管理实践指南.md` = 教科书（理论），repo `版本管理SOP.md` = 运行手册（操作）。**不重复，是分工**。

### 失败转成系统性解法

[0.4.0-wip] 拖 9 天没 close 是失败。处理方式：
- 不偷偷改 git 历史
- 写进 SOP §8 历史教训
- 建 4 层机制防再犯
- **失败本身变成 SOP 建立的契机**

> 这个 pattern 在 v0.5.0 AC 叙事 "认知 3 失败转成系统性解法" 里详细展开。

### AC 价值

| AC 核心问题 | 本事件贡献 |
|---|---|
| #1 問題発見 | 发现 [0.4.0-wip] 9 天拖延 + 文件名错位 |
| #2 問題意識 | 不接受"版本漂移作日常"，主动设计 SOP |
| #3 問題解決 | 4 层叠加机制 + 双 minor 一次 close |
| #4 自己認識 | 承认失败 + 不掩盖 + 转化为系统性解法 |
| #5 志望動機 | "工程成熟度" — meta 层面的项目管理思维 |

### 留个痕（给后续 AC 用）

> "我项目里有过一个失败：一个 minor 版本 wip 状态拖了 9 天没 close。我没掩盖，写进了版本管理 SOP 的历史教训段。然后我设计了 4 层机制：CLAUDE 项目指令 inline 5 条核心、WIP 头部当前版本行、pre-commit hook 提醒、会话结束 30 秒判断。任何一层失败时另外 3 层接住 — 这是 fault-tolerant 设计思维。失败转成系统性解法，比避免任何失败更重要。"

## §12 实战 bug — staging area 跨会话污染 + 误删 teacher_requirements.md 6 分钟 ⭐⭐ #AC候选

> 4-29 收尾会话。`[Mac-VersionMgmt-CC]` 在 commit `0e9fbb7` 时把另一会话 staged 的删除一起 push 出去 → GitHub main 上 `teacher_requirements.md` 消失 6 分钟 → CC 自查发现 → 立即恢复 + 写入 SOP §6。

### 时序

1. 14:11 `a0d8329` release commit（含 `A 02_design/teacher_requirements.md` 379 行）
2. 14:11 → 14:23 之间：另一 CC 会话 `git rm` 该文件（理由不明 — 可能误判为重复，可能改名意图未完成）→ `D` staged，但**没 commit**
3. 14:23 `[Mac-VersionMgmt-CC]` 收尾时 `git status --short` 显示 ` M WIP.md` `D teacher_requirements.md`（D 在前 column = staged）— **CC 没逐行核对**
4. 14:23 `git add 00_admin/WIP.md` + `git commit` → staging area 里的 D 被一起 commit 进 `0e9fbb7`
5. 14:23 `git push origin main` → GitHub 上文件消失
6. 14:29 itsuki 问"所有文件版本对齐了吗" → CC 跑全面检查时 git status 又看到 `D` 行 → 发现 bug
7. 14:29 `git checkout a0d8329 -- 02_design/teacher_requirements.md` 恢复
8. 14:30 `dda3541` fix commit + push → 文件回到 GitHub

误删窗口：约 6 分钟。

### 根本原因

**多个 CC 会话共用同一个 `.git/index` 文件**（Mac 文件系统层面）。任何会话 `git add` / `git rm` / `git mv` 都改这个共享 index。所以 "staging area" 不是会话私有的。

CC 思维定势："我没改的文件不会被 commit" → **错误假设**。staging area 可能被另一会话污染。

### 修复 + 加固

1. **恢复**：`git checkout a0d8329 -- 02_design/teacher_requirements.md`（379 行内容完整）
2. **fix commit**：`dda3541` push 到 GitHub
3. **SOP §6 加铁律**："commit 前 git status 逐项核对"+"非本会话产出 → git restore --staged"
4. **AC 素材**：本 #AC候选 ⭐⭐ dump

### AC 价值

| AC 核心问题 | 本事件贡献 |
|---|---|
| #1 問題発見 | 自查时发现已 push 出去的删除（不是被别人指出） |
| #2 問題意識 | 不放过"为什么 staging 里有我没改的文件"这个细节 |
| #3 問題解決 | 6 分钟内：发现 → checkout 恢复 → fix commit → push → SOP 升级 |
| #4 自己認識 | 承认假设错（"我没改就不会被 commit"）+ 写进 SOP §6 历史教训 |

### 留个痕（给后续 AC 用）

> "我做版本管理总修那次会话最后犯了一个错：commit 前没逐行核对 staging area，把另一个会话 stage 的删除一起 push 出去，导致一个 379 行的设计文档在 GitHub 上消失了 6 分钟。我 6 分钟内发现 + 修复 + 把铁律写进 SOP §6。这件事让我学到：多 CC 会话共用 `.git/index`，staging area 不是会话私有的。"

### 留意

这个事件**和 v0.4.0 [wip] 9 天没 close 的 pattern 一样** — 都是"假设错 → 失败 → 转成系统性解法"。**fault-tolerant 设计的核心是承认假设错并把规则写下来**。

SOP §6 加固后下次 commit 前会强制 git status 逐项核对。

**问题**: CC 派 agent 扫出 39 条后自动进入"修复模式"批量做 P2 机械修复
**正模式**: 找漏洞 → 列清单 + 严重度 + 建议 → 等拍板哪些修
**memory**: `feedback_audit_means_find_not_fix.md`

#### 反模式 2: 找重复要读全文,不靠标题

**触发**: itsuki "你读文件的时候不要只读标题,还要看内容,主要就是部分内容有重复"
**问题**: 第一个 agent 基于文件名 + metadata 判断"backlog 70-80% 重复",错
**正模式**: 找 L2 章节级重复 + L3 关键事实点散到多文件硬编码(如扣分阈值 ≥9/≥8 在 10 处漂移就是 L3)
**memory**: `feedback_audit_read_content_not_just_titles.md`

#### 反模式 3: 改动总结用"原来 / 问题 / 改成"三段式

**触发**: itsuki 反问 "[Q2 那段] 他妈的说了什么?你改了什么?" — CC 总结用 "git mv 8 文件 + perl 替换 22 处"工具术语堆砌
**问题**: CLAUDE.md §会话结束 #6 早规定"讲内容不讲工具",CC 仍犯
**正模式**: 每个改动 "原来 [旧版长啥样] / 问题 [哪漂移] / 改成 [新版怎样]",涉及具体文件名(不堆数字)
**memory**: `feedback_change_summary_three_part_format.md`
