## 1. IX-007 调查：任务前提是假的（模式 2 — 假设崩了→真因）

### 背景
交接文件 §4.2bis 把 IX-007 写成「otherDetailBody（申请详情页其它类分支：修繕/来訪/代理受取）接后端」。听起来是个普通接线活。

### 经过
派 3 个只读子代理并行调查 IX-007/009/034。我（CC）没等代理结论，自己先独立核对后端：
- `models.py:284` —— `applications` 表有 `CheckConstraint("kind IN ('帰省','外泊','帰国')")`，硬性只允许出寮届三种。
- grep `routers/` `models.py` `schemas.py` 全文 —— 「repair / guest / parcel / 来訪 / 代理受取 / 修繕」零命中。
- `dorm_life.py` 有冷蔵庫購入 / 物品所持 / 行事提案 / 日程変更，但没有修繕/来訪/代理受取。

结论：**iOS otherDetailBody 那些「其它类」申请，后端根本没有对应的表/接口。** 它在生产环境是「死分支」——能进申请详情页的真数据只来自 `/applications/mine`，全是出寮届系，全部走 StayDetailView（已接后端那条），otherDetailBody 永远到不了。子代理结论跟我独立核对完全一致。

### 关键判断
「把 otherDetailBody 接后端」这个任务**前提不成立**——它对应的申请类型后端零实装。我没有闷头去接（接什么？没有数据源），而是拆成两条路：
- Option A：otherDetailBody 降级 DEMO-only（圈 `#if DEMO`），生产兜底防显假人。最小诚实改动。
- Option B：真做这功能（新建表+schema+CRUD+承认链+iOS），是 5 端联动新功能，要 itsuki 拍板。

### AC 价值
- 对应核心问题：#1 問題発見 + #2 技術判断 + #4 失敗と修正（避免「闷头接一个没有数据源的接口」这种假完成）。
- 展示：拿到任务先审前提、不盲目执行；用代码事实（CHECK 约束 + grep）推翻文档描述。这跟 itsuki 反复要求的「转述/执行前先审前提」一脉相承（memory feedback_relay_ai_output_audit_premises）。

## 2. 「把所有问题都修好」= 三层，一个 GOAL 吞不下（方法论）

### 背景
itsuki 说「帮我写goal指令，我的目标是把所有问题都修好」。

### 经过
我把 `TODO.md` + `系统bug专栏.md` 盘了一遍，发现「所有问题」实际横跨：131 条 bug 专栏（43 🔴 阻塞 + 58 🟡 + 30 🟢）+ 5-30 审查 175 条 + 大工程 backlog（NFC 防代刷全栈 / Android 无网络层 / iOS 点呼接后端，都是几天到几周）+ iOS B 类接后端 + teacher_web 15 页真接入。

### 关键判断
我没把「fix everything」当一个 goal 写，而是分三层：
- ① 能自动修的 bug + 假数据接后端 → goal 该干的。
- ② 要 itsuki 拍板的（IX-007 上不上线 / 老师退回动作 / is_study_target / 版本号 bump）→ 自动跑会瞎猜，必须他先定。
- ③ 几天–几周的大工程（不是「修 bug」级）→ 半自动会做半成品。

goal 只锁第①层，②③明确划出去让它别碰。这样它能真跑完、不烂尾。

### AC 价值
- 对应核心问题：#2 技術判断 + #3 問題解決方法论。
- 展示：面对「全部修好」这种模糊大目标，先量化盘点、再按「能否自动 / 是否要决策 / 工作量级」分层，把不可执行的目标改造成可执行的。这是工程管理判断，不是埋头写代码。

## 3. 无人值守 GOAL 设计 —— itsuki 学会「设计规则让 AI 自己跑」（模式 5 候选）

### 背景
itsuki 原话：「我是直接把这个挂在这里，然后我就去睡觉了。我他妈没有时间停下来回答他的问题。所以如果真的遇到需要我，必须要我决策的问题，就直接跳过，留着下次做。然后去做那些能解决的事情。」

### 经过 + 关键判断
itsuki 设计了一套过夜无人值守的运行规则，让 AI 自己跑一晚：
1. **绝不问** —— 遇到要拍板的直接跳过、记「待决策清单」、继续做能做的。
2. **上下文自管** —— 他问「能不能到 50 万 token 自己 compact」。我摊牌：模型自己敲不了 `/compact`，但靠「harness 自动摘要 + 每阶段更新 handoff 文件」两层保证过夜不丢状态。
3. **绝不 push、灾难级不可逆操作跳过** —— 本地 commit 可以。

我把这三条写进 goal 指令 + handoff §7，让接手会话照着跑。

### AC 价值
- 对应核心问题：#5 自己認識 / 自我管理 + 方法论。
- 展示：itsuki 从「盯着 AI 一步步做」进化到「设计好护栏规则、把长任务委托给 AI 自主跑」。这是对 AI 协作方式的认知升级 —— 不是用得更熟，是**学会设计委托边界**（哪些能自动、哪些必须人工 gate）。
- ⚠️ 待 itsuki 本人补：他怎么想到要这样挂着跑的？以前是怎么做的（手动盯每一步？）？这个转变值得他自己口述。

## 4. 沟通翻车 —— 要我「写指令」我却「解释+跳去做事」

### 根因 + 修正
我把「写一份 X」的请求，错当成「解释 X + 去做相关的活」。itsuki 要的是**可粘贴的文本 artifact**，不是口头解释。
修正：他要我写指令 / 提示词 / 清单这类「产出一份文本」的请求时，**先把文本给全**，再谈别的。已写进 memory feedback。

## 5. IX-034 请假计数接后端（问题解决 — 标准接线）

### 做了什么
学生端「本月晚自习请假次数」原来只在手机内存累加（app 重启丢、跨月不清零 = 数字错）。接成后端按月真实计数：
- 后端新 `GET /api/v1/study/absence-requests/me/summary`（当月 target_date 全状态计数）+ schema `MyAbsenceSummaryOut`。
- iOS `StudyAPI.myAbsenceSummary()` + `loadMe` 登录后拉真实当月数。
- 照搬 IX-008b 的 `/discipline/me/summary` 样板（同样是「当前学生当月统计」）。
- 3 测试。后端 220 passed / iOS 双 scheme BUILD SUCCEEDED。commit `e0c150c`。

### 口径决定（itsuki 拍板「自己决定」，我按系统已有约定定）
- 按 target_date 算当月（不是提交日）/ 数全部状态（含被拒，匹配现有「提交即 +1」）/ 不加硬上限（严格按 IX-034 字面只修计数）。

### Codex 5.5 xhigh 审出 4 点（待修，已记 handoff §7.1）
跨月提交仍 +1 / loadMe 令牌竞态 / 测试时区边界 / formatYMD 未固定日本时区。逐条核实是真问题，留过夜 goal 第一件事修。

### AC 价值
- 对应核心问题：#3 問題解決。展示：复用已有样板（IX-008b）快速接线 + 每阶段 Codex 对抗审查找出自己没想到的边界（跨月 / 竞态）。
