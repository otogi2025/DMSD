## 1. [问题发现][技术判断] codex 审查注册页 — CC 不盲信工具，核实误报后只采纳真 bug

### 背景
itsuki 让 CC 把注册页学年/组/出席番号/房间号 4 个字段在 demo 模式下也默认空（原来预填假数据）。改完后 itsuki 要求「做完后调用 codex 做一次审查」。

### 经过
codex（OpenAI 的代码审查工具）报了 5 个发现。CC 没有照单全收：

- codex 标「最严重」的第 4 点：说删掉 4 个 `#if DEMO` 块后，别处读 `SEED.user.grade` 会读到空字符串。CC 去查 `SeedModels.swift:21`，发现 `var grade: String = "高3"` —— 全局假数据的默认值写死在模型里，CC 改的只是注册页本地输入框的初始值，根本没动 `SEED.user`。**第 4 点是 codex 误解了改动范围，证伪。**
- codex 第 5 点（真 bug）：提交时 `registrationDraft.grade_code` 送的是中文「高3」，但账号番号用的是数字码「06」。itsuki 判断「这个值得查」。CC 查后端 `schemas.py:588-590`，三字段都是 `pattern=r"^\d{2}$"`（正好 2 位数字）。**iOS 之前送中文/字母/1 位数，真实学生注册必被后端打回（422 校验失败）。**

### 关键判断
- CC 不盲信 codex —— codex 标「最严重」的反而是误报，核实源文件后证伪；标「可能重」的才是真 bug。
- itsuki 一句「这个值得查」精准命中影响生产的真 bug。

### itsuki 原话
> "这个问题顺手改一下"（出席号 >99 上限）
> "修"（数字码不一致）

## 2. [认知改变] itsuki 主动理解「码 vs 显示分离」的设计思想

### 背景
修数字码 bug 时，itsuki 问了一句：「所以后端还是知道06就是高三，05就是高二？」

### 关键
CC 解释：后端**不知道也不需要知道**「06=高3」，它只存数字码。「06=高3」的映射只写在一个地方（`system_features.md` 学年映射表），各端显示时各自翻译。为什么用数字码不用中文：每年 4 月升级时，后端只要 `grade_code + 1`（05→06），存中文就得做文字替换，慢且易错；数字码还能直接排序、直接拼成 6 位学号。

### itsuki 原话
> "所以后端还是知道06就是高三，05就是高二？"

### AC 价值
- 对应核心问题 #5 自己认识（认知改变）
- itsuki 通过追问理解「数据存储用码 / 界面显示用名」的分层设计 —— 模式 5（通过协作学到底层设计原则）
- 可挂学术概念：数据库设计的「编码 vs 展示分离」「单一真值源」

## 4. [方法论] design log 日语→中文的「界面文字 vs 说明文字」二分原则

### 背景
itsuki 让 CC 把 `IOS_DESIGN_LOG.md` 里的日语改中文。CC 先确认了一个关键边界。

### 关键
CC 识别出 design log 里日语分两种，处理方式相反：
- **说明文字**（CC 写给自己的设计笔记）→ 改中文
- **界面字符串**（学生手机上真看到的：按钮名「登録を完了する」/ 错误文案「アカウントが無効です」/ 推送通知）→ 保留日语（符合项目「UI 字符串保持日语」铁律）

itsuki 拍板「界面文字保留日语」。CC 据此改完 §1/§3/§5，§11 技术实装层约 180 行（混 Swift 代码注释 + API 名 + 术语笔记）拍板单独加 TODO §S。

- 对应核心问题 #2 技术判断
- 展示：执行批量改写前先识别边界、避免误伤 —— 不是机械全改，而是按内容性质分类处理
