## 1. [问题解决][失败] 后端 dev 库「假多头」侦探 — 计划的修法是错的

**背景**：前序会话留的交接（施工清单 §8）记了一个阻塞项：代録（老师代学生提交出寮届）搜学生时报「検索に失敗」，后端日志 `no such column: students.needs_renewal`。交接里我（CC）写的修法是「alembic merge heads 合并两个 head + upgrade」。

**经过（假设 → 假设崩 → 真因，模式 2）**：
1. 第一假设：以为是正常的「多头分叉」（两条迁移分支并行，需要 merge 合并）——这是交接里写的方案。
2. 拉迁移关系图核对，发现**不是分叉，是两个文件用了同一个 revision 号**：`b2c3d4e5f6a7` 同时被早期的 `align_application_schema` 和 6-05 别会话新加的 `add_needs_renewal` 占用。后者明显是复制前者文件改的，忘了改里面的 `revision =` 行。
3. 假设崩了：`alembic merge heads` 治不了「重复 revision 号」——merge 是合并两条真分支，重复号是另一种 bug。跑 `alembic heads` 确认：它只是**警告**「revision 出现多次」，但把图搞乱，报出两个假 head。
4. 真因 + 真修法：给 `add_needs_renewal` 换一个没被占用的唯一号 `f8a9b0c1d2e3` + 文件同步改名。换完单头恢复、警告消失。

**额外发现**：dev 库状态比「落后」更乱——版本戳停在 `e3f4a5b6c7d8`，但库里已经有本该后面才建的表（`guidance_records` 已存在）。说明这库是某次用 `create_all`（照 models.py 直接建全表）建的，但版本戳没跟着更新，schema 一部分超前于戳、`needs_renewal` 列又落后于现在的 models.py。逐个迁移修不动（一跑就报 table already exists）→ 改成**重建**：删库（先备份）→ seed.py 重灌 → `alembic stamp head` 盖最新戳。

**结果**：单头干净、needs_renewal 列在、34 表齐、311 测试全过。chrome 实测代録搜「田中」秒出学生。

**itsuki 原话**：（本会话 itsuki 只说了 `/compact` + 之前的授权「后端也交给你，肉眼签收最后我来，其余你都做」，无更多原话）

**AC 价值**（对应核心问题 #问题解决 #失败と修正 #技術判断）：
- 教科书级「计划的修法被现实推翻」——我自己交接里写的「merge heads」是错的，没盲目执行，先拉关系图核对发现真因（重复号 ≠ 多头分叉）。这正好印证 memory `feedback_relay_ai_output_audit_premises`（转述/执行结论前先审前提）+ `feedback_verify_agent_self_reports`（不盲信自报，独立核实）——这次审的是「我自己上一轮的结论」。
- 区分了三种 alembic 病：真多头分叉（用 merge）/ 重复 revision 号（改号）/ create_all + 版本戳脱节（重建+stamp）。
- 决策「重建 dev 库」而非「硬修半新半旧库」：dev 库是可重灌的 dummy 数据、无价值，重建给一个跟 models.py 完全一致 + 数据已知的干净库，正好给后面 chrome 验证用。

## 2. [方法论] chrome 自动化做「客观验证」而非「我觉得没问题」

**经过**：界面/功能验证没用「肉眼扫一眼觉得对」，而是 chrome-devtools 自动化打真后端：登录跑通 → 17 菜单页逐个点 → 读每页标题 + 正文长度（崩溃的页会没标题/正文极短）→ 拉控制台报错 → 拉网络请求看状态码。结果：17 页全渲染无崩溃、27 个接口请求全 200、控制台 0 报错、代録/点呼/学習/出寮者一覧/审批真数据通。

**AC 价值**（#問題解決 #自己認識）：把「验证」从主观感觉升级成可复现的客观证据链（标题表 + 网络 200 表 + 控制台日志）。这是工程成熟度的体现——区分「我相信它能跑」和「我有证据它在跑」。

## 3. [设计决策] 归档安全性：先证明是死文件再删

**经过**：归档旧文件（src/index.html 29629 行 / client.js / vendor / 打包脚本）前，先 grep 确认新源码没引用它们（只有 fonts.css 引用的 `_assets/` 字体是新构建需要的，保留），归档后**重新构建**——产物哈希 `index-DJArlqG4.js` 跟归档前完全一样，证明搬的全是死文件、对构建零影响。

**AC 价值**（#技術判断）：「删东西前先证明它没用」——用「构建产物哈希不变」作为客观判据，而非「我觉得这文件是旧的」。

## 5. [学习][认知改变] itsuki 搞懂版本号三个数字 + 拍板按天切 3 个 minor

**经过**：收尾后问「今天不止改了这个网页，还改了很多东西，看能迭代多少个版本、小版本号要不要动」。CC 拉了自 v0.12.0 以来的全部 80 commit（6-03/6-04/6-05 三天、5 端全动、动了字典 FIELD_REGISTRY + 共用功能真值 system_features），按 version-bump skill 决策树判断**该 bump minor**，给了三种切法（按天 3 个 / 合 2 个 / 合 1 个），itsuki 选「按天切 3 个」（v0.13.0/v0.14.0/v0.15.0）。

**关键认知改变（模式 5）**：itsuki 接着说「我还要改小 bug，能不能给我算小版本号？我现在版本号都是 0.10/0.11/0.12 这样跳的」——他**之前不清楚版本号三个数字的分工**，以为只能整批跳中间那个数字。CC 解释：版本号 = 主.次.修（0.15.0），中间「次」= 有新功能进来、最后「修」= 只修 bug 没新功能；他一直看到中间数字跳、最后一直是 0，是因为他这阵子**一直在做新功能**、没有「纯修 bug 不加功能」的时候。以后只修小 bug → 升 patch（v0.15.1、v0.15.2）。

**itsuki 原话**：
> "我还要改小 bug 之类的，能不能给我算小版本号啊？我现在版本号都是零点十十，零点十一，零点十二的跳的。"

**AC 价值**（#自己認識 #技術判断）：itsuki 主动发现自己对版本号机制的理解空白 + 提出疑问 → 通过 AI 协作补上语义化版本（SemVer）的概念。这是「通过工具实现自我升级」的典型路径，也是工程规范意识的成长（从「版本号随便跳」到「按 SemVer 区分功能/修复」）。

> "为什么你每次交接任务都喜欢放到 admin，然后每次用完都不删？你告诉我 admin 是拿来干什么的文件夹？我想的解决办法是，专门做一个给 ai 交接任务交接上下文的文件夹。"
