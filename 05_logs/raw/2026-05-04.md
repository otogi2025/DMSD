## §1 ⭐⭐⭐ AC 候选 —— 人机协作模型升级

### 起因

会话开始（"启动"），CC 报「现在站在哪」。我（itsuki）想升级现有的"等明示才 commit / push / tag"流程，最初想要"全自动":
- 收尾自动 commit（"免得每次都要开口"）
- 自动打 tag（"免得 git checkout 之后看不出做了什么"）

### CC 提醒了 3 个 unknown unknowns

我没意识到的事：

1. **GitHub repo public 后 git log 永久保留所有改动**
   - 任何人 git clone 后可以 `git log -p` 翻出每次 commit 加/删了哪些行
   - 隐私风险：commit message 里的真实姓名 / 密码 / 房间号永远在 history 里
   - AC 价值：评委也能看到"反复迭代"的过程，证据真实
   - 我意识到 → 撤回了"自动 push"授权

2. **commit 和 tag 是两件不同的事**
   - "每次改动有记录" = commit + 写详细 message 就够了，**不需要 tag**
   - "想回到某个具体版本" = tag 才有用（书签作用）
   - 我之前的提议把两个工具的功能混在一起了
   - 我学到了它们的差别 → 接受不打"重 tag"，commit message 写详细就够

3. **打 tag 在 DMSD 项目不是纯技术动作**
   - 4 个连带动作：决定版本号 / 写 CHANGELOG / 写 AC 叙事 / 决定时机
   - tag = "版本宣告 + AC 叙事"，是叙事级判断
   - 我意识到 → 重新思考分工

| 4 | "本地 commit 能删除吗？push 能挑着推吗？" | 能，没 push 前怎么改都行；push 可以推到某个 commit 为止 | 学到 git 工作流的"草稿 vs 公开"概念 |

### 最终拍板的协作模型

| 谁做 | 做什么 |
|---|---|
| **CC 自动** | commit 本地（不 push）/ raw/ 详细 dump / 起草 CHANGELOG 段（事实清单）/ 主动提 bump 时机 |
| **我（itsuki）主导** | push 时机 / bump 决定（patch / minor / major）/ **AC 叙事整个文档**（自己写） |
| **CC 执行** | 我点头后 → 打 tag + commit CHANGELOG + push 一气呵成 |

### 关键差别 —— CHANGELOG vs AC 叙事

- **CHANGELOG = CC 起草事实清单**（"v0.9.0 加了 X / 改了 Y / 修了 Z"，时间 + 文件 + commit hash）
- **AC 叙事 = 我自己写**（"为什么做、学到了什么、推翻过什么、面试时怎么讲"）

历史上 v0.3.0 ~ v0.8.0 的 6 个 `v0.X.Y_AC叙事.md` 都是 CC 起草的（旧分工），保持不动。新规则**从下一次 bump（v0.9.0）起生效**。
