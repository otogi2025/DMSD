## §5.4 (d) 指导履历 → **C 案 — 默认不显示 + 学生可申请开示**

### 真问题不是"显不显示",是"这功能本身要不要做"

itsuki 卡在前面 — 看到老师 LINE 提"指导履历"+"事案录入"立刻警觉:**"如果有指导履历这个功能,这个系统就脱离宿舍管理范畴了,变成整个学校的管理系统了"**。

CC 第一次回答跑偏了 — 直接进 "学生看不看" 拍板,没回应 itsuki 的真问题。被 itsuki 纠正后回到正轨。

事实查证(老师 LINE 完整原文里搜):
- 「**生徒の指導歴入力**」 — 教师输入指导履历(寮務部教師確認用 段下)
- 「**生徒個人データ表示(... 指導履歴 ...)**」 — 个人数据字段含指导履历

→ **是的,老师明确要了 2 处**。但语境是"寮務部教师"(负责宿舍事务的教师组),指导内容范围 = 宿舍生活相关(违反宿舍规则、生活态度、点呼态度、同寮生纠纷等),**不是**学校全体老师对学业的全方位指导。

→ 仍在宿舍管理范畴内,但确实从"点呼+出寮届自动化"扩展到"含学生宿舍生活行为记录的综合宿舍管理系统"。

### itsuki 接受了"指导履历功能要做"+ 拍板 C 案

C 案 = 默认不直接显示 + 学生可"申请开示"按钮 + 老师决定(全部/拒绝/部分开示)。

理由(CC 提案 + itsuki 接受):
1. 跟日本学校"开示请求"惯例一致(默认 confidential / 申请就开示)
2. 老师写指导记录时不必担心学生当场看到 → 能直率写,有引继价值
3. 学生有"申请权"的存在感(透明性的弱保障)
4. 个人情報保護法的"开示请求权"自然走这个路径,完全合规

## §5.5 (e) 寮監账号 → **关闭 + 2 条新规则**

### 规则 2: 寮監账号管理 — 前台不允许自助注册

**潜在风险点**(我提了,itsuki 没改):
- 任何寮監能加新寮監 → 离职寮監若失信任前未及时禁用,可能加恶意账号
