## A. 密码原来是 123456 — itsuki 以为不知道密码（模式 5，思考层数 3）

### 背景

实名账户登录上线后，itsuki 打开登录页看到 9 张老师卡片，说「密码我也不知道啊」。  
这 9 个账号是后端 `seed.py`（初始化假数据的脚本）自动建的，itsuki 没注意里面有个常量。

### 经过

CC 查了 `seed.py` 第 39 行：

```
DEV_PASSWORD = "123456"
```

这一行明文写了「所有假数据老师的密码是 123456」。后端会把 123456 哈希（用 bcrypt 算法，哈希 = 把密码变成看不出原文的乱码，存数据库用）存进去，登录时输 123456 就能通过。

itsuki「不知道密码」= 没注意到 seed.py 里的这个常量，不是真没有密码。

### 学到的东西

- **seed.py 是「幂等的」**（英语 idempotent，意思是「重复跑不会重复插入」——每次先查有没有这条记录，已有就跳过）。
  → 这意味着：光改 seed.py 里的账号列表是没用的。已经入库的 9 个账号还在数据库里，修代码不等于修数据。
  → 必须：改代码 + 备份旧数据库 + 删旧库 + 重跑 seed，才能让改动生效。
- 「改代码 ≠ 改运行状态」—— 这是 itsuki 第一次直接碰到「数据层 vs 代码层」分离的场景。

**itsuki 原话**：  
> 「密码我也不知道啊，只需要新股这一个人就好了」

**CC 操作**：
- 查 seed.py → 发现 DEV_PASSWORD = "123456"
- 把 DEV_TEACHERS 9 个→1 个（只留新建账号「新股」，全权限跨寮，role = 寮務部長）
- 备份旧库（`mv tomoshibi_dev.db tomoshibi_dev.db.bak`）→ 重跑 seed → 确认数据库只剩 `shingu|新股` 一条

**AC 价值**：
- 对应核心问题 #2（技术判断）+ #3（问题解决）+ #5（自己認識/认知改变）
- 展示了：通过 AI 协作工具查到自己代码里的「隐藏的默认值」，而不是猜、不是重置
- 展示了：「改代码 vs 改数据库状态」分离理解 — 工程初学者很容易认为「我改了代码，重启就生效了」，这次是第一次体感到「不对，数据库的数据需要单独处理」

## B. 返回按钮「失灵」— 根因是 CSS 点击区域极小（模式 2，思考层数 4）

### 背景

itsuki 进了密码输入页（屏2）后，想点「← 別の先生を選ぶ」（选别的老师）回到老师列表（屏1），结果回不去。

### 调查过程 — 假设链

**初始假设**：是 React 状态的 bug？——`lastTeacherId` prop 可能在 `setPicked(null)` 之后又把选中老师设回去了？  
→ 查代码，找 `lastTeacherId` 所有用法。只用于卡片高亮「上次」，没有任何 `useEffect` 会重新设 `picked`。**假设崩了**。

**第二假设**：代码逻辑有误（`setPicked` 写错了 / `type` 属性没写 / form submit 覆盖）？  
→ 读 LoginScreen 第 10408-10428 行，返回按钮原来是：  
```
type="button"   ← 写对了（不会触发 form submit）
onClick: setPicked(null) + 清密码/错误/失败次数   ← 写对了
```
逻辑完全正确。**第二假设也崩了**。

**关键推理（模式 2 顶点）**：截图里显示了「パスワードが違います (残り 2 回)」（密码错误）。这个错误是后端返回 401、React 处理 401、`setErr(...)` 更新状态、UI 重渲染才能出现的。说明 React 是活的、状态更新正常、同一套机制。  
→ `setPicked(null)` 技术上必然也能用  
→ 真正原因在别处

**真因**：返回按钮的样式是：  
```
fontSize: 12   ← 极小字体
color: T.ink3  ← 灰色（很浅）
padding: 0     ← 点击区域 = 文字本身高度，约 12px
background: transparent, border: none   ← 完全隐形
```
这个按钮视觉上「消失」了，实际点击区域只有 12px 高。itsuki 要么看不见它是返回入口，要么点击位置稍微偏一点就没点中。

### 修法

逻辑不动（`setPicked(null)` 正确），只改样式：
```
background: T.cobaltSoft   ← 淡蓝色背景，让按钮「出现」
color: T.cobalt            ← 主题蓝色，明确是可点的
borderRadius: 6            ← 圆角标记这是一个控件
padding: "8px 12px"        ← 点击区域从 12px 扩到 ~34px
fontSize: 13               ← 稍大一点
```

结果：按钮从「灰色 12px 透明文字」变成「蓝色背景圆角可点区域」，一眼能找到。

**itsuki 原话**：  
> 「然后进入输密码的页面，我没法返回上个页面，修一下」

**AC 价值**：
- 对应核心问题 #3（问题解决）+ #4（失败と修正）+ #5（自己認識）
- 展示了 debug 方法论：用「已知正常的功能（401 错误能渲染）」反推「整个 React 系统是活的」，缩小调查范围
- 展示了「假设崩了 → 不放弃 → 继续追查」的循环（合格者報告模式 2 最高级场景）
- 展示了：UI 设计中「看不见 ≠ 不存在 / 逻辑没问题 ≠ 用户能用」的认知

## C. 一键脚本 + 旧脚本归档（模式 1，思考层数 3）

> 本段补记本次会话前半段（因 context 压缩，已在 commit f4a882f 落地，未做单独 raw）。

### 背景 + 经过

实名账户登录让 teacher_web 必须同时跑「前端服务器（端口 8787）」+ 「后端服务器（端口 8000）」。旧的 `开发模式跑.command` 脚本只起前端一个服务器，不管后端 → 登录页一直报错（因为后端没在跑）。

itsuki 问：「我现在要怎么打开网站？每次都必须要有后端才能运行了？」

**解决思路**：
1. 写新的一键脚本 `启动老师网站.command`（双击就跑，不用命令行）  
   - 先清掉占用 8000/8787 端口的进程（有时候旧进程没关干净）
   - 启动后端（进入 `.venv`（虚拟环境，让 Python 用项目自己的依赖库），前台拿不到日志所以后台跑 + 写到 `/tmp/tomoshibi_backend.log`）  
   - 每秒检测后端是否就绪（`curl /docs`），最多等 20 秒  
   - 后端就绪后用 `open` 打开浏览器  
   - 前台运行 `python3 -m http.server`（静态文件服务器，让浏览器能访问 HTML 文件），让脚本窗口不消失  
   - `trap cleanup INT TERM HUP EXIT`（trap = 捕捉信号，这里的意思是：不管是关窗口/Ctrl+C/系统关闭，都会先跑 `cleanup` 把后端和前端一起关掉，不留僵尸进程）

2. 旧脚本「归档」而非直接删  
   - CC 检查发现旧脚本被 6 处文档引用（README / WEB_DESIGN_LOG / DESIGN_BRIEF / system_features / TODO / project-overview）
   - 直接删会留死链接（dead link = 文档里写了这个文件的路径但文件已经不存在）
   - 用 `git mv` 把旧脚本移到 `99_archive/`（git mv = git 版本管理里的移动命令，保留文件历史记录），同时更新 6 处文档引用

**itsuki 原话**：  
> 「开发模式跑.command 没用的话就归档，不要污染我的项目文件」
> （AskUserQuestion 回答）「归档 + 改 6 处引用（推荐）」

**AC 价值**：
- 对应核心问题 #2（技术判断）+ #3（问题解决）
- 展示了：改动前检查「这个文件/功能有多少地方依赖它」的习惯（引用分析）
- 展示了：`git mv` vs `rm` 区别（保留历史 vs 彻底删除）
