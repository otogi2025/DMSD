# 学习路径

> **这个文件记的不是"学过什么"(那在 `00_admin/progress_overview.md` 里),而是"为什么这样学"。**
>
> 每学一块新东西,回答三个问题:
> 1. 为什么要学它(现实需求,不是"网上说好")
> 2. 为什么选这个不选别的(和替代方案的对比)
> 3. 学的过程中感悟到什么(不只是记住了知识点)
>
> 最后更新: 2026-04-13

---

## 🧭 核心学习哲学:边做边学(2026-04-10 确立)

**我不走"先学几个月编程再开始做项目"的传统路径。我走"边做边学 + AI 辅助"。**

### 为什么

1. **传统路径在 AI 时代过时了**: AI 可以即时解释任何概念,"预先学完" 这个前提不再必要
2. **没有问题驱动的学习,记不住也用不上**: 我 3-11 开始学 Python 第一天后就停了一个月,正是因为没有真实项目推动
3. **AC 入試 更喜欢"带着问题学"的故事**: 评委看"你为什么学这个"比"你学了多少"更重要
4. **我试过传统路径,对我不可行**: 2-12 冻结规格 → 3-11 学第一天 Python → 一个月空白,就是证明

### 但警惕陷阱:vibe coding

纯粹"让 AI 写我不懂的代码" = vibe coding = 作弊。所以我定了 **三条铁律**:

1. **每行代码能解释** — AI 写完,我要能用自己的话讲清楚这行在做什么
2. **先猜后跑** — 代码跑之前,先预测它会怎么执行,然后跑一下对比预测
3. **写 dev_log** — 每次边做边学的过程要留下书面记录,强迫我"把学到的东西沉淀"

### 这个哲学对下面所有条目的影响

下面每一条"学了什么"都是在**具体任务推动下**学的,不是系统学习。这不是缺陷,是设计。

## 已走过的路(倒序)

### 2026-04-13 — SemVer 语义化版本规范

**为什么要学**: 项目里所有 spec 文件都叫 "v1.0",但根本没到 1.0,意识到版本号不能随便起。

**为什么学 SemVer,不是自己定规则**: SemVer 是业界标准,用它能和所有开源项目的版本号体系对齐,学一次通用,自己乱定的规则只能用在自己项目上。

**感悟**:
- 版本号不是标签,是**承诺**。"1.0" 代表"我对外保证不随便破坏兼容性",这个承诺在没上线前不能乱发
- 命名错了不可怕,可怕的是发现错了还不改(趁文件少立刻纠正)

---

### 2026-04-12 — NFC 原理 + 硬件架构

**为什么要学**: 决定了 NFC 方案但不懂原理,连它怎么工作都说不清,面试时没法回答。

**为什么学物理层面的原理,不只是 API**: 评委问"为什么 4cm 限制是优势",必须能从物理原理回答(电磁感应强度随距离衰减),不能只说"文档上这么写的"。

**感悟**:
- NFC 的"黑科技"感消失了 — 它就是高中物理的电磁感应 + 一些编码协议
- 技术的很多限制其实是**特性**(4cm 限制 → 必须物理在场 → 防作弊)
- 自己组装硬件(Raspberry Pi)比买现成方便、便宜、可定制,而且展示动手能力

---

### 2026-04-12 — iOS Core NFC 框架(Swift)+ Python nfcpy

**为什么要学这两个**: 两个阶段需要两套代码。Phase 2 手机端要用 Swift Core NFC,Phase 1 点呼机要用 Python nfcpy。

**为什么选 Raspberry Pi 上跑 Python,不是 Swift/Go**: Raspberry Pi 和后端都用 Python,设备代码和后端代码**同一种语言**,学习曲线陡度减半。

**感悟**:
- Swift 的 class/protocol/delegate/callback 这套概念对零基础有点难,但有结构
- Python 的 while True 循环 + requests 库组合,简单到不真实(~20 行代码)
- 同一个功能(读 NFC),不同语言有不同的范式思路

---

### 2026-04-10 — NFC vs NFD(Unicode normalization)

**为什么要学**: Git pull 在 Mac 和 Linux 之间失败,被逼着学的(不是主动学的)。

**为什么学这个冷门知识**: 实际项目会遇到跨平台问题,书本上不会讲这些"脏活"。知道这种坑的存在比什么都重要。

**感悟**:
- 跨平台开发有很多"看不见的坑",单平台永远遇不到
- 错误信息可能是误导的("untracked" 其实是 tracked),不能只看字面
- 零基础也能解决底层 bug — 关键是会和 AI 协作 + 非破坏性操作习惯(先 mv 到备份,不直接 rm)

---

### 2026-03-11 — Python 基础(第 1 天)

**学了什么**: 变量、数据类型(str/int/float/bool)、print、if/elif/else

**为什么要学 Python**: 后端选 FastAPI(Python),Raspberry Pi 点呼机也用 Python,数据分析/脚本也用 Python — 一套语言覆盖 3 个场景。

**为什么是 Python 不是 JavaScript/Go/Rust**:
- JS: 主要是浏览器/前端,后端选择相对少
- Go: 语法清爽但生态小,学习资源不如 Python 多
- Rust: 太难,不适合零基础入门
- Python: 入门最平缓 + 生态巨大 + 三个场景全覆盖

**感悟**:
- 变量要先赋值才能用(代码从上往下执行) — 这和数学的 "x=5, x 就永远是 5" 的直觉不一样
- True/False 要大写,语言有自己的规定,不能按直觉写
- 第一次看到自己写的代码运行起来的那种感觉

---

### 2026-03-11 — 前端/后端/API/数据库整体概念

**为什么要学**: 在开始写代码之前,必须先理解整个系统怎么通信。否则写后端不知道前端要什么,写前端不知道后端给什么。

**感悟**:
- 软件不是"一堆代码",是**多个组件在通信**的系统
- API 是组件之间的"合同",先定合同再写代码

---

### 2026-03-10 — Git 基础

**学了什么**: init, add, commit, push, pull, status, log

**为什么要学**: 代码需要在 Mac、VPS、GitHub 三个地方同步,手动复制不现实 + 没法追溯历史。

**为什么选 Git,不是其他版本控制**:
- Git 是业界事实标准
- GitHub 基于 Git,生态最大
- 其他(SVN/Mercurial)用的人越来越少

**感悟**:
- 工作区 → 暂存区 → 本地仓库 → 远程仓库,这个三层结构设计得很精妙
- 版本控制不只是"备份",是**能随时回到任何一个历史版本的时间机器**

---

### 2026-02 月 — 项目规格设计

**为什么要学**: 想做点呼系统,但不知道"做一个系统"包括什么 — 总不能直接开始写代码。

**学到的方法论**:
- 从真实问题出发定功能边界(不是"有什么技术可以用")
- 字段字典、枚举字典、错误码 — 让不同部分的代码对"同一个词"有同样的理解
- 冻结规格 vs 持续迭代 — 2 月份冻结的 v0.1 spec 让后续开发有稳定的参考点

**感悟**:
- 写规格比写代码更难,因为要想清楚"要什么"
- 规格文档不是一次写完的,是多次迭代的(后来在 4-12 又更新了 v0.2)

## 完整学习路线图(P0 / P1 / P2)

> 来源: 2026-02 月从旧的 `需要学习的内容.pages` 抢救出来的完整清单。
> 分级标准: **P0 必学**(直接决定 v0.x 能不能跑起来),**P1 重要**(降低返工),**P2 加分项**(做得更像完整产品)。

### 🔴 P0 — 必学(直接决定 v0.x 能否跑起来)

#### 1. 编程语言
- **Swift**: iOS 学生端页面、网络请求、JSON 解码、枚举映射、NFC 读写
- **Python(FastAPI)**: 后端选型。写 API、鉴权、业务逻辑、连数据库
- **SQL(PostgreSQL)**: 建表、查询、统计、结算、审计留痕
- **Shell(macOS 终端)**: 启动服务、查看日志、跑脚本、环境变量
- **Git**: 版本管理、提交、回滚、分支、diff

#### 2. 读懂本项目文档体系的概念
- **版本与冻结**: v0.x 与后续的边界,冻结决策,范围冻结,变更策略,Active/Obsolete 的含义
- **规格与契约**: Spec(业务规则) / Contract(接口约束) / Convention(全局约定) / Registry(唯一真值字典)

#### 3. Web 与 API 基础
- **HTTP**: GET / POST,Header,Body,状态码(200/400/401/403/404/500)
- **JSON**: object,array,null,字段缺失与默认值
- **统一返回结构**: `{ ok, data }` 与 `{ ok, error }` 的固定形状
- **参数校验与错误处理**: 输入校验,错误码与前端文案映射

#### 4. 点呼系统的业务规则与状态机
- **Session 生命周期**: `draft / running / ended` 状态集合
- **点呼判定**: 准时、迟到、缺席的判定条件;迟到窗口与截止时间;自动缺席结算触发点
- **座位表状态表达**: 颜色含义,叠加标记的优先级
- **老师手动操作**: 补签、改判、理由必填与审计留痕
- **纪律与扣分**: 扣分阈值,月度统计口径,处分触发规则的计算方式

#### 5. 时间与时区(项目的高频坑点)
- 时区概念: JST,服务端时间为准,倒计时只用于展示
- 结算时间点 `settle_at` 与判定逻辑

#### 6. 数据库与数据建模
- **关系型数据库基础**: 表、列、行,主键、外键、唯一约束
- **核心实体建模**: Student、Teacher、Session、Seat 状态、Checkin 记录、Manual 操作记录、Discipline 账本流水、Audit log
- **常用查询能力**: 按 student_id 查历史,按 session_id 查本场,按月份聚合日历数据

#### 7. iOS 客户端必备能力
- Swift 基础语法
- Codable 解码与编码
- enum 字符串映射,包含关键字冲突处理
- 网络请求与错误态处理
- NFC 基础流程与失败分支处理

#### 8. 后端服务必备能力
- 路由与控制器
- 请求体校验
- 鉴权与权限校验
- 事务与一致性
- 自动结算的实现方式: 定时任务 或 结场触发式结算
- 统一错误返回与错误码映射
- 审计日志写入

---

### 🟡 P1 — 重要(显著降低返工与联调成本)

#### 9. 安全与反作弊
- 设备与用户绑定的概念
- challenge / nonce / 一次性令牌
- 重放攻击与去重表
- 权限边界: 学生接口与老师接口严格分离
- 数据脱敏与日志安全

#### 10. 稳定性与异常场景
- **幂等**: 重复碰 NFC 的处理策略
- **弱网与断网**: 重试策略,客户端提示策略
- **数据一致性**: 汇总数据如何生成,统计口径统一

#### 11. 测试与验收
- 场景验收脚本的执行方式
- 回归测试概念
- 边界条件: 临界时间点、数据不存在、无权限访问、并发提交

#### 12. 工程化与可维护性
- **环境区分**: dev / staging / prod
- **配置管理**: 环境变量,secrets 管理
- **日志与可观测性**: 请求日志,业务日志,错误追踪

### 🟢 P2 — 加分项(做得好会很像"完整产品")

#### 13. 部署与运维
- Linux 基础命令
- Nginx 反向代理
- HTTPS 证书与更新
- Docker 与 Compose
- 数据备份与恢复演练

#### 14. 前端信息架构与交互设计
- IA 基础: 页面层级,导航结构
- 交互状态: loading / empty / error / success
- 日历视图数据组织方式
- 动画与性能基本概念

#### 15. 文档与产出(AC 材料)
- progress_log 写法: 每周完成、关键决策、问题、下周计划、可复现证据
- learning_process 写法: 概念卡片,踩坑复盘,解决步骤,迁移方法

## 关于"学习路径"这件事本身的反思

这份记录逼我每学一样东西都回答"为什么选它不选别的"。这个问题一开始很难 — 因为我常常"就是跟着教程学"。

但慢慢发现,**说不清"为什么选这个"就说明我没真懂**。面试时如果教授问"为什么你选 FastAPI,不是 Django",我只能说"我不知道,教程这样教的" — 这就没说服力。

所以写这个文件本身就是一种**学习方法论**: 强迫自己在学之前就做技术选型的思考,而不是被动接受。
