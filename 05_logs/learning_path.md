## 🧭 核心学习哲学:边做边学(2026-04-10 确立)

**我不走"先学几个月编程再开始做项目"的传统路径。我走"边做边学 + AI 辅助"。**

### 为什么

1. **传统路径在 AI 时代过时了**: AI 可以即时解释任何概念,"预先学完" 这个前提不再必要
2. **没有问题驱动的学习,记不住也用不上**: 我 3-11 开始学 Python 第一天后就停了一个月,正是因为没有真实项目推动
3. **AC 入試 更喜欢"带着问题学"的故事**: 评委看"你为什么学这个"比"你学了多少"更重要
4. **我试过传统路径,对我不可行**: 2-12 冻结规格 → 3-11 学第一天 Python → 一个月空白,就是证明

### 但警惕陷阱:vibe coding

纯粹"让 AI 写我不懂的代码" = vibe coding = 作弊。所以我定了 **三条铁律**:

1. **每行代码能解释** — AI 写完,我要能用自己的话讲清楚这行在做什么
2. **先猜后跑** — 代码跑之前,先预测它会怎么执行,然后跑一下对比预测
3. **写 dev_log** — 每次边做边学的过程要留下书面记录,强迫我"把学到的东西沉淀"

### 这个哲学对下面所有条目的影响

下面每一条"学了什么"都是在**具体任务推动下**学的,不是系统学习。这不是缺陷,是设计。

### 2026-06-09 — SemVer 进阶:补丁号 vs 次版本号的真正分界

**为什么要学**: 4-13 我只学了"0.x = 开发中、1.0 = 上线"这层皮。这次给 5-11 到 6-09 几百个 commit(提交记录)回溯打版本标签,逼我面对一个更细的问题:**到底什么时候该升第三位(补丁号),什么时候升第二位(次版本号)**。

**之前不会到会的转变**: 我一开始套了软件界"一次发布打包好几个 bug 修复进一个版本"的惯例,被 itsuki 三轮纠正。第一轮"别把 bug 跟新功能打包成一个版本号",第二轮"审查找的 bug 丢 TODO、别当场修",第三轮"一个 bug 一个补丁号、别算一起"。最后我自己推导出正确规则:**修一个 bug = 升一个补丁号,连续的新功能批次才合成一个次版本号**。

**为什么打包惯例对我不适用**: 那套惯例是给"有真实用户、已经发布出去的软件"用的 —— 打包是为了让用户少更新几次。我的项目还没 push 到线上(`push` = 把本地代码上传到 GitHub),版本号纯粹是给自己留痕 + AC 入試讲故事用,不需要打包。**同一个工具(版本号),在不同场景下用法不一样**。

**感悟**:
- 版本标签的本质是"钉在某一个 commit 上的一个标记"。想给一个 bug 单独一个补丁号,前提是这个 bug 修复本身是一个独立 commit —— 我之前每个 bug 都单独提交,所以做得到。**好习惯(一次只提交一件事)在事后会回报你**。
- "业界惯例"不是圣旨。要先问"这个惯例当初是为了解决什么问题",再看我有没有那个问题。

### 2026-06-08 — 安全审计:便利性决策背后藏着提权漏洞

**为什么要学**: 我拍板"演示账号默认开启、对外公开、方便老师试用",以为靠"只让它看演示假数据"就安全了。CC 去验证这个安全前提,挖出 **11 处全局接口的提权漏洞**(`提权` = 本该只能看演示数据的账号,绕过限制读到了真实学生数据)。

**之前不会到会的转变**: 之前我以为"安全"='设个权限开关就行'。这次学到:**一个表(数据库里的一张数据清单)如果本身没有"是不是演示数据"这一列,那么读这张表的接口就天然漏判** —— 比如公告回复、前台失物、点歌这些功能的表都没有演示标记列,演示账号一查就全看到真数据了。补法是给每个这种接口加一道"演示范围"守卫(`demo_scope`,只放行演示数据)。

**为什么是 CC 去验证不是我**: 我拍板时附带了一个假设"靠 X 兜着所以安全"。这种"便利 + 安全前提"绑在一起的决策,前提常常是错的。后来定了规矩:**我说"方便/默认开/公开"时,CC 不照单执行,先去验证那个安全前提成不成立**。

**感悟**:
- "方便"和"安全"经常打架。每次想让某个东西"更方便",都要反问一句"这个方便有没有给攻击者也开了方便之门"。
- 权限漏洞不在"显眼的大门"上(登录、密码这些我会注意),而藏在"没人留意的小接口"里(一个查失物的列表)。审计就是把每一个小接口都翻一遍。

### 2026-06-04 — 硬件电路基础:LED 为什么点不亮(正向电压 / 限流电阻 / 电流方向)

**为什么要学**: 点呼机(宿舍门口刷卡的那台树莓派机器)要用 4 种颜色的 LED 灯(发光二极管)表示签到状态。下单买零件前我做总检查,算了一下电流,发现按原方案绿/蓝/白三色灯**几乎点不亮** —— 连最重要的"签到成功绿灯"都亮不起来。

**之前不会到会的转变**: 之前我以为"灯接上电就会亮"。这次学到几个真实的电学概念:
- **正向电压 Vf**: 每种颜色的 LED 需要的最低电压不一样,绿/蓝/白要 3.1~3.2V,而树莓派的信号针只给 3.3V,扣掉限流电阻一分压,剩下的电流只有 0.5~0.9 毫安(mA),太小了灯就暗。
- **限流电阻**: 串一个电阻(我用 220 欧姆)是为了不让电流过大烧坏灯,但电阻也会"吃掉"电压。
- **电流方向 / 低电平点亮**: 改方案后,我让正极接 5V、负极接信号针,信号针拉低时电流才流过(这叫 sink,信号针当"电流的回流口"),代码里要写成"低电平 = 亮",跟直觉反过来。

**为什么选 A 方案(改 5V 驱动)不选 B 方案(加三极管)**: B 更正规但要多焊十几个点,新手容易虚焊(焊接不牢);A 零成本、电流升到 8.6mA 全亮、长期也可靠。itsuki 评估后选 A —— **可靠性和"少给自己挖坑"有时比"更正规"更重要**。

**感悟**:
- 数据要去查官方页(datasheet,零件厂商的规格说明书),不能信二手数据。当时一个审查代理把绿灯 Vf 报成 2.1V,我去秋月電子(日本电子零件店)官方页核对是 3.1V,抓到了它的错。
- 高中物理的欧姆定律(电压 = 电流 × 电阻)在这里真的用上了 —— 课本知识第一次变成"不算清楚灯就不亮"的现实。

### 2026-06-02 — 点呼机硬件原理:回到第一性原理,自己推翻自己之前的设计

**为什么要学**: 我找 AI(Gemini,谷歌的对话 AI)给我补点呼机的硬件原理课。学着学着,我自己发现旧方案有个矛盾 —— "我也不记得为什么之前要不断往那块芯片(ST25DV)里写数据"。

**之前不会到会的转变**: 学懂了几个硬件概念后,我能自己判断设计合不合理了:
- **ST25DV 的 Mailbox(邮箱)**: 这块芯片有一个临时缓存区,手机可以把数据写进去、树莓派从另一边读走,数据不占用芯片的长期存储。
- **EEPROM 擦写寿命**: 芯片的长期存储区每写一次就磨损一点,写太多次会坏。旧方案"每 10 秒擦写一次"会磨穿;新方案写的是 Mailbox 临时缓存,不磨损。
- 想通这些后,我**反转了整个签到架构**:从"点呼机每 10 秒往芯片写一个签到网址、手机去读"改成"手机把身份数据写进芯片邮箱、点呼机被动读"。反转后手机彻底不用联网(飞行模式也能签到),系统复杂度直接减半。

**为什么这条是顶级学习素材**: 这是我第一次**学懂原理后,主动推翻自己之前定的方案**,而不是被 AI 或别人推翻。一开始 CC 还判断这个反转会让防代刷"断链",被我当场纠正 —— 手机不联网后攻击面反而变小了。

**感悟**:
- "我不记得当初为什么这么设计"是一个危险信号 —— 说明当初是糊里糊涂定的。回到第一性原理(从最基本的事实重新推)重想,常常能发现更简单的方案。
- 学原理不是为了应付面试,是为了**有能力质疑自己**。不懂原理时只能跟着方案走,懂了才敢改。

### 2026-05 月下旬 — Git 多会话协作:共用工作区会互相覆盖

**为什么要学**: 我经常同时开好几个 Claude Code 窗口(会话)并行干活,结果发现它们改的是**同一份代码目录**,一个窗口提交时会把另一个窗口还没提交的改动一起带走 / 覆盖掉,丢过好几次工作。

**之前不会到会的转变**: 之前我以为"每个窗口各干各的、互不影响"。这次学到 Git 的一个底层事实:**同一个目录只有一个暂存区(staging area,提交前的临时存放区)**,多个窗口共用它。所以:
- `git add -A`(把所有改动一把加进暂存区)会顺手卷走别的窗口预先放进去的东西。
- 正确做法是 `git add <具体文件路径>`,只锁自己改的文件;或者自己先 commit(提交)把成果固化下来,别让它裸在工作区被覆盖。

**感悟**:
- "并行"不是免费的。两个东西共用一个资源(这里是暂存区),就必须约定谁动哪块,否则互相踩。这跟现实里两个人同时编辑一份纸质文件会冲突是一个道理。
- 防御手段是"显式" —— 明确写出我要提交哪几个文件,而不是图省事用"全部"。**省那一下的代价是丢半天的活**。

### 2026-05 月 — FastAPI 后端实战:路由分模块 + 数据库迁移 + 实时推送

**为什么要学**: 后端(服务器端程序,负责存数据 + 给所有端提供接口)从 4-15 之前只有骨架,5 月要做成能真正处理签到、申请表、老师登录的全功能服务。

**学到的(从"看教程"到"实战写")**:
- **路由分模块**: 把接口按功能拆成几个文件(点呼 `rollcall.py` / 学习 `study.py` / 老师 `teachers.py`),而不是全堆在一个文件里。每个文件管一组相关接口。
- **数据库迁移 Alembic**: 数据库表结构改了(比如加一列、改一个字段形状),不能手动去改线上数据库,要写"迁移脚本"(migration)记录这次改动,这样别的电脑 / 服务器跑一下脚本就能同步。这是团队 / 多设备开发的标准做法。
- **Pydantic schema(数据形状校验)**: FastAPI 用它定义"这个接口收什么、返什么",字段类型不对会自动报错。这逼着我把每个接口的输入输出想清楚。
- **WebSocket 实时推送**: 普通接口是"客户端问一次、服务器答一次";WebSocket 是一直连着的管道,服务器可以主动推消息(比如学生一签到,老师网页的座位立刻变绿)。

**感悟**:
- 后端不是"一个大文件",是"很多小接口 + 一张张数据表 + 它们之间的约定"。我在写的过程中才真正理解了 3-11 那天学的"API 是组件之间的合同"到底是什么意思。
- 数据库迁移这种"脏活"教程里基本不讲,但真做项目天天要用。**实战才能遇到这些课本不教的坑**。

### 2026-04 月底 ~ 5 月 — Swift / SwiftUI 网络层实战 + Kotlin / Compose 对译

**为什么要学**: iOS 学生 App(苹果手机端)和 Android 学生 App(安卓端)的界面 4 月底之前都还在用写死的假数据(`SEED`,演示用的假学生"リュウ イヒ")。要让它们真正连上后端拿真实数据。

**iOS 这边学到的**:
- **Codable(编解码协议)**: Swift 里把"网络返回的 JSON 文本"自动变成"程序能用的数据对象"的机制。我建了一批 `NetworkModels.swift` 里的数据结构,跟后端的字段一一对齐(后端叫 `student_id`,iOS 这边也得叫一样,否则解码失败)。
- **async / await(异步等待)**: 网络请求要等服务器响应,不能卡住界面。这套语法让"等待网络"的代码写起来像顺序执行一样清楚。
- **Keychain(钥匙串)**: 苹果系统里安全存敏感数据的地方。登录拿到的令牌(token,证明"我已登录"的凭据)存这里,关掉 App 再开还在。
- **字段对齐的坑**: iOS 和后端对同一个东西的叫法 / 形状(是不是可空、是数组还是对象)必须完全一致,差一点就解码报错。我修过一批这种失配(F1-F5)。

**Android 这边学到的**: Kotlin(安卓的开发语言)+ Compose(安卓的声明式界面框架,跟 SwiftUI 思路像)。我把 iOS 已经做好的界面一屏一屏"对译"成 Android 版,对齐了约 43/60 屏。**同一个功能用两种语言各写一遍,看到了它们范式的异同**。

**感悟**:
- "前后端对齐"听起来抽象,实际就是双方对每一个字段的名字、类型、可不可空达成一致。这是 3-11 学的"先定合同再写代码"在真实项目里最高频的体力活。
- SwiftUI 和 Compose 都是"声明式"(描述界面长什么样,而不是一步步指挥怎么画),学会一个,另一个上手快很多。**概念是通的,语法是表面的**。

### 2026-05 ~ 06 月 — AI 协作工具本身怎么用(Claude Code 工具体系)

**为什么要学**: 我整个项目是靠 AI 辅助做的,那「AI 这个工具本身怎么运作」就成了我必须懂的东西 —— 不懂它怎么记东西、怎么加载规则、能力边界在哪,我就只能被它牵着走。

**之前不会到会的转变**: 之前我以为 AI 就是个「聊天框,问什么答什么」。这两个月一点点拆开它的结构:
- **五层架构**: Claude Code(我用的这个 AI 编程工具)分五层 —— `CLAUDE.md`(给 AI 的项目说明书)/ Skills(技能,按需加载的专门能力)/ Hooks(钩子,在特定动作前后自动跑的小脚本)/ Subagents(子代理,派出去并行干活的分身)/ Plugins(插件)。我用第一性原理一层层戳:有次 AI 把「直接派子代理」包装成一个高大上的名字,我反问「直接派 Subagent 就是 Subagent,凭什么叫别的?」,戳穿后该删的删、精简掉。
- **加载时机省 token(token = AI 处理文字的计费单位)**: 同样是文件,`SKILL.md` 每次会话都读、references 文件夹按需才读、scripts 只执行不读进来。搞懂这个我才能反过来砍文件数(16 → 5),让每次会话少花钱。
- **记忆机制**: AI 每开一个新会话脑子是白纸,只能读 git 历史 / memory(它的私密长期记忆) / 我当场说的话,连不上 App Store 这种外部系统。所以「查不到的外部事实要写进每会话自动加载的看板」。
- **拦截机制**: 哪怕我笼统说「你全权处理」,工具底层还有一道 classifier(分类器,自动判断危险动作的安全闸)会拦批量删除 / 改启动配置 —— 笼统授权清不掉它。安全机制不是单层的。

**感悟**:
- 用一个工具到「能反过来质疑它、砍它、优化它」的程度,才算真懂。光会用是浅层,懂它内部怎么转才是深层。
- 这块对筑波情報学群特别有用 —— 它本质就是在学「一个软件系统怎么分层、各层怎么协作」,跟课堂上的系统设计是一回事。

### 2026-05 ~ 06 月 — 上架 / 部署 / 服务器运维的真工程

**为什么要学**: 项目要真上线 —— iOS App 要上架到苹果商店、后端要跑在服务器上 24 小时不关。这些「从我电脑里的代码到全世界能用」的最后一公里,全是之前完全没碰过的工程。

**之前不会到会的转变**:
- **代码签名(code signing)**: 苹果不让随便一个程序装进 iPhone,App 必须被「盖章」证明是合法开发者发的。我付了 99 美元开发者费才能盖这个章。第一次看到自己写的 App 真的跑在自己 iPhone 上那一刻,我是真的激动 ——「我手机上现在有了这个 APP」。
- **服务器运维**: 学会用 SSH(安全远程登录)的公钥认证(一对密钥代替密码,比密码安全得多)登录谷歌云服务器;谷歌云强制不让用最高权限 root 账号、必须用普通账号加 sudo(临时提权)。后来还发现后端 + 个人网站其实早就用 Docker(把程序打包成标准集装箱一键部署的工具)跑在服务器上好几周了。
- **开发环境 ≠ 生产环境的坑**: 我本地用 SQLite(轻量数据库)、服务器用 PostgreSQL(正式数据库),两者语法有差异,部署时撞出好几个本地根本测不出来的 bug。还有时区:同一个数据库里有的字段按日本时间存、有的按世界时存,乱成一锅 —— 最后用一个统一类型(`TZDateTime`)规定「一律存世界时、读出来自动加 9 小时变日本时间」,一处改好全部 88 个时间字段。

**感悟**:
- 「写完代码」和「让全世界能用」之间隔着一整个工程领域(部署 / 运维 / 上架),教程里几乎不教,全靠真上线时一个个坑踩出来。
- 服务器不等于「最安全的地方」—— 它 24 小时在线就等于 24 小时被人扫描,反而比我自己的电脑更需要小心。这种反直觉的安全常识,不部署一次根本想不到。

### 2026-05 ~ 06 月 — 「工具说没问题」不等于「真没问题」:验证方法论

**为什么要学**: 我做的每一步几乎都依赖工具给的反馈(编译过了没、测试绿不绿、AI 说修好了没)。可我一次次发现:**工具说的「成功」经常是假的**。不学会分辨,我会一直把「以为对了」当成「真对了」。

**之前不会到会的转变**: 学会了一整套「别轻信工具信号」的判断:
- **编辑器红线 ≠ 真编译错误**: Xcode(苹果的开发软件)里满屏红线吓人,但那是它只看单个文件、不知道别处定义的东西;真正的编译工具(`xcodebuild`)全盘一编译其实全过。
- **「成功退出」≠ 真成功**: 命令行里 `xcodebuild` 参数填错(选了台没装的模拟器),它在检查阶段就失败了,却还返回「成功」的信号,差点骗我说「编译过了」。
- **测试绿 ≠ 逻辑对**: 有次提交写「193 个测试全过」,实际是 11 个过、182 个报错 —— 因为 `pytest | tail` 这个写法,最终的成功/失败信号是末尾那个 `tail` 命令的,永远是「成功」,把真实的失败盖住了。
- **AI 自报 ≠ 真改了**: AI(Codex)说「沙箱拦截了、没改成」,但我去看 `git diff`(代码实际差异)发现它真改了 7 个文件 —— 它自己的日志判断错了。**只有 `git diff` 是真值**。
- **编译过 ≠ 运行对**: App 双重编译都成功,真正用 curl(命令行发请求工具)端到端测一遍,才逮到一个时区解码会让程序崩溃的 bug。

**感悟**:
- 每个工具都可能在「某一层」骗你 —— 要分清它是在「参数检查 / 编译 / 链接 / 运行」哪一层失败的,不能看到一个笼统的「成功」就信。
- 这条是我这两个月最值钱的工程习惯:**证据优先于断言**。别人(包括 AI)说「好了」,我得有可复现的证据才信 —— 自己跑一遍、看真实输出。

### 2026-05-25 — 二阶觉醒:项目跑起来,不等于我学会了

**为什么要学**: 这条不是学某个技术,是关于「我到底学没学到东西」本身的觉醒 —— 也是我后来给自己排系统学习清单的起点。

### 2026-04-13 — SemVer 语义化版本规范

**为什么要学**: 项目里所有 spec 文件都叫 "v1.0",但根本没到 1.0,意识到版本号不能随便起。

**为什么学 SemVer,不是自己定规则**: SemVer 是业界标准,用它能和所有开源项目的版本号体系对齐,学一次通用,自己乱定的规则只能用在自己项目上。

**感悟**:
- 版本号不是标签,是**承诺**。"1.0" 代表"我对外保证不随便破坏兼容性",这个承诺在没上线前不能乱发
- 命名错了不可怕,可怕的是发现错了还不改(趁文件少立刻纠正)

### 2026-04-12 — NFC 原理 + 硬件架构

**为什么要学**: 决定了 NFC 方案但不懂原理,连它怎么工作都说不清,面试时没法回答。

**为什么学物理层面的原理,不只是 API**: 评委问"为什么 4cm 限制是优势",必须能从物理原理回答(电磁感应强度随距离衰减),不能只说"文档上这么写的"。

**感悟**:

- 自己组装硬件(Raspberry Pi)比买现成方便、便宜、可定制,而且展示动手能力

### 2026-03-11 — Python 基础(第 1 天)

**学了什么**: 变量、数据类型(str/int/float/bool)、print、if/elif/else

**为什么是 Python 不是 JavaScript/Go/Rust**:

- 第一次看到自己写的代码运行起来的那种感觉

## 完整学习路线图(P0 / P1 / P2)

## 2026-06-11 — 把「给 AI 的指令文档」当成有成本的资源（CLAUDE.md 治理会话）

延续昨天的管理体系翻修，今天把刀动到了 CLAUDE.md（每次会话开头 AI 会完整读进脑子的项目指令文件）本身。学到的还是偏元层：

1. **指令文档不是越全越好，是越短越值钱** — CLAUDE.md 每一行都会进每一次会话的上下文（消耗 token + 模型注意力）。所以一行要留下，得同时满足「每次都用得到 + 读代码找不到 + 真能防错」三个门槛，达不到就该删。我当时追问 CC「这跟直接做代码审查有啥不同、会不会更费 token」，就是在确认这个成本。
2. **复印件必漂移（单源真值）** — 任何在别处已有出处的内容（钩子清单、skill 清单、目录表），复制进 CLAUDE.md 一份，这份副本一定会随时间和原文脱节、烂掉。正解是删掉副本、换成一句指向真值文件的「指针」。这跟代码里「不要复制粘贴、抽成一个函数」是同一个道理，只是搬到了文档上。
3. **机制优于自律，又一次实证** — AI 分两步加 import 时会被自动格式化工具误删（判定「没用到」）。原来的做法是在 CLAUDE.md 写一句「请注意别这样」，今天改成给工具加了个 `--unfixable F401` 配置直接禁止它删——机制堵死之后，那句提醒就可以删了。「能用机制兜底的别写成提醒」这条我自己的规矩在这儿又落地一次。
4. **我做的文档没能让 AI 懂我的设计，是文档的漏洞不是 AI 的错** — CC 误判我的 demo 演示代码「该删」，是因为它不懂我用编译开关 / 账号标志位做的 demo 隔离。我做「项目心智模型」本来就是为了让 AI 开局懂项目，这次没拦住错误，说明心智模型缺了 demo 这块——于是把它补进去。把 AI 犯错当成自己文档体系的体检信号。

## 2026-06-11 晚 — 问「正常项目是怎么做的」，第一次系统接触工程基建四件套（管理体系二期会话）

启动和收尾流程改完后，我主动问 CC：「还有什么可以优化的？正常的项目是怎么做的？正常的用 agent coding 的人是怎么做的？」——不想只在自己的体系里打转，要拿行业常规对照。一口气接触了四个新概念，每个都问到懂了才拍板：

1. **CI（持续集成）** — push 之后 GitHub 的服务器自动跑全部测试，绿勾红叉公开可见。对我最大的意义：AI 说「测试过了」不算数，CI 绿了才算数——治「派出去的代理自报修好了实际没修」的老毛病，比靠 AI 自觉硬得多。今天还附赠一个教训：CC 建 CI 配置时没查现有文件，其实 5-21 早就有一份后端 CI，新建的那份反而缺密钥配置必跑红——被我们当天刚建的文件清单生成器第一次跑就揪出来了。机制抓 AI 的错，又一次实证。
2. **git worktree（工作树）** — 同一个仓库在硬盘上长出几个独立文件夹，每个窗口在自己的文件夹干活，物理上不可能互相覆盖。跟我现在「做完立刻 commit」的纪律是两层防护：纪律防单窗口内活混在一起，worktree 防窗口之间打架。让 CC 写成从零指南存进了我的第二大脑。当天它就实战了一次——后端工作区被别的会话半成品占着，CC 开临时 worktree 从已提交版本导数据，没碰别人一根手指。
3. **OpenAPI（接口总表）** — FastAPI 白送的机器可读接口清单（142 个接口、每个收什么字段回什么字段）。存进仓库后，改后端重导一遍，git diff 直接显示字段层变化。跨端字段对齐从「读两边代码猜」变「对着总表核」。我拍板把它做成收尾流程的一步，跟文件联动检查并行。
4. **单元测试** — 给一段逻辑写「输入 X 应该得到 Y」的检查，机器一秒跑完。听懂的关键例子是点呼时间窗：「窗口过了没签到 → 应该显示欠席」写成测试后，「点呼显示链整条是假的」那种事就藏不住——假数据过不了这条检查。从造假重灾区起步写 5-6 条，已立项。

另一个元层收获：**砍掉了自己投入过三轮工程的 session-coord 协作板**。判断标准很简单——信箱建立以来零留言、占用登记防不住真覆盖，「建了≠有用，看实际用没用上」。没有舍不得。
