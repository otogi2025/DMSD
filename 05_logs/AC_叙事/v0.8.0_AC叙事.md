## 2. 遇到了什么困难（問題意識）

### 困难 1：三端字段不一致 + 没人协调过

5-1 早起手才发现 iOS / backend / teacher_web 各自前进了 2 周、**没人检查过 API 对齐**：
- iOS apply kind 用英文 `stay/holiday/returncountry`，backend 用日文 `外泊/帰省/帰国`
- iOS `stay_locations: ["1丁目"]`（扁平字符串），backend `stay_locations: [{kind, name, address?, phone?}]`（对象数组）
- iOS `meals_skip: [{date, meal: "朝食"}]`，backend `meals_skip: list[datetime]`
- iOS 多发 `student_id` 但 backend 用 JWT 解出来不收 → 422
- iOS form 必填 `reason` 但 backend schema 完全没这字段 → 422

**对齐成本** = 7 处 schema 改动 + Alembic migration + iOS encoder/decoder + teacher_web jsx 改 → 跨 3 端 13 个文件改动。

### 困难 2：iOS UI 写完了但「假按钮」不可信

10+ 屏 SwiftUI 全是 mock 数据，看起来完整，但点提交什么都不会发到 backend：
- LoginView：任何输入都通过
- StayForm.submit：`print` 调试 + 假成功 toast
- StayListMock.applyAmendment：只改本地内存数组
- AppStore.submitStudyLeave：直接 `count += 1`

**风险**：DEMO 4-28 给老师看的时候，老师以为系统在工作，实际 backend 啥也没收到。再不切真 API，做出来的东西没价值。

### 困难 3：JWT 安全 + 持久化（unknown unknown）

itsuki 不知道：
- JWT token 是机密、不能放 UserDefaults（明文 plist、越狱机能直接读）
- 业界标准是放 Keychain（苹果硬件加密的 secure storage）
- 不持久化的话 = 每次启动都要重登（用户体验差）

CC 主动诊断（§对话规则 §7）告诉 itsuki：「你现在做法是 X = 内存存 token 杀进程就丢，业界标准是 Y = Keychain 持久化，原因是 Z = JWT 是机密 + 用户体验」 → itsuki 学到。这是本会话的 ⭐⭐ AC 候选。

### 困难 4：Android 完全是新世界

itsuki iOS 已经熟（4-22 起手 sprint 来累积经验），但 Android 0 经验。Compose 跟 SwiftUI 形似但 API 不一样、Kotlin 跟 Swift 也不一样。要从零搭建工程框架 + 10 屏 UI + AppStore + NavGraph + MockData。

实装方针拍板（4-30、commit `889d65c` Round 1 prompt）：CC 主导逐屏对译 Compose（不派 sub agent / 不走 Claude Design 二次出工程）。

## 3. 怎么解决的（問題解決）

### 解法 1：按 plan 模式分 commit 序列推进

5-2 主会话 itsuki 让 CC 推所有「不需要决策、纯执行」的任务。CC 进 plan 模式 → 设计 7 commit 序列 → itsuki 批准后开始执行：

```
Commit 1: NetworkModels + APIClient 错误解码修正
Commit 2: Endpoints/ 配下 4 module + Encodable bodies
Commit 3: KeychainService + AppStore token 永続化
Commit 4: ApplicationStatus 加 approved_partial + 注释中文化
Commit 5: LoginView 切到 AuthAPI.loginStudent
Commit 6: StayForm + StudyAbsence 切到真 API
Commit 7: StayListView/Detail/Edit 切到真 API
+ Commit 8 收尾文档同步
```

每个 commit：写代码 → typecheck 0 error → commit → 跑 pre-commit hook → 下一个。

**为什么不一次性大改**：
- 小步 commit = 每条独立可 revert
- 每条 commit 跑一次 typecheck = 出错点定位精准
- 阅读 git log 时能看清每一步在做什么

### 解法 2：「先做不需要决策的、纯执行的」推进策略 ⭐⭐

itsuki 在 plan 之前明确说：「**先做那些不怎么需要我做决策，纯需要去做的任务**」 → CC 把所有任务分类：

| 类型 | 例 | 做法 |
|---|---|---|
| 纯执行 | iOS 网络层模块、AppStore wire-up、字段映射 | CC 直接做、不问 |
| 需 itsuki 决策（技术细节） | F6 backend register endpoint 的 step_token 存哪 | 列出推荐方案 + 等 itsuki 拍 |
| 需 itsuki 决策（产品 / UX） | 学習管理 6 fix、#21 老龄宿管 UI | 不动、等 itsuki 拍 |
| 需 itsuki 决策（人工动作） | 实物表照片、Mac mini setup | 列清单提醒 itsuki |

**为什么是好方法论**：零基础学生通常会卡在「啥都要问、啥都要决定」 → itsuki 这个分类法是**工程师思维**，把执行成本和决策成本分开。AC 面试可以讲：「我学会了把任务按需要决策的程度分类，不需要决策的让 AI 推进，需要决策的我聚焦思考」。

### 解法 3：JWT Keychain 持久化（CC 主动诊断 unknown unknown） ⭐⭐

CC 实装 KeychainService.swift 时主动告诉 itsuki：
- UserDefaults = 明文 plist、越狱机能直接读 → JWT 这种机密放进去不安全
- Keychain = 苹果硬件加密的 secure storage、即使 backup 也加密
- `kSecAttrAccessibleAfterFirstUnlock` = 解锁后可访问（锁屏后 background 也能用）
- 持久化好处 = app 重启自动登录（不用每次重登）

itsuki 学到了 iOS 安全模型的一个具体面 — **认证 token 跟普通 user data 应该分级存储**。这种「unknown unknown」（不知道自己不知道）由 CC 主动指出（§对话规则 §7），是 v0.8.0 学习金句的物化。

### 解法 4：discriminated union 在 Swift 没原生支持的处理

backend 用 Pydantic discriminated union（按 kind 字段 dispatch 到 3 个 schema：KisheiCreateIn / GaihakuCreateIn / KikokuCreateIn），但 Swift 没原生 discriminated union。

CC 给的解法（设计阶段、PlanAgent 思考）：
- **响应解码**：用单个 ApplicationOut struct + 全字段 optional（kind 别字段 nullable 友好）
- **请求编码**：用 3 个独立 struct，kind 字段硬编码日文「外泊」/「帰省」/「帰国」，避免出错
- **调用方按 kind switch** → ApplicationsAPI.create<Body: Encodable> 泛型方法

**为什么不模拟 union**：模拟代码会比直接用 3 struct 多 50 行 + 解码出错时调试更难。**「Swift 不是 Python，别硬套」**。

### 解法 5：错误分级 4 类（401/422/network/其他）

iOS 切真 API 后每个调用点都加 4 类 catch：
- `APIError.unauthorized` → token 失效、清掉 + 跳登录画面
- `APIError.unprocessable(let msg)` → 直接显示 backend 真实提示（如「出寮日は明日以降を指定してください」）
- `APIError.network` → 通信错、提示「電波を確認してください」
- 其他 → fallback `error.localizedDescription`

**为什么这样分**：
- 401 是 token 问题、不能让用户继续操作 → 强制重登
- 422 是输入问题、backend 知道具体原因 → 直接显示 backend message 给用户
- network 是环境问题、不是用户错 → 友好提示
- 其他兜底 → 不让 app 崩

这是 UX 设计哲学的体现（不是简单 try/catch）。

## 4. 学到了什么（自己認識）

### 1. 「设计 → 代码」不是直线

v0.7.0 close 时设计很完整（§7 14 子节 + §3.4 账号体系 + §8 数据模型），但代码上手第一天就发现 7 处字段不对齐。**设计跟代码之间有一道 schema 沟，得专门花时间填**。

教训：以后做大项目不要把「设计完成」等同于「代码能写」 — 中间还有 contract（API 契约）层要专门对齐。

### 2. 「AI 协作时把决策成本和执行成本分开」

零基础学生经常卡在「啥都要问 AI / 啥都要 AI 决定」 → 决策疲劳 + AI 越权。

itsuki 5-2 学会的策略：
1. 让 AI 列出「不需要决策的」+「需要决策的」+「需要人工的」三类
2. 不需要决策的让 AI 自己推（plan 模式 / auto 模式）
3. 需要决策的我聚焦思考、不被打断
4. 需要人工的我自己做（实物表 / Mac mini setup）

这种**「AI 协作分工法」**可以写进自我推荐书的「AI と協働する力」段。

### 3. 「JWT 这种机密不放 UserDefaults」是 unknown unknown

CC 主动诊断（§对话规则 §7）才知道。**自己不知道自己不知道**这种坑只能靠：
- AI 主动提（§7 「業界標準是 X、原因是 Z」话术）
- 经常跟有经验的人聊
- 出问题被打脸（生产事故）

itsuki 在自我推荐书里可以写：「AI と協働する一番大事な姿勢 = 让 AI 主动告诉我我不知道的东西」。

### 4. 「commit 不一定要 push」

CC 在收尾时主动说「不 push、不 tag、不 bump」 → itsuki 第一次明确意识到：
- commit = 本地保存（你电脑里）
- push = 发到 GitHub（全世界看得见）
- tag = 贴版本号标签（发布动作）

git 不是「**保存** = **发布**」一体的、而是分阶段。这是工程师的「**对外可见性**」概念。

### 5. 「Swift 不是 Python，别硬套」

CC 设计 discriminated union 处理时强调这点。语言生态特性不一样、强行用别的语言模式会变难。

更广义：**「业界标准做法」会因技术栈不同而不同 — 不要把一种语言的最佳实践硬塞另一种**。

## 5. 为什么筑波（志望動機）

v0.8.0 的范围让我意识到：**计算机科学不是「写代码」，是「在多个抽象层之间一致性管理」**。

- API 契约层：iOS / backend / teacher_web 三端 schema 必须 byte-perfect 对齐
- 类型系统层：Swift `Codable` / Python `Pydantic` / Kotlin `data class` 各自的 type checking
- 错误模型层：HTTP 状态码 → 应用层 enum → UI 错误提示
- 安全模型层：明文 plist vs 硬件加密 secure storage 选择

这种**「跨抽象层的一致性思考」**就是筑波情報科学類教的内容（系统设计 / OS / 数据库 / 编译原理 全部都在练这个）。

而 AC 入試重视「问题解決过程 > 结果」 → 我有 v0.0.1 → v0.8.0 完整 commit 历史 + 7 个 AC 叙事文件 + 31 个 raw 工作记录 + 6 个版本演变叙述 = 解决过程的完整可追溯证据链。
