# 监控告警清单

> 生产环境（api.tomoshibi.cc）的监控与告警：现状盘点 + 待接清单（按上线波次分级）。
> 原则：单人运维，所有告警统一进运营者邮箱（手机能收到推送），不建没人看的仪表盘。**每一项配完必须人为制造一次故障验证告警真的会响**，没验证过的告警等于没有。

## 0. 现状盘点

| 项 | 状态 |
|---|---|
| 存活监控（UptimeRobot 探测 /healthz） | 部署文档有配置指引（DEPLOY.md §6.3），Caddy 侧已为它关闭访问日志降噪 —— 但 UptimeRobot 是外部服务，账号里是否真配好、告警邮箱是否有效，**仓库内无法验证，需运营者登录 UptimeRobot 账号确认** |
| 错误追踪（Sentry） | **零配置零代码**。待办清单里是一条未勾选缺口（「无错误监控」），不是已就绪配置 —— 本清单 P0-2 落实 |
| 日志 | 仅容器默认 stdout 日志，无集中收集、无告警；出 500 只能事后手动 `docker compose logs` 翻 |
| 磁盘 / 证书 / 备份监控 | 全无 |

## P0 —— 真宿舍上线前必须接齐（五项）

### P0-1 存活监控（确认既有）

- 登录 UptimeRobot 确认：monitor 指向 `https://api.tomoshibi.cc/healthz`、间隔 5 分钟、告警邮箱有效。
- 验证：挑非点呼时段 `docker compose stop api` 约 6 分钟，确认告警邮件到达后 `docker compose up -d api` 恢复，确认恢复通知也到达。
- `/healthz` 会真探数据库（返回 db 状态），所以这一项同时覆盖「api 挂」和「数据库挂」两种大故障。

### P0-2 错误追踪 Sentry（新增）

后端 500 现在是静默的（只落容器日志没人看）。接入 Sentry 免费档：

1. Sentry 注册项目（平台选 FastAPI），拿 DSN。
2. `requirements.txt` 加 `sentry-sdk[fastapi]`；`app/main.py` 启动处按环境变量初始化（`SENTRY_DSN` 未配置时完全不启用，开发环境零影响）。
3. **隐私红线**（与隐私政策咬合）：初始化必须 `send_default_pii=False`（不发用户 IP/cookie），并确认请求体不上报 —— 本系统请求体里有未成年人姓名、健康报告等内容，**绝不能进第三方错误平台**。接入后隐私政策第 4 条需加第三方条目（见 `admin/E2_未成年人数据合规行动清单.md` §3.9）。
4. 告警规则：新错误类型首次出现 → 邮件。
5. 验证：临时踢一个测试异常端点或本地触发一次未捕获异常，确认事件出现在 Sentry 且**事件详情里没有任何学生姓名/请求体内容**再上生产。

### P0-3 备份成功监控（随备份 cron 一起上）

备份失败必须当天知道，而不是恢复时才发现备份是空的：

- 方式：healthchecks.io（免费）建一个每日心跳检查；备份脚本末尾成功才 `curl` 心跳 URL。24 小时没收到心跳 → 邮件告警。
- 备份脚本本体见 `ops/备份恢复演练SOP.md` §1（脚本已预留心跳这一步）。
- 验证：手动把心跳 URL 改错跑一次 → 次日应收到告警。

### P0-4 磁盘空间

磁盘满会把数据库一起带挂（故障手册 S2/S6 的常见根因），必须提前知道：

- 方式（不引新服务）：服务器 crontab 每天一次检查，使用率超 80% 时发信。healthchecks.io 变通做法：建第二个每日心跳，脚本「磁盘 < 80% 才 ping」，磁盘超限 = 心跳消失 = 告警，复用 P0-3 同一服务，零新增依赖：

```
#!/bin/sh
# disk-check.sh —— 磁盘低于阈值才发心跳；超限则不发，由 healthchecks.io 发告警
USAGE=$(df / --output=pcent | tail -1 | tr -dc '0-9')
[ "$USAGE" -lt 80 ] && curl -fsS -m 10 --retry 3 <healthchecks心跳URL> > /dev/null
```

- 验证：把阈值临时改成 1 跑一次（心跳停发），次日确认告警到达后改回。

### P0-5 证书（说明即可，无需新配置）

Caddy 自动续期证书；P0-1 的 UptimeRobot 走 HTTPS 探测，证书失效时探测即失败并告警 —— 证书监控被 P0-1 顺带覆盖，无需单独配置。知道这层关系即可（故障手册 S5 处理续期失败）。

## P1 —— 第二波（点呼机上线）追加

### P1-1 点呼机在线状态告警

设计已拍板：点呼机↔后端走长连接，断开即后端标记离线并向老师网页推「点呼机离线」告警，重连自动解除（BACKEND_DESIGN_LOG.md §5.8）。**当前两侧代码均未实装**（后端还没有设备侧长连接端点，点呼机软件未写）—— 属点呼机实装批次的工作，监控视角只需确认：上线前该告警在老师网页真的弹出过（拔一次点呼机网线验证）。

### P1-2 点呼完成度确认（可选，轻量）

每晚点呼结束后老师本来就会人为核对出席统计（业务流程自带），不必再建自动简报。若将来想要，从后端加一条定时任务发当晚统计邮件即可 —— 记录想法，不排期。

## 边界说明

- 老师网页里的「扣分告警」「设备离线通知」等是**面向老师的业务通知**，不是本清单的运维监控；两套体系目的不同（业务通知给现场老师看，运维告警给运营者修系统用），不要合并。
- 本清单不含点呼机硬件层监控（LED/喇叭自检等），归点呼机设计日志。
