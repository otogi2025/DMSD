# Tomoshibi 生产故障对应手册

> 按「症状 → 动作」组织。适用对象：生产环境 `api.tomoshibi.cc`（docker compose 三容器：caddy 网页服务器 / api 后端 / postgres 数据库）。
> 点呼机（第二波）相关条目见 §S11–S13，当前为设计态，硬件上线前须补成实操版。
> 本文件不含任何凭证；服务器连接方式见本地部署记录。

## 0. 三条原则

1. **点呼时刻先保点呼，不先修系统。** 点呼窗口只有几分钟，全寮约 120 人在排队。故障发生在点呼开始前后且 2 分钟内无恢复迹象 → 立即切纸质点呼（见 `ops/纸质点呼降级方案.md`），修复放点呼结束后。
2. **动生产前先确认备份。** 重启容器以外的任何写操作（改配置、动数据库、重新部署）前，确认最近一次数据库备份存在（见 `ops/备份恢复演练SOP.md`）。
3. **修完记录。** 故障时刻 / 症状 / 采取的动作 / 根因，当天写进开发日志。没有记录的故障等于会再来一次的故障。

## 1. 快速分诊

| 症状 | 最可能层 | 跳 |
|---|---|---|
| App、老师网页全都打不开 / 转圈超时 | 服务器或容器全挂 | S1 |
| 打得开但操作报错、健康检查显示数据库异常 | postgres | S2 |
| 刷卡/签到成功但老师网页座位不变绿 | WebSocket 显示层 | S3 |
| 个别功能报错，其他正常 | api 应用层 | S4 |
| 浏览器提示证书错误 / 连接不安全 | Caddy 证书 | S5 |
| 各种操作变慢、写入失败 | 磁盘 | S6 |
| 大批学生被误判迟到 | 服务器时钟 | S7 |
| 邮件不到 | 邮件服务配置 | S8 |
| 某个账号登录不上 | 登录锁定 | S9 |
| 刚部署完就出问题 | 新版本 | S10 |

判断顺序自外向内：域名解析 → HTTPS（Caddy）→ 后端（api）→ 数据库（postgres）。第一手信息永远是健康检查：

```
curl -s https://api.tomoshibi.cc/healthz
# 正常：{"status":"ok","db":"ok"}
# 数据库挂：503 {"status":"unhealthy","db":"down"} → S2
# 超时/连不上 → S1
```

## S1 全站不可用（/healthz 超时或拒绝连接）

**一分钟判断**：手机流量（非宿舍 Wi-Fi）访问 `https://api.tomoshibi.cc/healthz`。宿舍网能通说明是外网问题；都不通往下走。

**动作**：
1. SSH 登录生产服务器。登不上 = 服务器本体或网络挂 → 到 Google Cloud 控制台看实例状态，必要时重启实例（重启约 1–2 分钟）。
2. 登得上 → 看三容器状态：
   ```
   cd ~/tomoshibi-backend
   docker compose ps          # 三容器应全部 Up，api 应 (healthy)
   docker compose logs --tail 100 api
   ```
3. 单容器 Exited/Restarting → `docker compose restart <容器名>`。
4. 全部不在 → `docker compose up -d`。
5. **注意**：caddy 容器同时服务个人网站等多个站点，非必要不重启 caddy；确需重启，事后逐个确认邻居站点（pj / qts）仍 200。

**恢复确认**：`/healthz` 返回 ok + 老师网页登录一次成功。

**若在点呼时段且 2 分钟未恢复** → 降级纸质，修复放点呼后。

## S2 数据库异常（/healthz 返回 db:down 或大面积 500）

**动作**：
1. `docker compose ps` 看 postgres 是否 Up；`docker compose logs --tail 100 postgres`。
2. 先查磁盘再重启（磁盘满是数据库挂的常见根因，先 S6 排除）：`df -h`。
3. 磁盘正常 → `docker compose restart postgres`，等 30 秒再看 `/healthz`。
4. 重启无效、日志报数据文件损坏 → **停止尝试，走恢复流程**（`ops/备份恢复演练SOP.md` §恢复），不要在损坏的库上反复重启。

## S3 签到成功但老师网页座位不变绿（WebSocket 断）

**先安心**：签到数据已写入数据库，只是实时推送断了，**数据没有丢**。

**动作**：
1. 老师网页刷新页面（重建 WebSocket 连接），看座位状态是否恢复 —— 页面加载时会拉全量数据。
2. 刷新即好 → 多半是浏览器/网络瞬断，结束。
3. 刷新也不行 → 按 S4 查 api 日志。
4. 背景知识：后端固定单进程运行（WebSocket 连接表在进程内存里，这是设计约束不是 bug），api 容器重启会断开所有 WebSocket，老师端刷新页面即可重连。

## S4 个别接口 500 / 个别功能报错

**动作**：
1. `docker compose logs --tail 200 api | grep -i error` 找异常栈，定位是哪个接口。
2. 是刚部署的版本引入 → S10 回滚。
3. 是数据引起（某条脏数据触发）→ 记下复现请求，点呼时段外处理；老师端受影响的判定先用手动改判顶住。
4. 生产环境关闭了接口文档页（/docs），验证接口行为用 curl 带令牌手打。

## S5 证书错误（浏览器警告连接不安全）

Caddy 自动申请续期证书，正常时无需人工。出现证书过期/无效：
1. `docker compose logs --tail 100 caddy | grep -i -E "certificate|acme|error"`。
2. 常见根因：80/443 端口被占、DNS 记录被改动、Let's Encrypt 限流。按日志对症。
3. 修复后浏览器强刷验证；顺带确认邻居站点证书同样正常。

## S6 磁盘满 / 将满

**动作**：
1. `df -h` 看使用率；`du -sh ~/tomoshibi-backend/* /var/lib/docker 2>/dev/null` 定位大头。
2. 常规清理：`docker system prune -f`（清悬空镜像层；不加 `-a`，避免删掉在用镜像导致下次起不来要重新构建）。
3. 容器日志膨胀：`docker compose logs` 的底层文件可通过重建容器收缩（`docker compose up -d --force-recreate api`）—— 点呼时段外做。
4. 备份目录膨胀：按备份 SOP 的保留策略删过期备份。
5. **预防**才是正解：磁盘告警见 `ops/监控告警清单.md` P0-4。

## S7 大批学生被误判迟到（时钟漂移）

判定基准是服务器收到时刻（server_now，过渡态拍板），**服务器时钟 = 判定时钟**：
1. `timedatectl` 看 `System clock synchronized: yes` 与时区；NTP 未同步 → `timedatectl set-ntp true` 后复查。
2. 已产生的误判：老师网页手动改判逐个纠正（改判有审计留痕，放心改）。
3. 第二波点呼机上线后判定基准切点呼机打的 swipe_time（NTP 校准），届时点呼机时钟同样纳入本条检查。

## S8 邮件静默不发

已知坑：线上环境变量缺 `RESEND_API_KEY` 时邮件功能静默跳过（不报错）。确认服务器 `.env` 里该变量已配置且有效。改 `.env` 后需 `docker compose up -d api` 重载。

## S9 某账号登录不上（锁定）

后端有登录失败锁定机制（失败计数 + 锁定到期时刻，锁定等级递增）。学生忘密码反复试错会自锁：
1. 确认是锁定不是密码错：登录接口返回 423/403 类锁定响应。
2. 等锁定到期自动解除；急用时由管理员在数据库清除该账号的失败计数与锁定时刻（操作前记录原值）。
3. 批量出现 → 怀疑有人扫号，看 api 日志来源 IP，必要时临时封禁。

## S10 刚部署完出问题（回滚）

前提：部署 SOP 要求部署前必有 pg_dump 备份，没有备份不部署。
1. 症状明确由新版本引入（部署后立刻出现）→ 决定回滚，不现场调试。
2. 回滚 = 恢复部署前 pg_dump + 用旧版本代码重建容器（Mac 侧 git 检出旧 commit 重新 rsync + `docker compose build api && docker compose up -d api`）。
3. 数据库结构已被新迁移改动时，恢复 pg_dump 会回到旧结构 —— 部署后到回滚前新写入的数据会丢失，点呼时段部署被禁止的原因就在这。**部署窗口选点呼后、就寝前之外的时段。**

## S11–S13 点呼机相关（第二波，当前为设计态）

> 以下机制已拍板（flow_design.md §6 / ROLLCALL_DEVICE_DESIGN_LOG.md §6.1 / BACKEND_DESIGN_LOG.md §5.8 / WEB_DESIGN_LOG.md §5.8A）但**两侧代码均未实装**。点呼机软件实装完成后，把本节改写成实测过的操作步骤。

**S11 点呼机离线（断网）**：设计行为 = 点呼机本地比对缓存名单直接放行（绿灯+播报），签到存本地日志，网络恢复后按刷卡时刻批量补传；后端检测到长连接断开推「点呼机离线」告警给老师网页，老师可切手动点呼模式。补传与手动改判冲突时，老师手动优先。→ 运维动作：确认点呼机供电与 Wi-Fi、看告警是否解除；离线期间点呼照常进行，不需要人工干预队伍。

**S12 单台点呼机死机**：断电重启该机（软件按 systemd 服务自启设计）；该栋当场改用其他栋机器不现实（学生在各自寮栋）→ 该栋切纸质，事后手动补录。

**S13 个别学生卡读不出**：现场不排查卡。老师目视确认本人后，老师网页手动改判为出席（功能已实装），次日再处理换卡/重绑。

## 附：本手册边界

- 生产服务器为多站点共用（个人网站等同机），对 caddy 与服务器本体的操作牵连全部站点。
- 点呼机硬件故障（读卡模块 / LED / 喇叭）不在本手册 —— 属设备维修，见点呼机设计日志硬件章节。
- 演练与备份的一切细节在 `ops/备份恢复演练SOP.md`；监控接入在 `ops/监控告警清单.md`。
