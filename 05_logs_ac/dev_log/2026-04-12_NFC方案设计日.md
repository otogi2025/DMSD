## 今天做了什么

### 1. 学了 NFC 的原理

从零开始搞清楚了 NFC 到底是什么:
- NFC = Near Field Communication,工作频率 13.56 MHz
- 物理原理:手机里的线圈通电产生电磁场 → 卡片里的线圈靠电磁感应获得微小电流 → 芯片醒来把数据反射回去
- 距离限制 ≤ 4cm — 这个限制反而是优势(防作弊)
- 每张 NFC 卡有全世界唯一的 UID(出厂烧录,不可改)
- 空白 NFC 卡(NTAG215)大约 ¥30/张,100 张 ¥2000-3000
- iPhone 7 之后都能读 NFC,iOS 用 Core NFC 框架开发

### 2. NFC vs 二维码的决策

学校有个老师也在做类似的点呼系统,用的 Google 服务 + 二维码扫描。这让我有了紧迫感,但也帮我想清楚了为什么 NFC 更适合点呼场景:

> "学校另一位老师也在做类似的系统,他用的是 Google 二维码。我考虑过这个方案,但发现它有一个核心漏洞:学生可以截图二维码发给不在场的同学,系统无法识别。点呼的本质是'确认人在场',不是'确认有人扫了码'。所以我选择了 NFC——它的物理近场特性(<4cm)从根本上消除了这个漏洞。代价是每个学生需要一张 ¥30 的卡,但对于宿舍管理这个场景,防作弊比成本更重要。"

核心对比:

| 维度 | 二维码 | NFC |
|------|-------|-----|
| 成本 | 免费 | ¥30/学生 |
| 速度 | 2-3 秒(对焦) | < 1 秒 |
| 防作弊 | 截图就能转发 | 必须物理在场 |

### 3. 卡 vs 手机方案 — 分阶段策略(关键决策)

对比了两种 NFC 签到方案后做出的决策:

**方案 A**: 学生持 NFC 卡 + 老师/点呼机读卡
**方案 B**: 学生用自己手机碰固定 NFC 点

**我的决策: 先 A,后 B,最终两者共存**

Phase 1(最快上线): NFC 卡 + 后端 + 点呼机
- 不需要做学生 App → 开发量砍掉近一半
- 只需要: 后端 API + 点呼机上的读卡 App + 老师管理界面
- 目标: 最快速度上线一个可用的点呼系统

Phase 2(后续迭代): 加手机 App (iOS + Android)
- 学生可以选择用卡或用手机
- 手机 App 还能查看自己的出勤数据、扣分记录
- 没有智能手机的学生继续用卡 → 无人被排除

**为什么这样决定**:
1. 用卡可以绕过"学生手机 iOS/Android 不统一"的问题
2. 后端是两个 Phase 共用的,先做不浪费
3. 学校老师已经在用 Google 二维码了,我需要尽快上线自己的系统
4. Phase 2 不替换 Phase 1,而是增加选项 → 向后兼容

### 4. 播报防作弊设计(原创想法)

#### 心路历程: 从"发现漏洞"到"想出方案"

这个功能不是一开始就想到的,而是在讨论方案的过程中一步步推导出来的:

**第一步: 发现二维码的漏洞**
讨论 NFC vs 二维码时,我意识到二维码有一个致命问题——学生可以截图发给不在场的同学。这让我确定了选 NFC 而不是二维码。

**第二步: 发现 NFC 卡也有漏洞**
接下来在讨论"卡 vs 手机"方案时,我又想到:即使用了 NFC 卡,学生还是可以把自己的卡交给朋友,让朋友帮忙带去刷。NFC 的 4cm 限制只能保证"卡在现场",但保证不了"人在现场"。

**第三步: 关键的思维跳跃**
这时候我想到:如果系统读到卡之后大声播报学生的名字,而老师就站在旁边——老师听到"佐藤太郎",抬头一看,站在面前的不是佐藤太郎,就当场抓到了。

这个思维跳跃的关键是:**我不是在想"怎么用更高级的技术解决作弊",而是在想"怎么用最简单的方式让老师参与验证"**。技术验证设备,人验证人——两者配合比单靠技术更可靠。

#### 设计总结

> "我设计的时候发现,任何打卡系统都有一个共同弱点:技术只能验证设备,验证不了人。所以我加了一个语音播报:学生碰一下后系统大声念出名字,老师在旁边对照人脸。这一步看起来很简单,但它把人脸识别做不到的事——'让一个认识学生的人当场对照'——用最低成本的方式实现了。技术 + 人,比纯技术更可靠。"

**这个设计的价值**:
- 技术只能验证"设备/凭证",验证不了"人"
- 二维码可以截图、NFC 卡可以让朋友带、手机可以借给朋友
- 但播报名字 + 老师看脸 = 攻击者必须本人到场
- 本质: 把"机器识别身份"和"老师人眼识别"实时配对
- 成本极低: Python pyttsx3 库,几行代码就能念出名字

### 5. 点呼机硬件设计(已决定)

点呼机不是 iPad/iPhone,而是**贴在墙上的专用小设备**,类似公司门禁或图书馆入口的刷卡机。

**硬件方案: Raspberry Pi + NFC 模块**

```
  点呼室入口(墙上)
┌─────────────┐
│  ╭───────╮  │  ← 贴在墙上的小盒子
│  │  NFC   │  │
│  │ [触碰] │  │  ← 学生把卡贴上来就走
│  ╰───────╯  │
│    (指示灯)  │  ← 绿灯=成功, 红灯=失败
└──────┬──────┘
       │ WiFi
       ↓
     后端服务器
```

零件清单(一台):

| 零件 | 是什么 | 大约价格 |
|------|-------|---------|
| Raspberry Pi 4/5 | 微型电脑 | ¥8,000 |
| PN532 NFC 模块 | NFC 读卡器 | ¥1,500 |
| 小型扬声器 | 播报用 | ¥1,000 |
| microSD 卡 + 电源 | 存系统+供电 | ¥2,000 |
| 外壳(3D打印或买现成) | 固定到墙上 | ¥1,000 |
| **合计(一台)** | | **~¥13,500** |
| **两台(入口两条通道)** | | **~¥27,000** |

**关键优势**: Raspberry Pi 上跑 Python — 和后端用同一种语言,不需要学 Swift 或别的语言就能写设备端代码。

**为什么不用 iPad**: iPad 太贵(一台 ¥50,000+)、不适合固定在墙上、对 AC 入試没有加分(只是买了一个产品)。自己组装 Raspberry Pi 展示了动手能力 + 成本意识 + 技术选型能力。

**播报方案**: 点呼机自己播报(不依赖老师 iPad)
- 后端返回学生姓名(文字) → Raspberry Pi 本地用 Python pyttsx3 库念出声
- 延迟最低(不走额外网络)、开发量最低(Python 一行代码)
- 如果自带扬声器音量不够,外接 USB 小音箱(¥1,000)

### 6. 完整系统架构(已确认)

```
  点呼室入口                          VPS 服务器
┌─────────────┐                  ┌──────────────┐
│ 点呼机 A    │───── WiFi ──────→│              │
│ (树莓派+NFC)│←── 学生名字 ─────│  FastAPI     │
│ + 扬声器    │                  │  + PostgreSQL │
└─────────────┘                  │              │
                                 │              │
┌─────────────┐                  │              │
│ 点呼机 B    │───── WiFi ──────→│              │
│ (树莓派+NFC)│←── 学生名字 ─────│              │
│ + 扬声器    │                  └──────┬───────┘
└─────────────┘                         │
                                        │ WiFi
  碰 → 播报 → 下一个                     ↓
  整个过程 < 2 秒                ┌──────────────┐
                                 │ 老师 iPad     │
                                 │ (管理界面)    │
                                 │ 看出勤/缺席   │
                                 │ 不负责播报     │
                                 └──────────────┘
```

一次点呼的数据流(6 步):

1. 学生把 NFC 卡贴到点呼机 → Raspberry Pi 的 PN532 读到卡片 UID
2. 点呼机发 HTTP 请求到后端: `POST /api/v1/checkin { uid, device_id }`
3. 后端查数据库: UID → 学生姓名,写入签到记录
4. 后端返回: `{ success: true, student_name: "佐藤太郎", status: "on_time" }`
5. 点呼机收到结果 → 扬声器播报 "佐藤太郎" + 指示灯亮绿
6. 老师听到播报,抬头看一眼 → 确认是本人 ✅ / 不是本人 → 当场抓到 ❌

### 7. NFC 读卡代码(Swift 版 + Python 版都学了)

**Swift 版(~60 行)**: 用 iOS Core NFC 框架,读取 NTAG215 卡的 UID。涉及 class、protocol/delegate、callback、guard let 等 Swift 概念。这个是 Phase 2(手机 App)会用到的。

**Python 版(~20 行)**: 用 nfcpy + requests 库,跑在 Raspberry Pi 上。while True 循环等待刷卡 → 发 HTTP 到后端 → 播报名字。这个是 Phase 1(点呼机)直接用的。

**语音播报**: Python pyttsx3 库,3 行代码念出名字。iOS 的 AVSpeechSynthesizer 也是 5 行。

## 学到什么

1. **NFC 不是黑科技,原理就是高中物理的电磁感应** — 知道原理之后,设计决策变得有据可依(比如为什么 4cm 限制是优势不是劣势)
2. **和竞争对手做不同的选择,关键是能说清楚"为什么不同"** — 不是"我的更好",而是"在这个具体场景下,我的选择解决了他的方案解决不了的问题"
3. **分阶段上线比一次做完更聪明** — Phase 1 用卡跳过了 App 开发,直接砍掉一半工作量。Phase 2 加 App 不替换卡而是增加选项。这是一种产品思维。
4. **最好的防作弊不是纯技术方案** — 技术 + 人的组合比纯技术更可靠。播报想法的核心不是"语音合成"这个技术,而是"让认识学生的人实时对照"这个设计思路。
5. **自己组装硬件 vs 买现成产品** — Raspberry Pi + NFC 模块的成本是商用读卡器的 1/3 以下,而且用 Python 写设备代码(和后端同一种语言),对 AC 入試 还能展示动手能力。
6. **点呼机不应该是 iPad** — 一开始被 AI 误导以为点呼机=iPad,我纠正了。正确的设想是贴在墙上的专用小盒子,像门禁刷卡机一样。这说明我对产品有自己的画面,不是被 AI 的假设牵着走。
7. **版本号不是随便起的** — "v1.0" 这个标签有明确含义(正式发布),不能在项目还没写代码时就用。发现错误后立刻纠正,趁文件少的时候改,以后就不用背着一个错误的版本号体系继续走了。
