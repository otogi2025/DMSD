### 4. 推翻"手机发 UID"的初期设计,重设 Phase 2 为双路径共存

详见 `problem_solving/2026-04-15_iOS限制下的UID统一模型重构.md`。

我提出的"卡和手机都只发 UID,后端统一处理"这个统一模型撞上了 iOS 的平台限制(第三方 App 不能访问 Secure Element / HCE)。追问"自动贩卖机碰一碰怎么做的",挖到 Apple Pay 背后的 SE + 一次性 token 机制。最终架构:

- **路径 A(卡)**:卡 UID → 点呼机 PN532 → 后端判断 → 返回姓名 → 点呼机播报
- **路径 B(iPhone)**:iPhone 读点呼机外贴的静态 NFC 标签 → iPhone 自己发 `{student_id, device_id, ts, 签名}` 给后端 → 后端判断 → 后端通过 WebSocket 推回点呼机播报

两条路径互不干扰,最终都汇聚到后端。Phase 1 的卡设计不需要推翻,Phase 2 是"加",不是"改"。

## 学到什么

1. **NFC 卡里只有 UID 没有学生数据** — "标识符 vs 数据"的分离是数据库设计核心原则。数据在后端,UID 是"钥匙"
2. **iOS 第三方 App 访问 NFC HCE / SE 被 Apple 锁死** — "手机碰一碰"看似通用,Apple Pay 和普通 App 走的不是一条路
3. **Apple Pay 用 Secure Element + 一次性 token** — 每次 token 都不一样,复制无效;这是基础设施级的安全
4. **FeliCa(日本 Suica/PASMO)和国际 NFC 标准不同** — 频率相同,协议不同,iPhone 日本版特意加了 FeliCa 芯片
5. **WebSocket vs HTTP** — HTTP 是"问答模式",WebSocket 是"专用电话线,两边随时说话";Phase 2 后端推播报指令需要它
6. **thin client / thick server 架构** — 客户端越蠢越好,业务逻辑集中后端,改规则只改一处
7. **AI 推荐默认"加余量"** — 不是恶意,是保守偏向。作为决策者要有意识压最小可行配置
8. **"spec 冻结" ≠ "永远不改"** — 冻结是快照,设计演进应开新版本
9. **我今天纠正了 AI 两次** — 过度配置 + 漏报 problem_solving 类别
