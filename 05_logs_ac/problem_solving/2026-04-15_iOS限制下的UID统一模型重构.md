**触发场景**: 讨论 Phase 2 手机 App 方案时,我提出"卡和手机都只发 UID,后端统一处理"的架构

---

## 发生了什么

讨论 Phase 2 架构时,我提出一个看起来很优雅的统一模型:

> "那手机和 nfc 卡都只存 uid,数据还有判断全在后端完成
> 直接复制了 nfc 卡也无所谓,反正老师站在点呼机旁边"

AI 先肯定这个方向:
- ✅ 架构直觉对 — 这是 thin client / thick server,关注点分离
- ✅ 安全论证对 — 老师在场所以复制卡无效

但紧接着指出一个我不知道的技术约束:**iOS 第三方 App 根本不能伪装 NFC 卡发出任意 UID**。我理想中的"手机也发 UID" 在 iOS 做不到。

我原本设计的"一条协议通吃两种载体"方案,在此刻坍塌。

---

## 根本原因

Apple 把 NFC 卡模拟(HCE,Host Card Emulation)功能**锁死**:

- 只允许 **Apple Pay** 和 **Apple Wallet** 访问手机里的 **Secure Element**(独立加密芯片)
- 第三方 App 拿不到这个权限 — 不是技术做不到,是**平台策略**不允许
- Android 稍好,有开放的 HCE,但仍不能自由伪装任意 UID

所以"手机碰一碰"这个交互看似通用,实际上**普通 App 和 Apple Pay 走的不是一条路**。我作为个人开发者,不可能通过"我的 App 发 UID"来复制 Apple Pay 的体验。

---

## 我怎么一步步挖到原因的

### 第 1 步:不接受"做不到"

AI 说 iOS 限制后,我没直接放弃设计,而是追问:

> "那自动贩卖机上用碰一碰买饮料是怎么实现的?"

这个反问是关键。如果我止步于"做不到",就只知道"做不到"这个事实,但不知道**为什么**。而"为什么"才是真正有用的知识。

### 第 2 步:AI 解释 Apple Pay 机制,我学到新东西

- 手机里有一块独立的 **Secure Element (SE)** 芯片,物理上和主系统隔离
- 贩卖机读卡器直接和 SE 对话,**绕过 App 层**
- SE 发的不是 UID,而是 **一次性加密 token**
- 每次 token 都不一样,被 NFC 嗅探器抓到也没用(时间戳过期 + 签名对不上)
- 访问 SE 的权限必须由 Apple 亲自批准,只给支付网络和极少数合作方

还学到:**FeliCa**(日本 Suica/PASMO)是 Sony 的专用协议,不是国际 NFC 标准。iPhone 日本版特意多加了 FeliCa 芯片,这就是为什么国内 iPhone 刷不了 Suica。

### 第 3 步:想明白为什么我的 App 不能做同样的事

不是技术不够,是 **平台护城河**。Apple 投了几十亿建的 SE + token 生态,不是一个第三方 App 能复制的。

这个认知的关键:**我要区分"我能做的"和"平台内置能做的"**,不要幻想自己能做 Apple Pay 级体验。

### 第 4 步:重新审视设计前提

既然"手机发 UID"不成立,我原本的"统一协议"必须推翻。但不意味着整个架构报废 — 只需要给手机路径一条**不同的技术路径**。

---

## 最终怎么解决的

**方案:双路径共存**(卡走一条,iPhone 走另一条,不强求协议统一)

```
路径 A(卡):
  NFC 卡 → 点呼机 PN532 读 UID → HTTP 发后端 → 后端判断 → 返回姓名 → 播报

路径 B(iPhone):
  iPhone 用 Core NFC 读点呼机外贴的静态 NFC 标签(里面写 device_id)→
  iPhone 自己用 WiFi/4G 发 {student_id, device_id, ts, 签名} 给后端 →
  后端判断 → 后端通过 WebSocket 推"播报 xxx" 给点呼机 → 点呼机播报
```

**关键设计选择**:
- **点呼机不处理 iPhone 的签到数据**,只承担两个角色:
  1. 物理地标(外贴的静态标签,iPhone 读它拿 device_id)
  2. 接收后端推送的播报指令(WebSocket 长连接)
- **iPhone 用户的数据完全走自己的网络** — 即使点呼机离线,iPhone 用户也能签到
- **两条路径最终都汇聚到后端**,判断逻辑统一 — 没失掉原本 thin client/thick server 的优势

---

## 学到了什么

1. **"优雅的设计"要能容纳平台真实约束,不然只是空想**
   我的统一 UID 模型在纸上完美,但忽略了 iOS 的平台策略。软件设计不能只考虑"逻辑上应该怎么样",还要考虑"平台允许我怎么做"。

2. **Apple Pay 不是普通软件,是基础设施**
   苹果投了几十亿搭的 SE + token 生态,不是一个第三方 App 能复制的。

3. **批判性地接受限制:问"为什么不行",而不是直接放弃**
   如果我止步于 AI 说"做不到",就不会学到 SE / HCE / FeliCa / 一次性 token 这些真实的机制。**追问一步,认知多一层**。

4. **thin client / thick server 架构原则**
   设备端做最简单的事(读 + 转发),业务判断集中到后端。设备越蠢越安全,改规则时只改后端一处。

5. **Phase 1 的设计没白做**
   原本担心 Phase 2 会推翻 Phase 1,但实际上 Phase 2 的卡路径和 Phase 1 完全一样,只是额外加了一条 iPhone 路径。**分阶段策略的复利生效了**——早期决策没被废弃,这是"向后兼容"设计的价值。

---

## 遗留问题(诚实写)

1. **Android Phase 2 方案还没细化**
   Android 有 HCE 但机制和 iOS 不同,允许第三方 App 实现 NFC 卡模拟但受限。需要单独设计一套流程,不能直接复用 iOS 的 β1 方案。暂时记入 WIP 的项目债。

2. **后端→点呼机的 WebSocket 推送机制**
   需要搭持久连接通道 + 消息协议(播报指令格式、失败重试等)。技术上可行(Python `websockets` 库几行代码),具体设计等 Phase 2 开工时再细化。

3. **iPhone 提交数据的签名机制**
   要防重放攻击,但具体用什么算法(HMAC? JWT?)、key 怎么管理,还没想。Phase 2 开工时再说。

4. **这个认识的完整性检查**
   我对 Secure Element、HCE、一次性 token 的理解是今天刚学的。以后写 Phase 2 代码时,可能会发现更多细节(比如 Core NFC 读静态标签的 API 限制)。**承认:今天的方案是"设计意图层",不是"实现验证层"**。
