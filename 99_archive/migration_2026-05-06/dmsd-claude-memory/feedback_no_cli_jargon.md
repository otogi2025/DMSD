itsuki 说："要用我看得懂的语言教会我，而不是说黑话"。他不是不想知道工具，是 CC 的解释方式让他听不懂。

## 他举的反面例子

- 「13 条规则覆盖」「中途随时跑 3 模式：all / --staged / 指定文件」
- 「`bin/sync-check.sh` — 中途随时跑（3 模式：all / --staged / 指定文件）」
- 一句话里塞一堆路径 + 命令名 + 参数选项
- 用 CC 自己内部记号（D 系列 / S 系列）但不展开

## 正确做法

- **先说他要做什么**（人类动作，不是命令）："改完文件后我跑个检查给你看哪里漏了"
- **再说他能看到什么**："输出会列出'你改了 X 但 Y 没改'"
- **最后才说工具名**（如果他真要自己跑）：「这个检查脚本叫 sync-check.sh」
- **不要并列多个模式 / 选项 / 参数** — 选一个最常用的告诉他，其他的等他问
- **不要堆路径** — 一句话里超过 2 个文件路径就是太多

## Why
itsuki 完全零基础，没系统学过编程。他不懂 CLI 参数语法、不懂 `--flag` 是什么、不懂"模式"在工具语境里是什么意思。CC 一旦切到工程师对工程师的话术，他就掉线，整个解释失效。

## How to apply
- 写文档 / 总结 / 解释流程时，先问自己「他看了能不能直接照做」
- 答案是"能"才发出去
- 答案是"他得先猜 N 个术语意思"就重写
