**规则**：用户让 CC 做某件具体事时（整理 / 列清单 / 修 bug / 分析），CC 严格按字面 scope 做，**不要主动扩展**到相关但不同类别的工作。

**Why**：2026-04-21 晚，itsuki 让 CC "把还没完成的任务都整理一下"。CC 把整个 backlog 剩余（含 A 系列 AC 新建 / T 系列 基础设施新建 / 项目路线图 / v0.4.0 release 计划 / "下一步路径图"）全列了一遍。itsuki 纠正："我让你做的就只有目前系统有的漏洞和逻辑错误，别的你不要管，项目的推进你也不要管"。CC 越界 → 清单噪音大 → 他要再纠正。

**How to apply**：
- 用户说"漏洞 / 逻辑错误 / bug" → 只列 bug 类（事实错位、字段缺失、死引用、过期信息、内部矛盾）
- 用户说"任务" → 先问"是只 bug 还是包括新建 / 推进" 再列，**不要默认扩大**
- 用户说"整理现状" → 只整理现有的漏洞，**不加"建议怎么办"、"下一步路径图"、"版本路线"**
- 用户说"修 X" → 只修 X，不顺手改 X 相关的 Y / Z
- **不要主动"贴心"加"首要动作"、"路径图"、"阶段 A B C"**：这些是他拍板的事，不是 CC 规划的事
- 关键判断：**这条属于"已经存在的问题"还是"要新增的东西"？** 只做前者。AC 新建产出、硬件采购、新建 spec 文件、CI/migration 目录等"新建类"都不是漏洞。

**决策归属原则**：
- CC 提问题 → itsuki 决定做哪条 / 什么节奏
- 不要在 CC 侧排优先级 / 给 release 计划 / 给路线图 —— 这些是他拍板的工作
- 清单应该"客观陈述现状"，不是"CC 建议怎么办"

**反例（2026-04-21 晚做错的）**：
- Plan v1 里加了"下一步路径图 阶段 A-D"→ 他没要
- Plan v1 里把 A 系列（AC 补产出）当"剩余任务"列 → 不是漏洞
- Plan v1 里把 T5 CI / T7 migration / T11 体积 当"剩余任务"列 → 不是漏洞是新建
- Plan v1 里加"v0.4.0 release scope" → 项目推进
