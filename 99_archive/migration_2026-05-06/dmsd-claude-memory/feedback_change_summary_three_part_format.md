**规则**：CC 总结自己改动时（commit 后 / 任务结束 / itsuki 问"你做了什么"），用 **"原来 / 问题 / 改成"三段式**讲清楚每个改动。不要把工具操作（perl / git mv / 行号 / 数字）当成总结。

**Why**: 2026-04-29 itsuki 多次纠正 CC 的总结：
- 第一次："你完全没简单说明你懂了什么 [Q2 demo_4-28 那段] 他妈的说了什么？你改了什么？"
- CC 回答用了"8 文件 git mv 到 99_archive/.../ + perl 替换 22 处 + 9 文件" — 工具术语堆砌，看不懂
- 第二次：itsuki 引用 CC 改写后的 Q1 段（"原来：...问题：...改成：..."三段式）说"像以上的这种改动你也要记着才行"

itsuki 要的是**理解层面**的总结：
- "原来"：之前那段长什么样 / 写了啥（用人话描述内容）
- "问题"：为什么有 bug / 哪里漂移 / 谁出错（讲事实而非工具术语）
- "改成"：新版怎么样 / 解决了什么（讲新结果而非操作步骤）

**How to apply**:

格式（每个改动一组）：
```
**原来**：[旧版具体内容描述，用人话]
**问题**：[漂移 / 不一致 / 过期 / 风险，事实层面]
**改成**：[新版怎么样，结果层面]
```

例（itsuki 4-29 直接夸赞的 Q1 总结）:
> **原来**：CLAUDE.md "项目信息"那段特别长，把"iOS 用啥框架 / Android 最低版本 / Pi 型号 / 注册几步 / 账号几位数 / 密码错几次锁多久 / 采购多少钱"全部写死在 CLAUDE.md 里。
> **问题**：你 4-23 升级账号 ID 从 2 位变 6 位时，CLAUDE.md 没跟着改 — 还停在 2 位，已经错了好几天。
> **改成**：CLAUDE.md 那段每条只留一句话概述 + "详见 X 文件 §Y"指路。具体数字交给权威源（hardware_design / IOS_DESIGN_LOG / system_features）自己维护。

反例（itsuki 4-29 当面骂"他妈的说了什么"的版本）:
> Q2 demo_4-28 处理（CC 决定 = 整段归档）：8 文件 git mv 到 99_archive/2026-04-29_pre_v1.0_cleanup/demo_4-28/ + wifi_survey_howto.md 提到 00_admin/ 顶级（你调研日还要跑）+ 22 处路径引用批量 perl 替换（9 文件）

差别：
- 反例只讲工具操作（git mv / perl / 数字 / 路径），没讲"做了这件事的内容意义"
- 正例讲的是"以前是 X 状态，因为 Y 问题，所以改成 Z 状态"

**配套规则**：
- 不要用 "perl 替换"/"git mv N 文件"/"line A-B 改 line C-D"/"32 行 → 18 行"这种数字工具叙述
- 用 "把硬编码改成指针" / "搬到归档" / "断链修复" 这种动作叙述
- 涉及具体文件名要列（itsuki 看得见 = 能查），但不要堆数字
- 真要列改动文件清单时，用表格或一行一文件 + 改了啥
- 如果一个改动牵涉多文件，三段式一次描述完，不要拆每个文件单独写"原来/问题/改成"
- commit message 主体也用这个格式（讲为什么 + what changed 内容层面，不讲 git 工具）— CLAUDE.md §会话结束 #6 已经规定过

**触发该 memory 的关键时刻**:
- 任何 commit 后的总结
- itsuki 问"你做了什么 / 你改了什么 / 这一步在干嘛"
- 写 commit message 主体
- 任务结束 / 会话结束的总结
