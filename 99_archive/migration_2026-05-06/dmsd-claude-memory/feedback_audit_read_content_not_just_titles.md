**规则**：itsuki 让 CC 找"功能 / 内容重复"的文件时，CC 必须**读全文**对比，不能只看文件名 / 顶部标题 / 一行作用描述就下结论。重点找的是"**部分内容重复**"——同一信息在多个文件里被复述（不是整文件 100% 重复）。

**Why**: 2026-04-29 itsuki 让 CC 整理 / 找重复文件，CC 派 agent 扫了一遍，agent 报告大量基于文件名 + 顶部 metadata + 表面作用的判断（如"backlog 类高度可合并 70-80%"）。itsuki 立即纠正"读文件的时候不要只读标题，还要看内容，主要就是部分内容有重复" — 反映 agent 的判断粒度太粗。**真问题不是"两个 backlog 文件能不能合并"，而是"系统架构图 / 阈值规则 / 决策原因这种关键信息分散在 5 个文件各写一遍"导致漂移**。

**How to apply**:

- 找重复时**必读全文**：每个候选重复文件都 Read 完整内容
- 对比层级：
  - **L1 整文件重复**（罕见，文件名都几乎一样）— 显然该合并
  - **L2 章节级重复**（一节内容在 A 文件 + B 文件都写了）— 这是 itsuki 关心的主要类型
  - **L3 关键事实点重复**（一个数字 / 一个决策 / 一个时间在多文件硬编码）— 这是文档同步点漂移的根源
- 找的时候 grep 关键事实点：
  - 阈值数字（如"≥4 / ≥8"在多少文件出现 — 4-29 已发现 ~10 处漂移过）
  - 时间窗（如"3 分钟"/"180 秒"）
  - 重要名词定义（如"thin client"/"双路径"）
  - 架构图（同一组件关系画了几遍）
  - 路线图 / 阶段策略
- 列报告时分清"L1 / L2 / L3"，对每个重复点列清"哪些文件提到 + 各文件写得怎样 + 推荐合并到哪"
- **不要假设"标题不一样 = 内容也不重复"**，反之亦然
- 同样不要假设"标题一样 = 内容一样"（如 v0.3.0_AC叙事 / v0.3.2_AC叙事 / v0.4.0_AC叙事 / v0.5.0_AC叙事 标题相似但内容完全独立，每个版本的故事不一样，**不是重复**）

**反例（CC 误读时的样子）**：
- itsuki: "找重复 + 合并" → CC agent 看 `2026-04-19_项目审查_backlog.md` (87条) + `漏洞_剩余清单_2026-04-21.md` (38条) → 判定"70-80% 重复，应合并" ❌（实际未读全文，凭"都是 backlog 编号 D/S/A/T/L"误判）
- 正确: agent Read 两文件全文 → 对比每条 backlog 编号 → 实际 4-21 那 38 条是 4-19 87 条的"剩余未闭合子集" → 不是重复，是父子关系 → 合并 ≠ 删 ≠ 保留 ≠ 改成 4-19 含 [✅] checkbox 然后删 4-21（这才是真合并方案）

**正例**：
- itsuki: "找重复" → CC: 列阈值"≥4 / ≥8"在 ~10 处文档分散写 → 这就是"L3 关键事实点重复" → 推荐建文档同步点清单 §X 单源真值
- itsuki: "找重复" → CC 读 sprint.md / scope_tier.md 两文件全文，对比段落 → 发现 §0.1 demo 范围 + §1.x API 规格在两文件都写了同一信息 → "L2 章节级重复"，建议 sprint.md 改为指针引用 scope_tier.md

**操作模板**：

```
找重复时按这个顺序：
1. ls + grep 候选文件
2. Read 每个候选完整内容（不限于头部）
3. 用 diff / 人眼对比章节
4. 分类: L1 整文件 / L2 章节级 / L3 关键点
5. 报告时每条带 file:line 引用具体章节
6. 推荐方案: 合并 / 改指针 / 删 / 保留 (各有适用)
```
