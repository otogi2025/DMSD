**规则**：itsuki 让 CC 做"审查 / 排查 / 找漏洞 / 找不足"任务时，CC 的产出 = **漏洞清单 + 严重度分类 + 修复建议**，**不是**"自动开始修一遍"。

**Why**: 2026-04-29 itsuki 让 CC "排查所有项目文件，找 bug、找漏洞、找不足"。CC 在 plan mode 出了 39 条 finding 后，自动进入 auto mode 批量做 P2 机械修复 + 起草修复 batch 计划。itsuki 中途明确说"**我不需要你做项目推进相关的，我是让你找漏洞**" — 反映 CC 把"审查"误解成"审查 + 修复全套"，越界。审查任务的边界就是"找出来 + 给建议"，超出这个边界的修复，要等 itsuki 主动说"修这个"。

**How to apply**:

- 收到"找漏洞 / 排查 / 审查 / 检查 / 找不足"类指令 → **默认止步于产出漏洞清单**（plan 文件 + 简洁 chat 总结）
- 不要把"低风险机械修复"当作"无害可自动修" — itsuki 要的是**先看清现状**，再决定哪些修
- 即使发现"明显错的 1 行注释 / typo"，列出来不要默默改（除非和审查同时被授权）
- 真要修 → 先列出来 → 等 itsuki 选 → 才动
- 区分"审查任务"和"修复任务"的关键词：
  - **审查类**："排查 / 找漏洞 / 检查 / 审计 / 找不足 / 看看有什么问题 / 给我列一下"
  - **修复类**："修一下 / 改一下 / 把 X 改成 Y / 处理一下 / 删了 / 加上"
- 不确定就问："你要我列清单还是直接修？"
- 这条不影响"为什么 / 在干什么"的解释 — 该解释还是要解释（CLAUDE.md §对话规则 #1）

**反例（CC 误读时的样子）**：
- itsuki: "排查项目找漏洞" → CC 派 agent 扫一遍 → 列出 39 条 → **接着 git add + git commit 修了 7 条机械修复** ❌
- 正确: itsuki: "排查项目找漏洞" → CC 派 agent 扫 → 列 39 条 → 输出清单 → "需要修哪些？" → 等指示 ✅

**正例**:
- itsuki: "审查并修一下" / "排查 + 把能修的修了" → 这是审查 + 修复联合指令，可执行修复批次（仍要分级 + 高风险等授权）
- itsuki: "找漏洞" + 没说修 → 只产出清单
