## 1. 总览

### 1.1 三条签到路径共存（G2 决策 4-19）

| 路径 | 触发者 | 设备 | 学生操作步数 |
|---|---|---|---|
| **路径 A** | NFC 卡 | 点呼机 PN532 读头 | 1 步（贴卡）|
| **路径 B-iOS** | iPhone | 点呼机外贴 ST25DV16K（手机写入身份数据的邮箱）| 3 步（开 App + 点签到 + 碰）|
| **路径 B-Android** | Android 手机 | 同一张 ST25DV16K | 3 步（同上）|

**学生可同时持有卡 + 手机，日常任选一个路径**。每时间窗内一个学生只能签到一次（幂等规则 4-19）。

> **⚠️ 2026-06-03 架构反转后路径 B 的本质变化**：以前是「iPhone 读贴纸上的 URL → 手机自己上网 POST 后端」；现在是「iPhone 把身份数据写进贴纸的邮箱 → 点呼机读走 → 点呼机上网 POST 后端」。**手机不再上网**，路径 A（卡）和路径 B（手机）从此在「点呼机 → 后端」这段完全统一。详见 §3。

### 1.2 共同前提

- **服务器是唯一判定者**（架构原则 4-15）
- **手机 / 卡本地时间不参与判定** — 判定基准是点呼机盖的 `swipe_time`（学生接触机器那一刻、经 NTP 校准）。点呼机是唯一打时间戳的角色，后端拿这个时间戳判时间窗（避免「点呼机→后端」网络延迟把卡点学生误判迟到）。
- 每个 `device_id`（点呼机的设备编号）必须在 `DEVICE_REGISTRY` 注册后才能签到
- 老师现场目视监督（防代签的人防补偿 spec §5.1.3）

## 3. 路径 B-iOS — iPhone 写 ST25DV 邮箱 ✅（2026-06-03 架构反转重写）

### 3.1 端到端流程图

```
【待机 — 点呼机常态】
  ST25DV16K 是被动邮箱（Mailbox）。点呼机开机时初始化它：
  打开 Mailbox 功能 + 配置 GPO 引脚中断（被写入就拉低电平 = 硬件门铃）。
  点呼机平时不写 ST25DV（旧的「每 10 秒刷 nonce」已作废）。

【① 学生签到，T=0】
  1. 王小明打开 Tomoshibi App，点「签到」按钮
  2. App 唤起 iOS NFC 写入会话（CoreNFC），提示「请碰一下点呼机」
  3. 贴近 ST25DV16K（2-5cm）
  4. App 把身份数据写进 ST25DV 的 Mailbox 邮箱
     数据 = student_id（+ v1.1 可选：本机私钥签名，防造假学号）
  ※ 手机全程不联网 — 开飞行模式也能完成这一步

【② 点呼机读取 + 上报，T+0.1 秒】
  5. ST25DV 被写入 → GPO 引脚电平跳变（硬件门铃响）
  6. 点呼机监听到中断 → I²C 读走邮箱数据 → 发清空指令复位邮箱
  7. 点呼机给数据盖 NTP 校准的时间戳 swipe_time（= 接触机器那一刻）
  8. 点呼机 POST 后端：{ device_id, student_id, swipe_time, ... }
  ※ 是点呼机连后端，不是手机 — 走宿舍 Wi-Fi / 网线

【③ 后端判定，T+0.2 秒】
  9.  查身份：student_id 是注册学生吗？               ✅
  10. 查 session：现在在 running（点呼进行中）吗？     ✅
  11. 查时间窗：swipe_time 在受付时间窗内吗？          ✅
      （以点呼机盖的 swipe_time 判，不以后端收到的时间判 —
       避免「点呼机→后端」网络延迟把卡点学生误判迟到）
  12. 判定 = present（准时）
  13. INSERT 考勤记录（append-only 只追加，不改旧记录）
  14. WebSocket 推老师端  → 座位变绿
  15. WebSocket 推点呼机  → 播报 + 亮灯

【④ 现场反馈，T+0.5-1 秒】
  16. 点呼机喇叭：播报全名（不加「さん」，变速不变调，0.3-0.7 秒）
  17. 点呼机 LED：绿灯
  18. 老师现场：目视 + 听姓名对人脸
  19. 王小明 App 本地显示「已写入点呼机」（不等后端结果，手机不联网）
  20. 王小明走人
```

> **注（sysfeat-06）**：步骤 11 的「受付时间窗」不是固定时刻（例如不是写死的 21:50-22:05）。实装按点呼会话（RollCallSession）的动态受付窗（`on_time_end` 等字段）判定。别把任何示例数字误读成硬编码窗口。
>
> **注（手机端反馈，做法 A）**：步骤 19 手机只确认「数据写进点呼机了」，不等后端判定结果（手机不联网，也没法等）。最终判定结果靠点呼机的绿灯 + 播报 + 老师现场看脸。这是 6-02 拍板的「本地物理确认」方案。

### 3.2 关键技术要素（2026-06-03 架构反转后）

| 要素 | 说明 |
|---|---|
| **CoreNFC** | 苹果的 NFC 读写框架 — iOS App 用它把数据写进 ST25DV |
| **Mailbox 邮箱** | ST25DV 内 256 字节缓存区 — 手机隔空写、点呼机有线读的中转站 |
| **GPO 引脚** | ST25DV 的通知引脚 — 邮箱被写入后电平跳变，当点呼机的「硬件门铃」|
| **I²C 总线** | 点呼机有线读 ST25DV 邮箱用的两线接口 |
| **NTP 校时** | 网络时间协议 — 点呼机连网自动跟标准时间服务器对时，误差几毫秒 |
| **swipe_time** | 点呼机盖的时间戳 = 学生接触机器那一刻，后端拿它判时间窗 |
| **idempotency_key** | 幂等键 — 防同一请求被意外重复提交 |

> **以下要素架构反转后不再用于路径 B（保留作历史 / AC「假设崩」证据）**：
> - ~~BTR（Background Tag Reading 后台读标签）~~ — 手机改成主动写，iOS 不允许后台主动写 → 学生必须开 App 点按钮触发，「碰一下自动唤起」的体验没了
> - ~~Universal Link / AASA / Associated Domains~~ — 那套是为「碰贴纸自动开 App」设计的，现在不需要
> - ~~nonce 一次性随机数~~ — 旧防远程代签机制，手机不联网后作废
> - ECDSA 签名（椭圆曲线数字签名，私钥签+公钥验）— 降级为 **v1.1 可选**（手机写的数据带签名防造假学号），不是 v1.0 必须；详见 §5

### 3.3 时效链条（2026-06-03 重写 — 来自硬件实测时间账）

```
手机写 ST25DV 邮箱:    100-150ms  (CoreNFC 物理握手 + 写入)
点呼机 I²C 读 + 复位:   10-15ms   (GPO 中断 → 读走 → 清空邮箱)
点呼机 → 后端往返判定:  50-80ms   (走宿舍网 / 公网 + 后端查库判时间窗)
点呼机播报全名:        300-700ms (留学生短名 ~300 / 日本人长名 ~700)
总时延:               约 0.58 - 0.99 秒（贴近 1 秒死线，仍达标）
```

> **关键：芯片释放 ≠ 等后端**。ST25DV 邮箱在约 165 毫秒（手机写入 + 点呼机读走清空）就空了，不挡下一个学生。瓶颈只在「邮箱何时变空」，跟后端网络延迟解耦 → 卡点高并发（2 分钟几十人）也不会堵在门口。点呼机靠双线程异步 + 声音掐断撑住，详见 `ROLLCALL_DEVICE_DESIGN_LOG.md`。

### 3.4 ~~Nonce 时效防御的数学~~（2026-06-03 作废）

> ⚠️ 本节整套（nonce 每 10 秒刷新 + 复制 URL 攻击窗口数学）是「手机读贴纸 URL、自己远程 POST 后端」时代的防御。架构反转后手机不联网、不存在「手机 POST 后端」这回事 → 这套防御**不再需要**（是简化，不是缺口）。新架构下的防代刷分析见 §5。
>
> 〔历史原文保留作 AC「假设崩」证据〕：nonce 生成速率每 10 秒 1 个 × 4 台 = 0.4 个/秒；有效窗口 10 秒；复制者攻击窗口最多 10 秒；现实更短因回房间要 1-2 分钟 → nonce 早过期；防御生效率近似 100%。

## 4. 路径 B-Android — 同写 ST25DV ✅（2026-06-03 架构反转同步）

> ⚠️ **跟 iOS 一样反转**：Android 也从「读贴纸 URL → 自动开 App → 手机联网 POST 后端」改成「App 主动把身份数据写进 ST25DV 邮箱 → 点呼机读走上报」。所以下面 §4.1 / §4.2 / §4.4 里的 App Links / `assetlinks.json` / `autoVerify`（那套「碰链接自动开 App」机制）跟 iOS 的 BTR / AASA 一样**作废**；Android 改用系统 NFC 写入能力（前台、学生点按钮触发）。**§4.3 的 APK 自建分发 + keystore 备份不受影响，保留有效。**

**决策来源**：2026-04-20 议题 B（raw §B-B.1-B-B.15）— 〔机制部分 6-02 反转后作废，保留作 AC 证据；APK / keystore 仍有效〕

### 4.1 机制对应（iOS vs Android）

> ⚠️ 下面 §4.1 表 + §4.2 + §4.4 描述的是**旧的「读 URL」机制**（App Links / assetlinks.json / autoVerify / BTR），2026-06-02 反转后**全部作废**，保留作历史。新机制 = Android App 主动写身份数据进 ST25DV 邮箱（前台触发），跟 iOS 一样。

| 项目 | iOS | Android |
|---|---|---|
| 后端配置文件 | `apple-app-site-association` | **`assetlinks.json`** |
| 托管路径 | `/.well-known/apple-app-site-association` | **`/.well-known/assetlinks.json`** |
| App 配置 | `Associated Domains` | `AndroidManifest.xml` + `IntentFilter android:autoVerify="true"` |
| 后台唤起名称 | BTR (Background Tag Reading) | **App Links** |
| 最低支持版本 | iOS 14+ 推荐 | **Android 10+**（议题 B 拍板）|

### 4.2 贴纸共用

~~**Android 读同一张 ST25DV16K + 同一个 URL**~~ → 反转后：Android 也是 App 主动**写**身份数据进同一张 ST25DV 的 Mailbox 邮箱（前台、点按钮触发）。AASA / assetlinks.json 那套作废。

### 4.3 Android 额外考量

- **APK 自建分发**：首次安装有"未知来源"警告（Android 8+ 每浏览器独立授权）
- **分发页面**：itsuki 计划搭"宿舍综合官网"（`dmsd.otogi2025.com`）承载 APK + AASA + assetlinks.json → TODO 已记
- **keystore 备份**：Mac + 服务器加密 + 纸质密码（毕业传承考量，议题 B 定稿）

### 4.4 ~~流程差异（相对 iOS）~~〔旧读 URL 机制，反转后作废〕

- 首次 tap 贴纸：Android 可能弹"用哪个 App 打开此链接？"菜单（assetlinks.json 验证成功后不弹）
- 系统权限：`<uses-permission android:name="android.permission.NFC" />` 是 install-time 授予，**无运行时弹窗**（比 iOS 简单）

## 5. 攻击路径 + 防御

> ⚠️ **2026-06-03 整章状态：旧方案作废，待重新设计**
>
> 下面 §5.1-5.4 整套攻击/防御分析，是「手机读贴纸 URL、自己联网远程 POST 后端」时代写的，核心是 nonce + ECDSA 验签防远程代签。架构反转后**手机不联网、不存在「手机 POST 后端」这回事** → 这套大部分作废。**保留原文作 AC「假设崩」证据链，不删。**
>
> **新架构下防代刷怎么想**（`hardware_design.md §2.3` itsuki 6-02 已厘清的方向，待完整落地）：
> 1. 攻击面变小：复制学号 / 借卡 / 借手机本质都是「拿别人凭证替刷」，**必须到现场**（NFC 近场几厘米）→ 靠现场播报姓名 + 老师看脸防（4-12 既定设计）+ v2.0 人脸识别自动化。这类攻击路径 A 实体卡一样有，不是反转新增的。
> 2. 真正要做的传输安全（跟反转无关、本来就要做）：**点呼机↔后端用 WebSocket（后端推指令）+ HTTP（上传 / 下载）双通道，都要加密 + 点呼机持设备密钥认证** → 防有人冒充点呼机、防截获重发请求。「防重放」属于这一层、点呼机参与，不在手机侧。
> 3. 可选增强（优先级低）：手机写进邮箱的数据带签名防造假学号，v1.1 可议。
> 4. 实体卡 NTAG215 的 UID 可克隆是老问题（TODO 已列 NTAG424 DNA 替换），跟反转无关。
>
> → 完整的新攻击场景分析，待 itsuki 给方向后重写本章。

### 5.1 攻击场景 α — 本人复制 URL 在房间代签（ST25DV 防御生效）

```
Step 1. A 用 NFC Tools 读真贴纸
        → 拿到 "https://.../checkin?device=DEV001&nonce=X7Kp9wQ2fB"

Step 2. A 回房间，写到自己的空白 NTAG215

Step 3. 【关键】10 秒过去
        → 点呼机刷新贴纸为 nonce=Y8Lq5xR1Kc
        → 后端 X7Kp9wQ2fB 标记过期

Step 4. A 在房间 tap 假贴纸
        → Tomoshibi App 被 BTR 唤起
        → POST 带 nonce=X7Kp9wQ2fB（旧）

Step 5. 后端校验
        → nonce 过期 → 返回 INVALID_NONCE

Step 6. 代签失败 ✅ （防御生效）
```

### 5.2 攻击场景 β — 甲替乙代签（签名 + 单设备防御生效）

甲有甲自己的 App + 甲自己的私钥，生成的 signature 只对甲的账户有效。甲无法以"乙的身份"签到。✅

### 5.3 攻击场景 γ — URL 泄漏到公网（无账号防御生效）

第三方从公网拿到 URL，但没有 Tomoshibi App / 没注册账户 → 签到流程走不通。✅

### 5.4 议题 D 补全（2026-04-20）

| # | 攻击 | 防御 |
|---|---|---|
| 同 UID 并发 4 台 tap | `session_id + student_id + idempotency_key` 幂等 | 后端唯一判定者 |
| 异常时间签到（21:30 / 23:00）| `SESSION_NOT_RUNNING` / `WINDOW_CLOSED` | spec §5.2-5.3 |
| 设备指纹伪造 | 入学日老师面签 + ECDSA 签名（私钥硬件级）| 议题 C |
| 换机欺诈 | 任意设备签名即可（取消硬限制），旧密钥自动作废 | 议题 C |
| 制度层兜底 | 老师现场 + 纸质补签 + 次日后端录入 | 4-19 |

### 5.5 异常行为检测（推迟 M3+）

议题 D-2 决策：**推迟到 v0.6.0+** 实施。场景：

## 6. 失败场景 + 兜底

> **2026-06-03 架构反转后重写**：手机不联网 → 一大批「手机没网 / 老机型锁屏 / BTR 失效」场景直接消失。删掉过时场景，补点呼机侧的新场景。

| 场景 | 表现 | 兜底方案 |
|---|---|---|
| **手机没网（流量卡 / 飞行模式）** | ✅ **不受影响** | 手机本来就不联网，飞行模式也能签到 — 这正是反转要解决的痛点 |
| iPhone 低电量模式 (<20%) | NFC 写入可能失效 | App 内重试 + 卡路径兜底 |
| 学生没开 App 就碰 | 没反应（手机主动写要 App 前台触发）| 提示「先开 App 点签到」+ 卡路径兜底 |
| 贴纸被撕坏 / 脏了写不进 | 手机碰了没反应 | 每台点呼机备用贴纸 2 张（都接同一点呼机）+ 卡路径兜底 |
| **点呼机↔后端断网** | 点呼机 POST 失败 + 后端长连接断 | **离线降级**：① 点呼机侧本地放绿灯让学生通行 + 存树莓派本地、恢复后批量补传；② 后端发现长连接断 → 推老师平板告警「点呼机已离线」→ 老师确认后进手动模式逐个改判。补传与手动判定撞同一学生时老师手动优先。详见 `ROLLCALL_DEVICE_DESIGN_LOG.md §6.1` + `BACKEND_DESIGN_LOG.md §5.8` + `WEB_DESIGN_LOG.md §5.8A` |
| 点呼机断电 | 该台完全失效 | 其他 3 台可用 / 纸质补签 |
| 老师没按"点呼开始"按钮 | 所有签到返回 SESSION_NOT_RUNNING | 老师到场第一件事 |

## 7. 账号规则（2026-04-20 议题 C 修订 — 推翻 4-19 "一设备一账号"）

**原 4-19 G2 规则**：一设备一账号 + 换机必须老师审批 + 一次性换机码

**原问题**（itsuki 4-20 质疑）：
> "做不到帮顶设备的话，这点就取消，就算没有绑定设备也不会有什么改变"

**防御有效性分析**（议题 C §C.2）：
| # | 防御目的 | 绑定设备能防吗？|
|---|---|---|
| 1 | 多设备并发签到 | ❌ 幂等就能防 |
| 2 | 借手机代签 | ❌ 私钥在借方设备里 |
| 3 | 账号盗用 | ❌ 盗用者可走注册流程 |
| 4 | 一人刷多次 | ✅ 但幂等更直接 |

→ 4 项防御中仅 1 项成立，且可被幂等替代 → **规则的严密性 ≠ 防御的有效性**。

### 7.1 新规则（议题 C 方案 A + C-3）

**注册流程**（入学第一天）：
1. 新生下载 Tomoshibi App
2. 填姓名 + 生日 + 性别
3. App 显示一个二维码（含一次性注册 token）
4. **老师扫码 → 屏幕显示"张三 / 女 / 2008-03-15"**
5. 老师确认"是张三本人" → 点击确认
6. App 生成 ECDSA 密钥对（存 Keychain/Keystore）→ 注册完成

**日常签到**：任意已激活设备 + 学生私钥签名 → 后端验签 → 接受

**换机 / 重装**：
- 学生在新设备登录（姓名+生日+性别+PIN/其他二次验证）
- App 生成新密钥对，提交新公钥
- 旧设备密钥自动作废
- **不需要老师**

**核心防御**（2026-06-03 架构反转后调整）：
- 老师现场监督（主要）+ 现场播报姓名对脸
- ~~ST25DV 动态 nonce（路径 B 防远距离代签）~~ — 作废（手机不联网，无远程代签这回事）
- ECDSA 签名 — 降级为 **v1.1 可选**（手机写进邮箱的数据带签名防造假学号）
- 点呼机↔后端传输安全（WebSocket + HTTP 双通道加密 + 设备密钥）— 防冒充点呼机 / 防重放
- session 幂等

**账号盗用防御新锚点**：入学日老师面签 = 整个账号体系的唯一身份验证环节。

## 8. 错误码区分（2026-04-20 议题 D 补全 backlog S4）

### 8.1 UID 相关错误码

| 错误码 | 触发场景 | 业务含义 | 点呼机反馈 |
|---|---|---|---|
| `UNKNOWN_UID` | UID 从未注册过 | 空白卡 / 伪造卡 / 其他学校的卡 → **审计重点** | 红灯 + "未注册卡，请联系管理员" |

| `ALREADY_RUNNING` | 老师按"点呼开始"时已在 running 中 | 老师端提示 |
