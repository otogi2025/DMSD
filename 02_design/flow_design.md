## 1. 总览

### 1.1 三条签到路径共存（G2 决策 4-19）

| 路径 | 触发者 | 设备 | 学生操作步数 |
|---|---|---|---|
| **路径 A** | NFC 卡 | 点呼机 PN532 读头 | 1 步（贴卡）|
| **路径 B-iOS** | iPhone | 点呼机外贴 ST25DV16K 动态贴纸 | 2 步（拿出手机 + tap）|
| **路径 B-Android** | Android 手机 | 同一张 ST25DV16K 贴纸 | 2 步（同上，待议题 B 细化）|

**学生可同时持有卡 + 手机，日常任选一个路径**。每时间窗内一个学生只能签到一次（幂等规则 4-19）。

### 1.2 共同前提

- **服务器是唯一判定者**（架构原则 4-15）
- 客户端本地时间不参与判定
- 每个 `device_id` 必须在 `DEVICE_REGISTRY` 注册后才能签到
- 老师现场目视监督（防代签的人防补偿 spec §5.1.3）

## 2. 路径 A — NFC 卡 tap

详见 `RollCall_Spec.md §5.1.1`。本文不重复，引用链路：

```
学生卡 ──贴近──> 点呼机 PN532 读头
  → 1. 读 UID
  → 2. POST /api/v1/checkin {device_id, uid, ts_local}
  → 3. 后端校验 + 判定 + 写 attendance_event
  → 4. WebSocket 推老师端 + 点呼机
  → 5. 点呼机播报 + 亮灯
```

## 3. 路径 B-iOS — iPhone BTR + 动态贴纸 ✅

### 3.1 端到端流程图

```
┌──────────────────────────────────────────────────────────────────┐
│ 【后台循环，每 10 秒一次】                                          │
│                                                                  │
│   点呼机 (Pi 3A+) ──Python 循环──> 后端                            │
│           │         POST /api/v1/nonce { device_id: "DEV001" }   │
│           │                              │                        │
│           │         <──── { nonce: "X7Kp9wQ2fB", ttl: 10 } ───     │
│           ▼                                                       │
│   通过 I²C 写入 ST25DV16K:                                         │
│   URL = "https://dmsd.otogi2025.com/checkin                       │
│         ?device=DEV001&nonce=X7Kp9wQ2fB"                          │
└──────────────────────────────────────────────────────────────────┘

┌──────────────────────────────────────────────────────────────────┐
│ 【学生 tap，T=0】                                                  │
│                                                                  │
│   1. 王小明拿出 iPhone（已装 Tomoshibi App、已注册、已绑定设备）           │
│   2. 贴近 ST25DV16K 贴纸（距离 2-5cm）                              │
│   3. iOS BTR 读到 NDEF URL（无需打开 App / 无需解锁 iOS 14+）        │
│   4. iOS 查缓存的 AASA 文件 → 匹配 Tomoshibi App 的 Associated Domains   │
│   5. 【iOS 直接启动 Tomoshibi App】到签到页，不弹通知，不开 Safari        │
│   6. App 从 URL 参数拿到 device_id=DEV001, nonce=X7Kp9wQ2fB         │
└──────────────────────────────────────────────────────────────────┘

┌──────────────────────────────────────────────────────────────────┐
│ 【App 签到，T+1 秒】                                                │
│                                                                  │
│   7. App 用本机 iOS Keychain 私钥做 ECDSA 签名                      │
│       signature = sign(student_id || device_id || nonce ||        │
│                        session_id || ts_local)                    │
│                                                                  │
│   8. POST /api/v1/checkin                                          │
│       { student_id, device_id, nonce, signature,                  │
│         ts_local, idempotency_key }                               │
└──────────────────────────────────────────────────────────────────┘

┌──────────────────────────────────────────────────────────────────┐
│ 【后端判定，T+1-2 秒】                                               │
│                                                                  │
│   9. 校验 nonce 有效性：是 10 秒内发给 DEV001 的吗?      ✅          │
│   10. 验签：用学生注册时存的公钥验 signature             ✅          │
│   11. 查 device：DEV001 在 DEVICE_REGISTRY active 吗？   ✅          │
│   12. 查绑定：王小明绑了 DEV001 吗？                      ✅          │
│   13. 查 session：现在在 running 吗？                     ✅         │
│   14. 查时间窗：当前时间在 21:50-22:05 吗？                ✅         │
│                                                                  │
│   15. 判定 = present（准时）                                        │
│   16. INSERT attendance_event（append-only）                       │
│   17. WebSocket 推老师端  → 座位变绿                                │
│   18. WebSocket 推点呼机  → 播报 + 亮灯                             │
│   19. HTTP 响应给 App     → 显示"签到成功"                          │
└──────────────────────────────────────────────────────────────────┘

┌──────────────────────────────────────────────────────────────────┐
│ 【反馈，T+2-3 秒】                                                  │
│                                                                  │
│   20. 王小明 iPhone 屏幕："签到成功，准时"                            │
│   21. 点呼机喇叭："王小明 准时"                                       │
│   22. 点呼机 LED：绿灯                                               │
│   23. 老师现场：目视 + 听姓名对人脸                                   │
│   24. 王小明走人                                                    │
└──────────────────────────────────────────────────────────────────┘
```

> **注（sysfeat-06）**：上図ステップ 14 の「21:50-22:05」は説明用の例示値。実装では判定窓口は固定時刻ではなく、点呼セッション（RollCallSession）の動的な受付時間窓（`on_time_end` 等）で判定する。図の数字をハードコード窓口と誤読しないこと。

### 3.2 关键技术要素

| 要素 | 说明 |
|---|---|
| **BTR** | Background Tag Reading — iOS 11+ 后台自动扫描 NDEF 标签的能力 |
| **NDEF** | NFC Data Exchange Format — NFC 标签的标准数据格式 |
| **Universal Link** | Apple 的链接跳 App 机制 — 访问 HTTPS 域名直接唤起对应 App |
| **AASA 文件** | `apple-app-site-association` — 后端声明"此域名属于 X App" |
| **Associated Domains** | iOS App 的配置项 — 声明"我可以处理 X 域名的链接" |
| **ECDSA 签名** | 椭圆曲线数字签名 — 用私钥签 + 公钥验，防伪造 |
| **nonce** | 一次性随机数 — 10 秒内有效，每次动态生成，防重放 |
| **idempotency_key** | 幂等键 — 防同一请求被意外重复提交 |

### 3.3 时效链条

```
点呼机:    nonce 每 10 秒刷新   (I²C 写入)
贴纸:      nonce 每 10 秒变化   (被动存储)
后端:      nonce 10 秒内有效   (状态表)
学生 tap:  BTR 启动 App ~1 秒  (系统级处理)
App POST:  ~200ms             (网络请求)
后端判定:  ~50ms              (内存 + DB)
总时延:    T=0 到反馈 ~2-3 秒
```

### 3.4 Nonce 时效防御的数学

- nonce 生成速率：每 10 秒 1 个 × 4 台点呼机 = 0.4 个/秒
- nonce 有效窗口：10 秒
- 任何时刻每台点呼机有效 nonce 数：1 个
- 复制者攻击窗口：**最多 10 秒**（从真 tap 到代签完成）
- 现实攻击窗口：更短，因为要 A 先回房间（至少 1-2 分钟）→ nonce 早过期

**防御生效率 = 近似 100%**（物理现实中无法 < 10 秒从点呼机前回到房间完成代签）

## 4. 路径 B-Android — App Links ✅

**决策来源**：2026-04-20 议题 B（raw §B-B.1-B-B.15）

### 4.1 机制对应（iOS vs Android）

| 项目 | iOS | Android |
|---|---|---|
| 后端配置文件 | `apple-app-site-association` | **`assetlinks.json`** |
| 托管路径 | `/.well-known/apple-app-site-association` | **`/.well-known/assetlinks.json`** |
| App 配置 | `Associated Domains` | `AndroidManifest.xml` + `IntentFilter android:autoVerify="true"` |
| 后台唤起名称 | BTR (Background Tag Reading) | **App Links** |
| 最低支持版本 | iOS 14+ 推荐 | **Android 10+**（议题 B 拍板）|

### 4.2 贴纸共用

**Android 读同一张 ST25DV16K + 同一个 URL**。后端需同时托管两个文件（iOS 的 AASA + Android 的 assetlinks.json）。

### 4.3 Android 额外考量

- **APK 自建分发**：首次安装有"未知来源"警告（Android 8+ 每浏览器独立授权）
- **分发页面**：itsuki 计划搭"宿舍综合官网"（`dmsd.otogi2025.com`）承载 APK + AASA + assetlinks.json → TODO 已记
- **keystore 备份**：Mac + 服务器加密 + 纸质密码（毕业传承考量，议题 B 定稿）

### 4.4 流程差异（相对 iOS）

- 首次 tap 贴纸：Android 可能弹"用哪个 App 打开此链接？"菜单（assetlinks.json 验证成功后不弹）
- 系统权限：`<uses-permission android:name="android.permission.NFC" />` 是 install-time 授予，**无运行时弹窗**（比 iOS 简单）

## 5. 攻击路径 + 防御

### 5.1 攻击场景 α — 本人复制 URL 在房间代签（ST25DV 防御生效）

```
Step 1. A 用 NFC Tools 读真贴纸
        → 拿到 "https://.../checkin?device=DEV001&nonce=X7Kp9wQ2fB"

Step 2. A 回房间，写到自己的空白 NTAG215

Step 3. 【关键】10 秒过去
        → 点呼机刷新贴纸为 nonce=Y8Lq5xR1Kc
        → 后端 X7Kp9wQ2fB 标记过期

Step 4. A 在房间 tap 假贴纸
        → Tomoshibi App 被 BTR 唤起
        → POST 带 nonce=X7Kp9wQ2fB（旧）

Step 5. 后端校验
        → nonce 过期 → 返回 INVALID_NONCE

Step 6. 代签失败 ✅ （防御生效）
```

### 5.2 攻击场景 β — 甲替乙代签（签名 + 单设备防御生效）

甲有甲自己的 App + 甲自己的私钥，生成的 signature 只对甲的账户有效。甲无法以"乙的身份"签到。✅

### 5.3 攻击场景 γ — URL 泄漏到公网（无账号防御生效）

第三方从公网拿到 URL，但没有 Tomoshibi App / 没注册账户 → 签到流程走不通。✅

### 5.4 议题 D 补全（2026-04-20）

| # | 攻击 | 防御 |
|---|---|---|
| 同 UID 并发 4 台 tap | `session_id + student_id + idempotency_key` 幂等 | 后端唯一判定者 |
| 异常时间签到（21:30 / 23:00）| `SESSION_NOT_RUNNING` / `WINDOW_CLOSED` | spec §5.2-5.3 |
| 设备指纹伪造 | 入学日老师面签 + ECDSA 签名（私钥硬件级）| 议题 C |
| 换机欺诈 | 任意设备签名即可（取消硬限制），旧密钥自动作废 | 议题 C |
| 制度层兜底 | 老师现场 + 纸质补签 + 次日后端录入 | 4-19 |

### 5.5 异常行为检测（推迟 M3+）

议题 D-2 决策：**推迟到 v0.6.0+** 实施。场景：
- 5 分钟内 >5 次失败签到 → 标记审计
- 同 session 跨点呼机异常切换
- 签到时间集中异常（例如 21:51 就 30 人 tap）

## 6. 失败场景 + 兜底

| 场景 | 表现 | 兜底方案 |
|---|---|---|
| iPhone 低电量模式 (<20%) | BTR 静默失效 | App 内"手动 tap 签到"按钮（前台读模式）|
| iPhone 7/8/X 老机型 | 必须锁屏 tap | 学生培训 + 卡路径兜底 |
| 飞行模式 | NFC 关闭 | 学生自助解除 |
| 手机没网（WiFi/4G 都失败）| App 启动但 POST 失败 | 走卡路径 / 纸质补签 |
| 宿舍 WiFi 拥堵（120 人并发）| 后端 / 网络过载超时 | 后端限流 + App 重试队列 + 纸质补签 |
| 贴纸被撕坏 / 脏了读不到 | 学生手机完全无反应 | 每台点呼机备用贴纸 2 张（都绑同 device_id）+ 卡路径兜底 |
| iOS 26 系统级 BTR bug | 签到失败率异常 | 跟踪苹果修复；先按 iOS 18 基线开发 |
| nonce 刷新瞬间 tap | 小概率读到旧 nonce | 后端保留上一代 nonce 2 秒容差 + idempotency_key |
| 点呼机断电 | 该台完全失效 | 其他 3 台可用 / 纸质补签 |
| 老师没按"点呼开始"按钮 | 所有签到返回 SESSION_NOT_RUNNING | 老师到场第一件事 |

## 7. 账号规则（2026-04-20 议题 C 修订 — 推翻 4-19 "一设备一账号"）

**原 4-19 G2 规则**：一设备一账号 + 换机必须老师审批 + 一次性换机码

**原问题**（itsuki 4-20 质疑）：
> "做不到帮顶设备的话，这点就取消，就算没有绑定设备也不会有什么改变"

**防御有效性分析**（议题 C §C.2）：
| # | 防御目的 | 绑定设备能防吗？|
|---|---|---|
| 1 | 多设备并发签到 | ❌ 幂等就能防 |
| 2 | 借手机代签 | ❌ 私钥在借方设备里 |
| 3 | 账号盗用 | ❌ 盗用者可走注册流程 |
| 4 | 一人刷多次 | ✅ 但幂等更直接 |

→ 4 项防御中仅 1 项成立，且可被幂等替代 → **规则的严密性 ≠ 防御的有效性**。

### 7.1 新规则（议题 C 方案 A + C-3）

**注册流程**（入学第一天）：
1. 新生下载 Tomoshibi App
2. 填姓名 + 生日 + 性别
3. App 显示一个二维码（含一次性注册 token）
4. **老师扫码 → 屏幕显示"张三 / 女 / 2008-03-15"**
5. 老师确认"是张三本人" → 点击确认
6. App 生成 ECDSA 密钥对（存 Keychain/Keystore）→ 注册完成

**日常签到**：任意已激活设备 + 学生私钥签名 → 后端验签 → 接受

**换机 / 重装**：
- 学生在新设备登录（姓名+生日+性别+PIN/其他二次验证）
- App 生成新密钥对，提交新公钥
- 旧设备密钥自动作废
- **不需要老师**

**核心防御**（不变）：
- 老师现场监督（主要）
- ECDSA 签名（私钥硬件级保护）
- ST25DV 动态 nonce（路径 B 防远距离代签）
- session 幂等

**账号盗用防御新锚点**：入学日老师面签 = 整个账号体系的唯一身份验证环节。

## 8. 错误码区分（2026-04-20 议题 D 补全 backlog S4）

### 8.1 UID 相关错误码

| 错误码 | 触发场景 | 业务含义 | 点呼机反馈 |
|---|---|---|---|
| `UNKNOWN_UID` | UID 从未注册过 | 空白卡 / 伪造卡 / 其他学校的卡 → **审计重点** | 红灯 + "未注册卡，请联系管理员" |
| `REVOKED_UID` | UID 曾注册但作废 | 学生拿错旧卡（毕业/丢失/管理员禁用）→ **运营提示** | 红灯 + "此卡已作废" |
| `UNKNOWN_DEVICE` | iPhone/Android device_id 未注册 | App 客户端未走完注册流程 | App 显示"设备未注册" |

### 8.2 时间窗相关错误码

| 错误码 | 触发场景 | 响应 |
|---|---|---|
| `SESSION_NOT_RUNNING` | 老师没按"点呼开始" / 时间窗未开 | 点呼机 "等待中，请稍候" |
| `WINDOW_CLOSED` | 时间窗已过 | 点呼机 "点呼已结束" |
| `ALREADY_RUNNING` | 老师按"点呼开始"时已在 running 中 | 老师端提示 |

### 8.3 签名 / nonce 相关错误码

| 错误码 | 触发场景 | 响应 |
|---|---|---|
| `INVALID_SIGNATURE` | ECDSA 验签失败 | 后端拒绝 + 审计 |
| `INVALID_NONCE` | nonce 过期（URL 被复制）| 后端拒绝（防御生效）|
| `DUPLICATE_CHECKIN` | 同学生同 session 重复 | silently ignore + 日志 |
