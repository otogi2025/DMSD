## 1. 为什么做(問題発見)

## 2. 遇到了什么困难(問題意識)

### 困难 1: 默认日语漂移(自己重复犯)

CC 重写 system_features.md v0.2 时,**继承了旧版的日语风格** — 章节标题 / 表头 / 说明文字大量日语。itsuki 当场指出:

> 「为什么会有那么多日语?」

这是**已经被纠正过多次**的"做日语 UI 时整段日语漂移"问题(memory `feedback_default_chinese_response.md`)。再犯一次。

**解决**: 当场承认 + 完整重写中文骨架,只保留**专有名词**(寮監 / 出寮届 / 帰省 / 学習 等)+ **老师原文 evidence** 的日语。

### 困难 2: 双轨版本号容易混淆

itsuki 看到 `system_features.md v0.2` 标记后疑问:

> 「v0.2 为什么是 v0.2?我系统版本不是 0.2,这个意思是这个文件是第二个版本?所以文件做出修改后不是覆盖而是迭代?然后还独立于系统版本?」

itsuki 完全合理的疑问 — **文件级版本号 + 项目级版本号 双轨**违反单源真值原则。

**解决**: itsuki 拍板"并不一定要单版本号"(灵活),CC 决定**删除文件级版本号**:
- git 已记录每次改动 = 单源真值
- 项目级版本号(SemVer)在 CHANGELOG 顶部 + WIP 头部 双源同步
- 文件级 v0.x 是第三套版本号 = 多余 + 易漂移 → 删

### 困难 3: 不知道什么时候 bump 项目版本

itsuki 原话:

> 「我也不知道什么时候迭代版本比较好,我修改了一个两个文件要迭代吗?还是要修改很多才迭代之类的我也不知道。看你。」

→ 触发 CC 自己读 `00_admin/版本管理SOP.md` §2 决策树自主判断。

**解决**: 跑 SOP §2 决策树命中三重(spec 主体 + 设计大重写 + 03_dev 大重组)→ Minor bump v0.5.0 → v0.6.0,CC 自主决定 + 同步 6 处必改文件 + commit。

### 困难 4: demo 通过后的"临时 / 长期"边界要建立

itsuki 拍板新规则:

> 「demo 的文件单独放在一个文件夹里,然后具体可以用到我的正式版的东西就复制一份就好了,demo 的文件不要动。」

之前 demo round3 = "当前唯一 active" 的理解被推翻 — 应该 demo 锁定 / v1 是新文件夹。这是从"demo 通过即 v1 起点"到"demo 锁定 + v1 从 demo 复制"的边界明确化。

## 3. 怎么解决的(問題解決)

### 解法 1: 三层档案分层方针

| 层 | 档案 | 写什么 |
|---|---|---|
| 1 共用真值 | `02_design/system_features.md` | 业务规则 / 时间窗 / 数据模型 / 角色权限 / R1-R4 |
| 2 iOS 専属 | `IOS_DESIGN_LOG.md` | App 视觉 / flow / Phase |
| 3 Web 専属 | `WEB_DESIGN_LOG.md` | Web 页面 / Ryō tokens / 老师动线 |

CC 用菜谱类比解释给 itsuki: 共用 = 食材清单 + 基本规则;iOS / Web = 各自实操步骤。只看一边会漏掉"盐多少克"这种共用规则。

### 解法 2: 03_dev demo/v1 分离

```
03_dev/
├── backend/    {demo/(锁定), v1/(README 占位)}  + README.md 顶层
├── teacher_web/ {demo/(锁定), v1/(README 占位)} + DESIGN_BRIEF + WEB_DESIGN_LOG
└── student_ios/ {demo/(锁定), v1/(README 指向独立 repo)} + IOS_DESIGN_LOG + DESIGN_BRIEF + README
```

210+ 文件 git mv,4 个新 README 占位,LATEST.md / 文件结构指南.md / sync-ios-refs.sh 同步路径。

### 解法 3: RollCall_Spec.md 5 处时序修订

老师没明说但 itsuki 推断的新规则:

| 修订 | 旧规则 | 新规则 |
|---|---|---|
| §4.2 时刻表 | "老师 -3min 按" | "应开始 -5min / 兜底 -3min / 准时截止起算迟到" |
| §5.4 窗口 | 老师早按 → 整窗口平移(准时截止也提前) | **窗口固定**,老师早按只激活签到通道 |
| §5.5 自动开始 | `window_start` 自动 | `on_time_end - 3min` 自动 |
| §5.6 结束 flow | 按结束 → 直接回主页 | **跳「点呼総結」中层页**(4 区块: 缺席 / 迟到 / 特殊要求 / 外宿)→ 再点回主页 |
| 附录 A.4 | 平移规则反直觉(疑问)| ✅ CLOSED |

### 解法 4: system_features.md 中文骨架大重写

357 → 830 行,以老师 38 条 + Q1-12 + R1-R4 + 4 砍/留 为锚:

- §8 数据模型扩充(applications / study / events / bus / meals / teachers + R4 CHECK)

### 解法 5: 让 CC 主动识别"档案体系元思考"(规范化未来)

itsuki 原话:

> 「为了未来就算我不说 cc 也会主动这样记录,记得写到记录规范里。」

→ 在 `CLAUDE.md § 触发清单` 加一条:**"档案体系 / 文件管理规范 / 目录结构分层 等元思考决策"**(方法论级,~1500 字详细记录,AC 价值高)。`CLAUDE_CODE_记录指南.md §3.1` 同步加。

## 4. 学到了什么(自己認識)

### 4.1 整理一次不够,要建立规范

itsuki 原话:

> 「之前文件太分散,就算整理了时间久了就会乱。」

→ 一阶治理(具体清理)→ 二阶治理(建立规则)→ 三阶治理(让 AI 主动按规则识别)的递进。

### 4.2 单源真值原则(双轨版本号是反例)

文件级版本号 + 项目级版本号 双轨 = 必然漂移。git 已经是单源(每次 commit 是一次迭代),不需要文件再标 v0.x。

### 4.3 demo 通过后的战略转换

从"做出来给老师看"(战术: 快 + 一次性)到"做得能长期维护"(战略: 慢 + 边界明确)。demo 临时性必须主动收敛,否则会变成永久债务。

### 4.4 默认中文是已经犯过的错(再犯)

CC 在做日语 UI 项目时容易整段日语漂移,即使被纠正多次。**根本解法 = memory + CLAUDE.md 双层规则 + 自检触发**。

### 4.5 自主判断版本 bump

第一次完整跑 SOP §2 决策树 + §3 五步 + §4 必改 6 处。从"itsuki 拍板 bump"到"CC 自主判断 bump"的递进。CC 现在能自己读 SOP / 命中决策树 / 跑联动文件清单。

## 5. 失败的地方 / 还能更好(失敗・改善余地)

### 5.1 默认日语漂移(再次)

虽然 memory `feedback_default_chinese_response.md` 已经写了多次,但**重写 system_features.md 时还是没自检过滤掉日语骨架**。改进: 重写大文件前**先自检语言基调**(章节标题 / 表头 / 主体说明 是不是中文)。

### 5.2 文件级版本号留了一段时间没意识到问题

`v0.1` 在 system_features 顶部写了一周(2026-04-23 → 2026-04-29),CC 没主动质疑这种双轨设计,直到 itsuki 问出来。改进: 见到任何"文件内部版本号"应该自动质疑"是不是和项目版本号双轨漂移"。

### 5.3 SOP 6 处必改的"AC 叙事"和"raw log"是同时写的(本会话末尾),效率不够高

理想流程是 bump 前每次 commit 累积内容到 raw log,bump 时只是 close。本次是 bump 时一次性补 ~2000 字 §13 + 1000 字 AC 叙事,工作量集中。
