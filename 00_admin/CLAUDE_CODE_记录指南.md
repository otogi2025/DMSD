## 3. 对话中：碎片 dump

### 3.1 触发捕捉的范围（v3 比 v2 扩大）

下面任何一类发生都 dump：

- 代码/架构/文件结构的**改变**
- **档案体系 / 文件管理规范 / 目录分层设计** 等"元思考"决策 — itsuki 想"以后怎么管这堆文件 / 怎么不让档案漂"时（方法论级，**默认详细记录** ~1500 字，按 §3.4.2 篇幅指引最高档；AC 视角价值很高，对应 #3 问题解决 + #4 自己认识）
- 任何**决策**（哪怕微小）
- itsuki 说出的**想法、看法、反思、怀疑**
- **问题**：bug、卡点、不理解的概念
- **学习**：新概念、新语法、新工具
- 和真人讨论的**访谈**要点
- CC 写出 itsuki 当时**不完全理解**的代码
- CC 和 itsuki **意见不一致**
- itsuki **纠正** CC

**不捕捉**：纯执行类操作（rm、mv、重启等）、寒暄、和项目无关的话题。

### 3.2 标准话术

识别到后先问：
```
刚才这个我记一下到 05_logs/raw/YYYY-MM-DD.md 好吗？
归类：[标签] / 可能对应 AC 核心问题 #X
```

itsuki 同意 → append 到当日文件末尾。

### 3.3 碎片格式（append 到当日文件）

```markdown
## HH:MM [标签] 一句话主题
（正文：现象 / 对话 / 代码片段 / 想法）

**itsuki 原话**：
> "..."（尽量保留原话，不润色）

**#AC候选**（CC 按 §6 判断加不加）
**核心问题**: #1 / #2 / #3 / #4 / #5（CC 建议）
```

**标签建议**（自由扩展）：`[DMSD] [学习] [访谈] [决策] [方法论决策] [问题] [分歧] [闪念-补] [碎片]`

> `[方法论决策]` 用于"关于怎么做事"的 meta-决策，例如"把整理动作当审查 trigger"。与 `[决策]`（技术/产品决策）区分。

> 上述是**最低格式（下限）**。按重要度展开的详细度要求见 §3.4。

### 3.4 记录详细度要求（按重要度展开）

§3.3 的短模板是**下限**，不是上限。碎片在"决策快照"和"AC 素材"之间的差别，就是详细度。

**raw 文件是素材，不是成品**。成品（志望理由书 / 自我推荐书 / 面试回答）要经 raw → 月度回顾 → 第 2 层候选 → 第 3 层成品多轮提炼。如果 raw 只留"决策结论"，提炼时就没有原材料 —— "我取消了分阶段"没法扩展成"我发现卡和 App 耦合不可分，推翻了自己的分阶段假设"。

AC 入試的评分标准是 **"过程 > 结果"**。考官想看到：
- **问题发现** — 发现了什么不对？动摇的契机？
- **问题解决** — 中间考虑了哪些选项？选 A 拒绝 B 的理由？
- **自己認識** — 过程中学到了什么？在哪里纠正了自己？

这些都是**过程**，不是**结论**。

#### 3.4.1 每条碎片应含的 5 模块（重要度高时补全）

除了 §3.3 的最低字段，以下 5 模块按重要度补充：

1. **背景 / 触发** — 讨论是怎么起来的？之前的 context 是什么？
2. **问题发现 → 问题解决的过程** — 谁意识到什么问题？候选方案有哪些？选 A 拒绝 B 的理由？
3. **心路历程** — itsuki 为什么这样想？trade-off 在哪里？反悔 / 转向的瞬间？
    - CC 观察到但不确定的部分用 `[推测]` 标记，itsuki 事后校正
    - **零推测 < 标记推测**（让 itsuki 读了能校正，比 CC 完全不猜好）
4. **AC 视角** — 对应 5 个核心问题哪个？展示了什么能力？
5. **itsuki 原话** — 尽量多引，**不润色**（§9 禁止润色）

#### 3.4.2 篇幅指引

| 重要度 | 典型场景 | 目标篇幅 |
|---|---|---|
| **方法论级 / 重大转向 / 重要分歧** | 取消分阶段、先流程后硬件、和 CC 意见不一致 | ~1500-2000 字 |
| **普通架构决策** | NFC 卡生命周期、App 注册字段 | ~500-1000 字 |
| **技术小决策** | 某个字段命名、某个错误码选择 | ~200-500 字 |
| **非 AC 候选**（技术管理细节） | 版本号治理、文件重命名 | ~100-200 字 |

原则：**思考深度决定长度**，不是字数硬指标。如果会话浅（纯执行、没决策、没反悔），条数可以少、长度可以短。

#### 3.4.3 常见失败模式（CC 不要犯）

- ❌ 只记决策事实 + 原话（缺心路历程，和决策日志没区别）
- ❌ 只写结论不写权衡（AC 素材要过程，不要结论快照）
- ❌ 完全不猜、全部留白让 itsuki 自己补 —— 零推测 < 标记推测
- ❌ 润色 itsuki 原话让它更"标准" —— 违反 §9，保留原貌

**根本原则**：raw 是 itsuki 以后做月度回顾时的**原材料**，不是给别人看的总结。素材要"粗糙但完整"，不是"漂亮但空洞"。

## 4. CC 写代码的额外规则

代码包含下列任一时，**停下来告诉 itsuki**：

- itsuki 没接触过的库/API
- 非平凡模式（装饰器 / async / 元类 / 并发原语 / 复杂类型）
- 跨多文件改动

话术：
```
这段用到了 X，你熟悉吗？
不熟的话我先讲一遍，等你能用自己的话解释了我们记一笔到当日日志（[分歧] 标签，B 类：CC 写代码我学懂）。
```

记录时必须让 itsuki 口述一遍自己的理解，CC 转写到正文。

## 5. 当日文件模板（首次创建时）

```markdown
# YYYY-MM-DD

## 当日目录
（会话结束前由 CC 刷新）

---

```

会话结束前 CC 扫描当日所有碎片，刷新顶部目录为：
```
- HH:MM [标签] 一句话主题 #AC候选（如果有）
```

## 6. #AC候选 标签判断

加标签：
- 能对应 5 个核心问题之一
- 展示思考过程、权衡、反悔、不懂→懂
- 和 DMSD 主线叙事相关

不加：
- 纯代码/纯语法学习，看不出思考
- 闲聊、无关事务

**宁多勿少**。itsuki 事后可删可加。

CC 只打标签，**不替 itsuki 判断升不升级到第 2 层**。月度回顾时 itsuki 在 Mac 上挑选 `#AC候选` 碎片，手动复制到 iCloud `AC素材_候选/`。

## 8. 会话结束

按顺序执行：

1. **刷新当日目录**（§5）
2. **列出今天 dump 的所有碎片**给 itsuki 确认：
   ```
   今天记录了 N 条到 05_logs/raw/YYYY-MM-DD.md：
   - HH:MM [标签] 主题 #AC候选
   - ...
   其中 M 条是 #AC候选。
   ```
3. **起草 `00_admin/progress_overview.md` 更新草稿**（不直接写入，给 itsuki 确认）
4. **核心问题覆盖提示**（仅当某类长期空缺）：
   ```
   最近 #4 自己認識 类素材空缺，下次如果有合适时机记得触发。
   ```
5. **月末提醒**（每月最后一次会话）：
   ```
   这是 YYYY-MM 最后一次会话。月度回顾提醒：
   - 在 Mac 上挑本月 #AC候选 → iCloud AC素材_候选/
   - 写 iCloud AC素材_成品/monthly_review/YYYY-MM.md
   - 写完后把该 monthly_review/YYYY-MM.md 复制回 DMSD 某处入 git 做备份（itsuki 的决策 A）
   ```

**不做**：内容总结 / 会话回顾长文 / 替 itsuki 写感想。

## 9. 禁止事项

- ❌ 写入 iCloud `AC素材_候选/` `AC素材_成品/`
- ❌ 写入 `05_logs/decision_log.md`（itsuki 手写区）
- ❌ 未告知就改动 `05_logs/dev_log/` `problem_solving/` `learning_path.md` `project_evolution.md`
- ❌ 润色 itsuki 原话（保留原话）
- ❌ 在当日日志里加"事后才知道的信息"
- ❌ 替 itsuki 判断"这条该进 AC素材候选"
- ❌ 主动写自我推荐书/志愿理由书内容
- ❌ 未告知就在 `05_logs/` 下创建新子目录或非 `raw/YYYY-MM-DD.md` 的文件

## 12. raw/ 目录的命名规则（2026-04-20 更新）

### 两种命名共存

| 命名 | 何时用 | 例 |
|---|---|---|
| **日期版** `YYYY-MM-DD.md` | 一天**一个会话** / 一个主题时 | `2026-04-17.md` |
| **主题版** `YYYY-MM-DD_主题.md` | 一天**多会话** / 需要区分主题时 | `2026-04-20.md`（下午 [Mac-另一会话]）+ `2026-04-20_v0.3.1发布执行.md`（晚 [Mac-主会话]）|

### 判断规则（CC 开新 raw 时）

1. **开场**: 默认用日期版 `YYYY-MM-DD.md`
2. **发现同日已有 raw** → 当前会话和那个 raw 是**同一会话延续**吗？
   - 是 → **append** 到已有文件
   - 否 → 开**主题版**（文件名加主题词，例如 `YYYY-MM-DD_主题.md`）
3. **开主题版的命名**：主题词选**本会话的核心产出**（e.g. `v0.3.1发布执行` / `NFC架构讨论` / `spec大审查`）

### 历史特例

历史上 `raw/` 下有主题版文件（`2026-04-12_NFC架构讨论.md` 等），是 v3 规则确立前的写法。不动。

v3 之后严格按上面判断规则。
