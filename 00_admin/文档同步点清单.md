> **这是什么**：DMSD 项目里所有"版本号 / 路径引用 / 时间戳 / 共享概念"的同步点清单。每次 bump 版本号 / 改重要概念 / 创建含版本号的新文件时，对照本清单逐条 check。
>
> **为什么需要**（2026-04-19 发现）：
> - 项目已迭代到最新版本（见 `CHANGELOG.md` 顶部），但 CLAUDE.md / WIP / TODO 等文件里残留"v0.2 修订进行中"等过期表述
> - 根本原因：**同一信息多处存储 → 必然漂移**
> - 本清单 + `hooks/pre-commit`（自动化强制执行）+ CLAUDE.md 单源规则 = 这个问题的系统性解
>
> **最后更新**: 2026-04-21（加入 §5 项目名 vs 系统名）
>
> **相关**:
> - `2026-04-19_项目审查_backlog.md` — 本清单是对 D22-D25 / L11 等漏洞的系统性解法

## § 1 — 版本号

**单一真值**：`CHANGELOG.md` 顶部第一条 `## [vX.Y.Z] - YYYY-MM-DD` 就是"当前版本号"。

### 规则

- 其他文件**不写**具体版本号
- 引用时用 "当前版本见 `CHANGELOG.md` 顶部" 这类指针

### 声明性文件（pre-commit hook 会拦）

下面这些文件里如果出现 `v0.X.Y` / `v1.X.Y` 等模式，pre-commit hook 会拒绝 commit：

- `CLAUDE.md`
- `00_admin/WIP.md`
- `00_admin/TODO.md`
- `00_admin/progress_overview.md`

### 允许出现版本号的文件（hook 不检查）

- `CHANGELOG.md`（权威）
- `01_specs/**/*.md`（spec 里引用历史决策 "v0.2 时决定..." 是正常的，不是状态声明）
- `05_logs/**/*.md`（日志写"今天 bump 到 v0.3.0"是记录）
- `99_archive/**`（归档区）
- `00_admin/2026-04-19_项目审查_backlog.md`（审查报告里引用各版本）
- `00_admin/hooks/**`（hook 脚本本身会举例提版本号）
- `00_admin/文档同步点清单.md`（本文件）

### 豁免机制

如果某行必须写具体版本号（极少见），**在该行末尾加 `<!-- VERSION_OK -->`** 注释，hook 会跳过。

例（本清单也用得着）：

```markdown
当前版本见 CHANGELOG.md 顶部
上个版本 v0.2.0 做了字典重构 <!-- VERSION_OK -->
```

## § 5 — 项目名 vs 系统名（2026-04-21 加入）

**单一真值**：
- `CLAUDE.md §项目信息` 顶部区分块
- `memory/project_naming_tomoshibi.md`

### 规则

- **项目名 = DMSD**（Dormitory Management System Digitalization）— 仓库 / 开发代号 / AC 叙事项目名。用在 git / commit / spec 文件名前缀 / 内部开发文档
- **系统/产品名 = Tomoshibi**（灯火 / ともしび，2026-04-21 itsuki 定名）— 面向用户的品牌。用在 App title / Web `<title>` / 登录欢迎语 / FastAPI app title / Swift Bundle Display Name / README 给用户看的段落 / 对管理员或教授的产品介绍
- **不要做无脑 replace_all**：两者有不同使用场景，替换前判断上下文
- **AC 话术定版**（不改）："我在日本留学，宿舍是我在异国的第二个家。这个系统守护的是'灯火'——每个学生夜晚平安归来、房间亮起一盏灯。"

### 新增文档时须声明的场景

- 新建面向用户的代码（App / Web / FastAPI / Web 页面标题）→ 直接用 **Tomoshibi**
- 新建 spec / 内部文档 → 标题可继续用"DMSD vX.Y 某某 spec"，但正文里描述"系统如何"时用 Tomoshibi
- 新建对教授的 AC 材料 / 面试准备 → 首次提到产品时用 "Tomoshibi（灯火）"，后文可简称

## § 5 — 时间戳（每个文件自己维护，不能单源化）

每个文件头部的"最后更新"独立维护。这**不是** bug —— 新鲜度信号必须文件级独立（WIP 今天没动 ≠ TODO 今天没动）。

### 需维护头部"最后更新"的文件

| 文件 | 更新时机 |
|---|---|
| `00_admin/WIP.md` | 每次会话开始 / 结束 |
| `00_admin/TODO.md` | 每次 itsuki 改 TODO 内容 |
| `00_admin/progress_overview.md` | 每次章节级更新后 |
| `00_admin/文档同步点清单.md`（本文件）| 改 § 或加清单时 |
| `05_logs/learning_path.md` | 加新学习条目时 |
| `05_logs/project_evolution.md` | 加新转折时 |
| `05_logs/decision_log.md` | 加新决策时（itsuki 手写） |
| `CHANGELOG.md`（头部）| 每次 bump 版本号 |
| `CLAUDE.md` | 改重大规则时 |

### 执行保障

`CLAUDE.md §文档一致性规则` 里的"会话结束前一致性检查"要求 CC 扫时间戳新鲜度（过去 7 天 commit 改过但头部时间戳没动的文件 → 提醒 itsuki）。

## § 6 — 打 tag 前的 Release Checklist

每次 `git tag v0.X.Y` 前按这个清单走一遍：

- [ ] `CHANGELOG.md` 加新版本条目（含日期 + "为什么 bump 的说明"）
- [ ] `CHANGELOG.md` 头部"最后更新"时间戳刷新
- [ ] 跑 `git status` 确认相关改动全部已 staged
- [ ] `git commit` 前 pre-commit hook 自动跑一致性检查（通过后再打 tag）
- [ ] `git tag vX.Y.Z -m "..."` + `git push origin vX.Y.Z`
- [ ] 本次 bump 有"重大决策" → 在 `05_logs/raw/YYYY-MM-DD.md` dump 一份（CLAUDE.md 规定"版本号 bump 时必须触发 AC 记录"）

## § 7 — 创建新文件时的 Onboarding Checklist

如果创建的新文件**会含版本号 / 路径引用 / 时间戳**：

- [ ] 如果是"状态声明类"文件（会写"当前做到哪"）→ 加入 §1 "声明性文件" 列表 → 让 hook 保护它
- [ ] 如果是"历史引用类"（日志 / spec / 审查报告等）→ 加入 §1 "允许列表"
- [ ] 如果需要头部"最后更新"时间戳 → 加入 §5 "时间戳表格"
- [ ] 如果引用了目录结构 / 5 核心问题 → 用指针（"见 CLAUDE.md §..."）而不是复读

## § 8 — 如何维护本清单

1. **加新同步点** → 本清单直接加 § 条目
2. **发现机制失败**（hook 没拦下一次漂移）→ 在 `05_logs/raw/YYYY-MM-DD.md` 记录 + 更新本清单
3. **改 hook 逻辑** → 同时更新 `00_admin/hooks/README.md §如何调整`
4. **新会话看到本文件过期** → 直接改（有"最后更新"时间戳，不怕被覆盖）
