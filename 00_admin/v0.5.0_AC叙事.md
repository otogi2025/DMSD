### D1: 4-22 砍 Pi 硬件 demo —— 推翻自己 24 小时前的计划

**决策**：4-22 上午 itsuki 推翻 4-21 晚的"Demo 1 台 Pi ¥12380"采购计划 → Demo 阶段 0 采购，软件代替方案：

**为什么**：deadline 视角。7 天里硬件调试占太多风险，且失败概率最高的环节是"卡读头驱动"。砍掉硬件 = demo 成功率从 60% → 95%。

**注意**：上线版 v1.0 仍按 Pi 3A+ 方案保留（hardware_design.md §2.1）— **demo 是临时降级，不是产品定型推翻**。

### D2: 学号 6 桁体系（业务规则改动）

**决策**：从 2 位 ID（00 / 01 ... 99）改为 6 桁体系：
- 学年（中高一貫 6 年制）× 組（A=01 / B=02）× 番号

**业务规则改动级别**：影响**所有** ID 字段 / 显示位置 / 注册流程 / seed 数据 / accounts.jsx 列宽。这是 SOP §2 条件 1 minor 触发。

### D3: 跨会话同步规则 A+B+C（A 单源 / B 物理 copy / C 明文 ルール）

**决策**：Tomoshibi-iOS Swift 实装在独立 repo（`otogi2025/Tomoshibi-iOS`），cloud agent 取不到 DMSD repo → 设计真值需物理 copy 到 `Tomoshibi-iOS/refs/`。

**A 单源真值层**：新建 `02_design/system_features.md` = iOS + Web + 後端 共用功能真値（账号 / 申請 / 通知 / コミュニティ / 規律 / 巴士）。

**B 物理 copy 层**：`bin/sync-ios-refs.sh` 脚本 → DMSD 单源 → Tomoshibi-iOS/refs/ 复制。

**C 明文 ルール层**：CLAUDE.md §跨 repo 同步规则写明三种状况 × アクション。

**为什么是新决策机制**：之前所有共享真值都假设"所有 CC 在同一 repo"。Cloud agent 出现破坏了这个假设 → 必须设计**物理同步层**。

### 认知 1：deadline + 零基础 = 减法工程

**关键判断**（itsuki 原话补）：

**减法工程**的核心：deadline 紧 + 经验少时，加一项功能就加一份失败风险。砍掉硬件 = demo 成功率 60% → 95%。

### 认知 2：跨会话同步是物理工程问题不是文档问题

**D3（4-23）跨会话同步规则 A+B+C** 不是"文档同步规范"问题，是**物理工程问题**：
- Cloud agent 跑在 Anthropic 基础设施上，**取不到** itsuki 本地 DMSD repo
- 单源真值 = `02_design/system_features.md` 在 DMSD repo
- 物理同步 = `bin/sync-ios-refs.sh` 脚本把 DMSD 单源**物理复制**到 Tomoshibi-iOS/refs/
- CLAUDE.md 明文规定哪个会话有权改 / 复制 / 通知

**和软件工程的 cache invalidation 类比**：
- Tomoshibi-iOS/refs/ ≈ cache 副本
- DMSD/02_design/ ≈ origin
- bin/sync-ios-refs.sh ≈ cache invalidation script
- "禁止直接编辑 refs/" ≈ cache 不能反向写源

**面试可用原话**（Q3 + Q4）:
> "iOS 的 Swift 实现在独立 GitHub repo，cloud agent 取不到我本地的 DMSD repo。所以设计文档需要物理复制过去。我设计了三层：单源真值在 DMSD，物理复制脚本是单向的（DMSD → Tomoshibi-iOS），明文规则写在 CLAUDE.md 哪个会话改哪个文件。这其实是分布式系统里 cache invalidation 的小型版本。"

### 认知 3：失败转成系统性解法 = 工程成熟度

**v0.5.0 close 时回顾 v0.4.0 的失败**（[0.4.0-wip] 拖 9 天）：
- 选项 A：偷偷修改 git 历史，假装没发生
- 选项 B：道歉但不改流程
- 选项 C：**承认失败 + 设计系统性解法**（SOP 4 层机制）

**4-29 itsuki 选 C**。SOP 不是 "documentation"，是 "把人类必然犯的错误编码成机器执行的规则"。

- pre-commit hook 在 commit 时强制提醒 = 机器执行
- WIP 头部当前版本行 = 信息密度（每次会话开始扫一眼就知道）
- CLAUDE.md inline 5 条 = CC 一定看到
- 会话结束第 4 项 = 强制 30 秒判断

**4 层叠加 = 任何一层失败时另外 3 层接住**。这是 fault-tolerant 设计思维。

### 认知 4：Demo 做到这种程度的 prototype 比真代码更接近"产品"

**v0.5.0 demo prototype 量级**：
- iOS Phase B v2 HTML：73 画面 + 4 参考图
- Web Round 3：12 组件 + 130 字体 inline + 32MB single-file U 盘版
- accounts.jsx 学生账号管理 + カレンダー仿 iOS + リクエスト曲管理 + 主页 LAN IP 自动检测
- demo_server.py + iPad TTS + iPhone Shortcuts 软件代替 Pi

这种 prototype 比"真代码 backend stub"**更接近产品**：
- 管理员一眼看到"完整的产品长什么样"
- 真代码 backend = 看不见的黑盒，管理员不会评估
- HTML prototype = 视觉密度高，管理员能直接说"这里改一下"

**Demo Driven Development 的雏形** — itsuki 没学过这个名词，但实际跑出了这个节奏。

### 陷阱题应对

**Q: "你说 4-22 推翻了 4-21 的计划。这种朝令夕改不是项目管理失误吗？"**

**A**: 不是。理由：
1. 4-21 的计划是基于"理想完成度"假设 — 时间充裕、零件能到、驱动能跑
2. 4-22 上午我重新评估 = "deadline 紧 + 我零基础 + PN532 I²C 驱动 + TTS + 接线" 5 个失败点叠加
3. **越早识别问题越早改方案** — 4-22 改比 4-26 demo 失败再改成本低 100 倍
4. 上线版 v1.0 仍按 Pi 3A+ 方案保留 — 砍的是 demo 临时方案，不是产品架构

**这恰恰是项目管理能力的体现**，不是失误。

**Q: "[0.4.0-wip] 拖 9 天没 close，你怎么解释？"**

**A**: 那是失败，但我处理方式我自己满意：
1. 没掩盖，写进 CHANGELOG / SOP §8 / 版本演变一览
2. 建立 SOP 4 层机制（pre-commit hook / WIP 头部 / CLAUDE.md inline / 会话结束 4 项）
3. 这 4 层任何一层失败时另外 3 层接住 — 这是 fault-tolerant 设计
4. **失败转成系统性解法**比"避免任何失败"更重要 — 后者是不可能的
