## 心路历程（从 raw 775 行里提炼的认知演变）

### 认知 1：spec rewrite 不是重写代码，是重建"设计意图"

v0.1 冻结时，spec 是"早期想法的快照"。中间 4-12 / 4-15 的架构决策没进 spec —— 每次讨论都是"绕过 spec"做的。

4-17 rewrite 的**第一层价值**是：**把散在 decision_log / raw / 脑子里的架构决策**显式写进 spec 主体。让 spec 重新成为"真实决策的权威"，不再是"过时快照"。

### 认知 2：字典 + spec 分层是"防漂移"的架构做法

4-17 的第二个认知：
- v0.2.0 做的字典三件套（ENUM / FIELD / ERROR_CODES）+ DEVICE_REGISTRY 是**定义层**
- spec 主体应该只**引用**字典，不**重复**定义

这个分层让后续改动成本降低：改一个字段 → 只改 FIELD_REGISTRY → 所有引用它的 spec 章节自动"同步"。

**后续延伸**：4-19 的"文档同步机制 A+B+C"是这个"字典 / spec 分层"思维的泛化 —— 从"字段级单源真值"扩到"版本号 / 目录结构 / 核心问题" 等所有共享概念的单源真值。

### 认知 3：spec 长度不是负债，是沉淀

681 → 958 行，+277 行的增长**有顾虑**："spec 这么长教授会不会读不完？"

但 4-17 的判断是：**spec 长度应该反映真实设计复杂度，不应该为"可读性"人为压缩**。真正的可读性来自：
- 分层（主体 + 附录 A-D 分块）
- 单源真值（不重复定义）
- 索引（目录 + 章节标号 + 交叉引用）

**面试可用原话**（Q3 问题解决）:
> "我的 spec 从 v0.1 的 681 行写到 v0.3.0 的 958 行。有人会说太长。但我的判断是：spec 的长度应该反映真实的设计复杂度，不是为了好看去压。真正让 spec 可读的是结构 —— 字典层分开放、附录按主题切、每条都有编号。一个教授三分钟看不完整个 spec，但他能三分钟找到他想看的那一节。"

### 认知 4：版本号连跳两个 minor（v0.1.3 → v0.2.0 → v0.3.0）是合理的

v0.2.0 是字典重构（新 scope 范围：字典作为独立文件）
v0.3.0 是 spec 主体 rewrite（新 scope 范围：spec 核心章节升级）

这两次都是 minor bump。按版本管理指南 §2 判据 "新增功能 / 新范围进来" = Minor —— 字典文件是新 scope，spec 主体 rewrite 是新的业务规则范围。

**不合理的写法**：把两件事合并成一个 v0.2.0。那样会：
- CHANGELOG 不清晰（两个不同目的的改动混在一起）
- 回溯时难以区分"字典"和"主体"改动的时间线

## 这份文件作为模板的用法（给未来 v0.3.1 / v0.4.0 / ... 参考）

### 推荐 6 节结构

1. **是什么** — 日期 / 语义 / scope / 量级变化 / 配套改动 / CHANGELOG 指针
2. **背景** — 这个版本为什么存在，解决了 v 上一版本的什么问题
3. **核心决策** — 本版本拍板的关键判断（用表格列，指针到 decision_log / raw）
4. **心路历程** — 3-5 层认知演变（每层约 100-300 字 + 面试可用原话）
5. **AC 5 核心问题素材映射**（每条问题 50-100 字概括本版本的贡献）
6. **面试片段**（60 秒 + 3 分钟 + 陷阱题应对）+ **遗留**（给下一版本）

### 命名规则

`v{major}.{minor}.{patch}_AC叙事.md`

Patch 级版本如果 scope 小（像 v0.3.1 的文档层同步），可以**合并写**到 minor 叙事（v0.4.0）里作为"前置 patch"段；如果 scope 大（像可能的 v0.3.1 这种 AC readiness 专项），单独一份。

### 写作时机

**版本号 tag 打完后 24 小时内**（按 CLAUDE.md §会话结束 + AC 记录协作触发清单第 9 条"版本号 bump"）。

热度高的时候写最有感觉。冷下来以后再写会失去细节。
