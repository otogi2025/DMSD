## 4. 心路历程（4 层认知演变）

### 认知 1：AI 进度粉饰的风险 + 主角如何防

v0.3.1 发布后 CC 给的总结用了"Batch 1 完成 (4/11)"的措辞。听起来"做了不少"，但对齐 87 条 backlog 分母就是 **4/87 ≈ 5%**。

itsuki 直接追问"漏洞都修好了吗？"。CC 立刻 Grep 精确统计，如实摆出 10/87 数字。

**认知突破**：**AI 的描述方式可以把同一事实包装成不同的进度感。主角必须用自己的分母校验**。

这不是一次性的警觉，是一种**持续的协作质量**。itsuki 在版本号争议时再次展现这一点 —— 她反驳议题 CC 的 v0.3.2 推荐，但拒绝接受 AI **立刻倒戈**的回应。([Mac-主会话] 分析显示议题 CC 倒戈是 AI 顺从性翻车)。

### 认知 2：多会话并行的工程协调

DMSD 今日有两个并行 CC 会话。没有传统 PR / code review 机制，但**通过以下 4 个规则实现了 0 冲突**：

1. **WIP.md 归属一个会话维护**（[Mac-主会话]）—— 避免两会话同时改
2. **commit 分工** —— 设计文档归议题讨论会话，backlog 推进归主会话
3. **不覆盖对方文件** —— 议题讨论会话明确"不改 backlog / 记录指南 / symlink.sh"，主会话明确"不改 02_design / flow_design"
4. **代 commit 协议** —— 主会话在 `f36d10b` 代落盘议题会话上午的产出，commit message 明确归属

**AC 叙事价值**：这是**分布式协作**的实战 —— 哪怕是"AI 两个窗口同时开"的最简单场景，也需要工程化协调。

### 认知 3：架构决策可以推翻，但要有结构化理由

4-19 G2 决定"一设备一账号"。今天（一天后）议题 C 推翻了它。

不是朝令夕改。推翻时做了以下事：
1. **明确记录原决策**（CHANGELOG v0.3.2 Fixed 段 + flow_design §7 修订说明）
2. **给出推翻的 first-principle 理由**（学生换手机麻烦 + 设备指纹靠不住）
3. **同一方向的新决策**（用"老师面签"替代设备绑定）
4. **更新所有引用处**（CLAUDE.md §项目信息 + flow_design § 7）

**关键 rule**：**可以推翻自己的决策，但必须留下结构化的推翻痕迹**，不是静默 delete。

### 认知 4：工程断舍离 —— 什么时候加新文件 / 什么时候复用

今天新建 12 个文件，但同时：
- **T2 iOS 归档** 写了 dry-run 但**没执行**（破坏性操作等授权）
- **M2 版本管理指南** 只加 backlog 元条目，**不改 iCloud 原文件**（CC 无权）
- **Batch 3 itsuki 手笔区 draft** 放独立辅助文件，**不改 decision_log / project_evolution / learning_path 正文**

这是**AI 权限边界的持续守护**。背后的认知：**"新建文件比改已有文件安全"，但不滥用新建 —— 每个新文件都要有独立存在理由**。

### 陷阱题应对

**Q: "一天推翻两条架构决策，你的系统是不是不够稳？"**

**A**: 不是系统不稳，是**设计阶段本就应该高频迭代**。v0.3.2 仍是 0.x 版本（按 SemVer 约定：0.x 阶段一切可变）。推翻发生在 spec 主体 rewrite 之前 **刻意**设计的窗口里 —— 1.0.0 宿舍上线后的推翻才需要担心。而且我每次推翻都留下了完整的**决策歧路**（decision_log + CHANGELOG），新队员进来能看懂为什么是现在这样。

**Q: "你用 AI 这么多，不是 AI 在设计你的系统吗？"**

**A**: 看今天一天：我 5 次追问 AI 的默认假设（漏洞盘点 / URL 可复制 / 树莓派必要性 / keystore 安全 / 版本号判断），2 次推翻 AI 推荐的方案（选贵方案 B + 拒绝 AI 倒戈）。**AI 给我材料，我做判断**。如果你去看我的 memory，里面最优先级的规则是"做镜子不做回音"—— 这不是装的，是每天在实战。
