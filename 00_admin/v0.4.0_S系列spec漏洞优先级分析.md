## MVP 必修（7 条，阻塞 Phase 1 代码开工）

如果不修，Phase 1 代码一写就会卡或写错。

### S1 🔴 → **改 🔴🔴**
**问题**：§7 边界 "卡未启用" 判据用 `device_active=false`。`device_active` 是**点呼机字段**，不是卡/学生字段。
**影响代码**：开发写鉴权逻辑时找不到字段 → 卡在第一步
**修复复杂度**：**简单**（15 分钟）
**修法**：spec §7 边界里把 "`device_active=false` 或学生离寮" 改为 "`card_active=false` 或 `student_status != active`"
**依赖**：需要先做 S2 (card_uid 字段) + S3 (student_status 字段) —— 否则这两个字段定义不存在

### S2 🔴 → **改 🔴🔴**
**问题**：`FIELD_REGISTRY` 缺 `card_uid` 字段
**影响代码**：Phase 1 路径 A 的核心字段 —— 数据库建表都建不起来
**修复复杂度**：**简单**（20 分钟）
**修法**：`FIELD_REGISTRY §2.2 身份与对象` 新增 `card_uid` 字段定义（类型 / 唯一性约束 / 绑定到 user_id）+ spec §10.2 idempotency_key 公式更新
**依赖**：无

### S3 🔴 → **改 🔴🔴**
**问题**：`FIELD_REGISTRY` 缺 `student_status` 字段（spec 附录 C.5 声明了，字典没登记）
**影响代码**：**字典和 spec 主体不一致** → 前后端代码拿不到字典权威
**修复复杂度**：**简单**（15 分钟）
**修法**：`FIELD_REGISTRY §2.x 生命周期` 新增 `student_status` 字段（active / paused / transferred / graduated）
**依赖**：无

### S4 🔴 → **改 🔴**
**问题**：`UNKNOWN_CARD` vs `UNREGISTERED_UID` 语义边界不清
**影响代码**：实现鉴权时开发不知道返回哪个错误码
**修复复杂度**：**中等**（30 分钟）—— 需要澄清业务决策
**修法**：`ERROR_CODES` 里加判据说明。建议：
- `UNKNOWN_CARD` = 卡 UID 在数据库里**完全没有记录**（新卡 / 外部卡）
- `UNREGISTERED_UID` = UID 有记录但 `card_active=false`（被停用 / 学生离寮）
**依赖**：建议和 S1 同时改

### S7 🔴 → **改 🟡**
**问题**：附录 D B.4 标 ✅，但实际落地在 §7 边界的 S1 错位条款 → ✅ 是假象
**影响代码**：附录 D 里 ✅/🟡/🔄 盘点失去可信度（后续看盘点的人会被误导）
**修复复杂度**：**简单**（10 分钟）
**修法**：S1 修好后，附录 D 里 B.4 的 ✅ 标注保留；如 S1 不立即修，B.4 降级为 🟡
**依赖**：S1

### S6 🔴 → **补决策**
**问题**：§11.3 改判时限矩阵 ">30 天 → 只读走追溯申请（v0.3 设计）"。v0.3 已经是当前版本，**追溯申请流程并没有设计**。字面笔误 + 承诺未兑现
**影响代码**：改判功能开发时 ">30 天"分支无 spec 可实现
**修复复杂度**：**中等**（1-2 小时 —— 要设计追溯申请流程）
**修法（两个选项）**：
- **A（简单）**：改 spec 为 "追溯申请独立流程设计推迟到 v0.5.0"，v0.4.0 只处理 ≤30 天
- **B（完整）**：v0.4.0 本次就设计追溯申请流程（新章节 §11.5）
**建议**：A（不想在 v0.4.0 引入新 scope）
**依赖**：无

### S10 🟡 → **改 🟡**
**问题**：§10.2 `idempotency_key` 客户端生成 UUID 和路径 A thin client 原则矛盾
**影响代码**：路径 A 代码写幂等时要么违反 thin client 原则，要么没 idempotency_key
**修复复杂度**：**中等**（1 小时）
**修法（推荐）**：路径 A 不用 `idempotency_key`，改用 `(card_uid, session_id, ts_secondbucket)` 的复合唯一索引作为幂等依据
**依赖**：S2（需要 card_uid 字段）

## Nice-to-have（8 条，v0.4.0 如有时间做）

### S5 🔴 → **改 🟡**
**问题**：`exempt_range` 和 `present` 同绿色，UI 无法视觉区分
**影响代码**：不影响后端代码；影响老师端 UI 开发
**修复复杂度**：**简单**（ENUM 加 icon 字段或 display_hint）
**修法**：`ENUM_REGISTRY §3 base_status` 为 exempt_range 加 `icon: "🛡️"` 或 `border_style: "dashed"` 字段
**延后判断**：v0.4.0 做 spec 侧，UI 落地到 v0.7.0（老师端开发）

### S8 🟡
**问题**：§5.3 时间窗公式里 X 分钟未决（附录 A.3）
**影响代码**：结算公式依赖 X → 不定就不能写结算代码
**修复复杂度**：**低（决策本身快，实现简单）** —— itsuki 拍板一个值
**修法**：附录 A.3 定 X（推荐 X=3 或 X=5）
**建议**：v0.4.0 拍板

### S9 🟡
**问题**：`path_type` 取值 A/B 硬编码，Android HCE 怎么扩展没说
**影响代码**：v1.0 按 4-19 G2 决策 Android 不走 HCE（走贴纸），所以当前不阻塞
**修复复杂度**：**简单**（ENUM 加一条说明）
**修法**：`ENUM_REGISTRY §13 path_type` 加 note "A/B 为当前取值（A=卡，B=贴纸）。未来若引入 HCE 走独立 path_type='C'"
**延后判断**：v0.4.0 顺手改

### S11 🟡
**问题**：§11.4 改判联动扣分表缺反向 transition（`exempt_range → 任意`）
**影响代码**：扣分引擎写到"申请拒绝后变 absent"时 spec 无 ledger 规则
**修复复杂度**：**中等**（1 小时）
**修法**：§11.4 表格加一行反向转换规则（exempt_range → absent 时按制度扣分）
**依赖**：无

### S12 🟡
**问题**：`device_active` 混用"临时停用"和"永久注销"
**影响代码**：历史查询分不清两种状态
**修复复杂度**：**简单**（20 分钟）
**修法**：`DEVICE_REGISTRY` 加 `device_retired_at` 字段（null = 仍在使用 / 非 null = 永久注销日期）
**依赖**：无

### S13 🟡
**问题**：`API_CONVENTIONS` 太简薄（47 行）
**影响代码**：开发 API 时规约不清，前后端可能各做各的
**修复复杂度**：**中等**（2-3 小时，要补 URL 命名 / HTTP 动词 / 分页 / 版本 / error.detail schema）
**修法**：扩写 API_CONVENTIONS 到 ~150-200 行
**建议**：v0.4.0 做（代码开工前必补）

### S14 🟡
**问题**：`v0.1_冻结决策.md` 过期（"特殊状态：红十字 / 免 / 申"还是 overlay 表述，实际 4-17 Q1 后已升为 base）
**影响代码**：不影响代码；影响历史文档可信度
**修复复杂度**：**简单**（10 分钟）
**修法**：在 v0.1_冻结决策.md 顶部加一段 "2026-04-17 Q1 决策后：`exempt_range` 从 overlay 升为 base_status。本文件其他叙述保留原始冻结版"
**建议**：顺手做

### S16 🟡
