## 关键概念（给 itsuki 解释时用，他是零基础）

1. **push 推的是 commit，不是文件清单**——没法「选择性推某些文件」。一个 commit 进了历史，push 时就整个上去。
2. **没 commit 的文件天然不会被 push**——工作区里那些未跟踪的东西（数据库备份 `.db.bak*`、图标源文件、`.bak` 工程备份等）只要不 commit 就永远不上 GitHub。itsuki「不想 push 的文件」多半是这类 → 答案是「什么都不用做，顺手把该进 `.gitignore` 的进了更保险」。
3. **已经 commit 但还没 push 的文件**想不公开 → 在 push 前提交一个删除该文件的 commit（首页和最新版没有它，但**历史里仍能翻到**——告诉 itsuki 这点，由他判断够不够）。要历史里也查不到，只剩重写历史一条路——破坏证据链，本项目原则上不做，除非泄密级内容（密钥/真实学生个人信息）。
4. **绝不 `git push --force`**——本项目灾难级红线。

## 建议操作顺序（每一步都把结果给 itsuki 看、push 动作必须他逐次明示）

1. `git fetch origin`，报告本地领先多少、远程有没有新动静。
2. 盘点将要公开的内容：`git diff --stat origin/main..HEAD` + `git log --name-status origin/main..HEAD | grep -E '^A' | sort -u` 列**新增文件清单**给 itsuki 过目——重点扫：含密钥/密码嫌疑的、真实人名/个人信息、他可能不想公开的内部文档。
3. itsuki 点名不想公开的已提交文件 → 逐个按上面概念 3 处理（删除 commit），并问清「历史里留着行不行」。
4. 顺手核对 `.gitignore` 把工作区那批 `.db.bak* / *.bak* / 图标源文件` 类挡住（先跟 itsuki 确认哪些是垃圾哪些要留本地）。
5. itsuki 明示后：`git push origin main`，再 `git push origin --tags`（76 个新标签必须 `--tags` 才上去）。
6. push 后验证：`git ls-remote --tags origin | grep -cv '\^{}'` 应为 143+；GitHub 网页 Tags 页抽查 v0.11.30 / v0.22.3 存在。
7. 提醒：push 后 GitHub Actions（6-11 新建的 CI 配置 `04fe9de`）会第一次真跑——后端 pytest + 老师网页构建，红了不要慌，看日志再说。
8. push 完成后更新 memory `project_release_status.md` 的远程状态行（或注明 live 查）。
