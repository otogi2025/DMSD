## 核心决策（5 项）

### D1: 项目名 vs 系统名 双层分离

**决策**：
- **项目名** = DMSD（Dormitory Management System Digitalization）— git repo / 开发代号 / 内部 spec / commit 历史
- **系统/产品名** = **Tomoshibi（灯火 / ともしび）** — 学生 App / 老师 Web / 点呼机品牌 / 对外文案

**为什么这次拍板**：4-21 晚 itsuki 自己提出"项目要有名字"。中文名 / 日文名 / 英文名候选评估后，定 Tomoshibi。

**面试原话定版**（itsuki 拍板）：
> "我在日本留学，宿舍是我在异国的第二个家。这个系统守护的是'灯火'——每个学生夜晚平安归来、房间亮起一盏灯。所以取日语名 Tomoshibi（灯火）。"

### D2: S 系列 14 条 spec 漏洞**一次性扫完**而不是 patch 碎片

**决策**：4-21 → 4-22 上午用 3 个 commit（c8e05ea / d02ba18 / 00e5aab / 8a9d226）扫掉 14 条，不分多个 patch。

**为什么**：
- 单条 patch 节奏会带来 CHANGELOG 噪声 + 反复触发 hook + 难以跟踪
- 累积到 minor bump 时一次性 close 才符合 SOP §3 "版本号是给发布用的，不是给保存用的"

### D3: Device_Contract 先建骨架不填细节，OQ 占位

**决策**：v0.4.0 只建骨架（9 节 + OQ1-9 开放问题），不强求完整 spec。OQ 包括 mTLS / nonce+HMAC / HTTP 超时 / device 注册 / 心跳 / 降级策略 / 固件更新 / LED 语义 / path_type 扩展 — **9 个问题暂不阻塞主线**。

**为什么**：minor incremental 思维 — 90% 完成度的骨架比 0% 完成度的"等所有 OQ 拍板再写"更有用。

### D4: API_CONVENTIONS 48 → 240 行扩写（5 倍）

**决策**：把 URL 设计 / 动词约定 / 幂等性 / 分页 / 日期格式 / 命名规则 / 状态码语义 / error.detail 格式 一次性写清楚。

**为什么**：S13 漏洞修补的连带产出。后端开工后这些约定每次都要查 — 一次写好胜过分散在多个 ad-hoc 决策。

### D5: 87 条 backlog 抽取剩余 38 条精简清单

**决策**：4-19 项目审查产生的 87 条 backlog 已 close 25 条，剩 62 条评估后筛掉过期 / 重复，留 38 条精简清单 → `00_admin/漏洞_剩余清单_2026-04-21.md`。

**为什么**：原 87 条清单太大，下次会话不知从哪开始。38 条带 D / S / T-L 三段权限标签，可直接接力。

## 心路历程

### 认知 1：命名是产品身份，不是技术决策

**v0.4.0 之前的 5 个月**，DMSD 一直只是"开发代号"。Demo / 面试 / 介绍系统时，没有 30 秒可发音、有故事、有情感锚点的词。

**4-21 晚 itsuki 主动提**："这个系统应该有个名字"。CC 提了几个候选（中英日各几个），最终 itsuki 选 **Tomoshibi（灯火）**。

**关键判断**：
- **不放弃 DMSD** — 项目代号、git 历史、内部文档继续用 DMSD（命名一致性）
- **新增 Tomoshibi 作面向用户层** — App / Web / 终端品牌全部 Tomoshibi
- **双层不冲突** — 内部技术世界（DMSD）和产品世界（Tomoshibi）有不同的需求

> **itsuki 自补**：选 Tomoshibi 那一刻在想什么？(_AC 面试用 — 80 字内自由写_)

### 认知 2：spec 闭合的工程节奏

S 系列 14 条 spec 漏洞如果按"一条修一个 patch"会产生 14 个 patch tag。但 **v0.4.0 选择把它们攒到一次 minor close**。

**理由**：
- 单次 patch 改 spec 的修补成本很低（grep + 改字段 + 加注），但**版本号管理成本**（CHANGELOG / 同步 / tag）固定。一次 minor close 14 条比 14 次 patch 高效 14 倍
- spec 修补本质是"补漏" — 应当看作一次性的"消除技术债工作量"，不是"持续 incremental"

**和软件开发对比**：spec 修补 ≈ 重构 commit，应当攒批做。生产代码 = 业务功能，按用户需求节奏 incremental。

### 认知 3：minor wip 状态有 deadline

**v0.4.0 的最大教训不是 spec 修补本身，是 [0.4.0-wip] 状态拖了 9 天没 close。**

时间线：
- 4-21 16:32：commit eeb39d2 标 `[0.4.0-wip]` — v0.4.0 开工
- 4-22 17:00：实际产出 close 节点（最后一个 spec 修 commit）
- 4-29：SOP 建立后才追认 tag

中间 7 天（4-23 → 4-29）发生了 demo-4-28 sprint 全部内容（应归 v0.5.0），但因为 [0.4.0-wip] 没 close，新 commit 边界混乱。

**SOP §10 30 秒决策树**就是为这个教训设的 — 会话结束前必跑"是否该 close wip"判断。

> **itsuki 自补**：你为什么 9 天没注意到 wip 状态在拖？(_AC 面试 #4 自己认识素材_)

### 认知 4：API_CONVENTIONS 5 倍扩写不是过度设计

48 → 240 行（5 倍）会让人觉得"过度设计"。但 v0.4.0 的判断：

- API 约定**写一次后所有人复用**。后端 / 老师 Web / iOS / Android / Pi 点呼机 5 个端点都要查约定
- 写得太简（48 行）= 5 个端点各自猜 → 最终发现 5 套不兼容（典型分布式系统反模式）
- 240 行**不是为了完美，是为了消除歧义**。每条约定有 "为什么这样" 的简短理由

**面试可用原话**（Q3 问题解决）:
> "我把 API_CONVENTIONS 从 48 行扩到 240 行，5 倍。有人会说过度。但我的判断是：API 约定写一次后所有 5 个端点都要查 — iOS、Android、老师 Web、后端、Pi 点呼机。如果约定写得简，每个端点都自己猜，最终 5 套不兼容。240 行不是为了完美，是为了消除歧义。"
