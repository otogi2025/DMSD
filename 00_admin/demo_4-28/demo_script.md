## 1. 开场 pitch（30 秒）

**地点**：请管理员坐下 / 把 iPad 递给管理员

> "谢谢老师今天抽时间。我做了一个宿舍点呼的电子化系统，想请您看一下能不能取代现在的纸质点呼。
>
> 这个系统分三部分：**学生手机 App**、**老师 Web 管理端**（就是您手上 iPad 里这个）、**点呼机**（桌上这个 Raspberry Pi）。
>
> 今天我演示一下完整的点呼流程和主要管理功能，大概 12 分钟。有问题您随时打断我。"

## 2. 介绍 Web 菜单（2 分钟）

**动作**：指着 iPad 左侧菜单，从上往下介绍

> "这是老师 Web 的主菜单。
>
> 最上面 **"点呼"** — 开始点呼和查看实时座位表。
>
> **"通知中心"** — 所有待处理的事项汇总：待审批的申请、待审核的扫除、预警名单都在这里。
>
> **"纪律处分"** — 学生扣分累计、月度排名、罚扫和禁足名单。
>
> **"申请中心"** — 学生提交的归国申请、归县申请、外宿酒店申请、出租车预约，都在这里审批。
>
> **"扫除审核"** — 学生扫除完拍照上传，您审核后可以产生抵扣额度。
>
> **"公告 / 活动 / 巴士"** — 发公告、活动日历、巴士时刻表。
>
> **"宿舍互动治理"** — 匿名建议、宿舍墙、点歌、遗失物专区、快递通知，这些学生生活功能都在这里管理。
>
> 最下面是搜索，可以按学生名字或日期查所有历史记录。
>
> 我一项项点给您看。"

**动作**：快速点 2-3 个 Tier 2 菜单（扫除审核 / 遗失物 / 宿舍墙），每个停留 3-5 秒让管理员扫一眼页面，然后：

> "这些是完整的功能面。核心的点呼流程我重点演示。"

## 3. 开始点呼 + 学生 tap 签到（3 分钟）⭐ 核心

### 3.1 老师开点呼

**动作**：引导管理员点击"点呼" → "开始点呼"按钮

> "第一步，您点'开始点呼'。这就进入了实时座位表。"

**iPad 显示**：座位表，所有学生灰色（未签到）

> "现在所有学生都是灰色，表示还没签到。"

### 3.2 学生 tap

**动作**：itsuki 拿 iPhone，走到点呼机前

> "现在我作为学生，拿手机碰一下点呼机上这个 NFC 贴纸。"

**动作**：iPhone 靠近贴纸 → 等待 2-3 秒

**发生的事**：
- iOS Shortcuts 自动触发 → 后端 POST /api/checkin
- 后端 WS 推送 → iPad 座位变绿（itsuki 的座位）
- Pi 接到 WS → 喇叭出声："itsuki 签到成功"

**动作**：指 iPad + 听喇叭

> "看，我的座位瞬间变绿了，点呼机也喊出了我的名字。
>
> 这个喊名字的功能是故意设计的防作弊 —— 如果有人用别人的手机来代签，喇叭喊的是被代签学生的名字，其他学生一听就知道不对，会举报。这是我的一个原创设计。"

### 3.3 讲颜色含义

**动作**：指 iPad 座位表

> "座位表颜色的意思是：
> - **绿色** = 准时到
> - **黄色** = 迟到
> - **红色** = 超时仍未到，缺席
> - **灰色** = 点呼进行中，还没签到
> - **蓝色** = 免点呼（批假了）
> - **红色十字叠加** = 提交了健康问题（发烧、不舒服等）
> - **橙色问号叠加** = 提交了'本次不去点呼'申请，等您审批"

## 4. 座位手动改判（2 分钟）

### 4.1 场景引入

> "万一有学生手机坏了或者忘带了，怎么办？您不用打断点呼回教室改纸，在这里直接改就行。"

### 4.2 操作

**动作**：引导管理员点某个灰色座位（一个未签到的学生）

**弹面板**：选状态（准时 / 迟到 / 缺席 / 免点呼）+ 填原因

**动作**：引导管理员选"准时" + 填"手机坏了，老师口头确认在场" → 保存

**iPad 响应**：座位立刻变绿，右下角小标记"M"（manual override）

> "所有手动改判都会记录下来，什么时候、哪个老师、什么原因改的，后台都能查。"

## 11. 管理员可能的追问（备用应答）

### Q1: 学生拍照 URL 发给朋友代签怎么办？
→ 见 `ST25DV_fallback.md §5.2`（讲上线版 ST25DV 动态 nonce）

### Q2: 学生换手机怎么办？
> "学生新手机下载 App 登录时，旧手机的密钥会自动作废。换机不用找老师，但最开始注册账号时需要老师扫码面签确认身份。"

### Q3: 没手机的学生怎么办？
> "有两种方式：一种是发 NFC 卡（NTAG215 空白卡），学生贴个自己的名字贴纸，在点呼机上刷卡签到。另一种是老师管理员后台代录。大多数人会用手机，但宿舍肯定有 1-2 个没手机的，这两个通道都有。"

### Q4: 点呼机坏了怎么办？
> "上线版是 4 台点呼机分布在宿舍不同位置，1 台坏了其他 3 台还能用。如果全坏了，可以降级为老师 iPad Web 直接手动勾选到齐（就是刚才我演示的手动改判）。"

### Q5: WiFi 断了怎么办？
> "点呼机会本地缓存签到记录，WiFi 恢复后自动上传。老师 Web 也能离线查看之前的记录。"

### Q6: 学生在别的学生手机上装 App 代签？
> "App 注册时用 Apple 的 Secure Enclave 硬件安全芯片生成密钥，这个密钥绑定手机硬件取不出来。一个手机登录 A 同学账号后，给 B 用就必须重新登录 B 的账号 — 但同时 A 的旧密钥就作废了，A 签不了。相当于'一部手机同时只能是一个活跃学生的签到工具'。"

### Q7: 一个人同时持有多个手机怎么办？
→ 这个场景 demo 没覆盖完整风控，老实答：
> "这个边缘情况我想法是：每个学生注册只能绑一个 '当前活跃设备'，换新设备旧设备自动作废。如果两个设备同时想签到，后来的被作废那个就失败。我会在上线前补全这块策略。"

### Q8: 系统成本能细一点吗？
→ 点呼机单台 ¥6500 日元（Pi 3A+ 本体 + 配件 + NFC 外设）× 4 = ¥26000 日元。NFC 卡 120 张 × ¥40 = ¥4800 日元。后端服务器 ¥500 日元/月。总计初始 ¥30800 日元 + 月 ¥500 日元。

### Q9: 学生隐私 / 数据保护？
> "数据存在我个人租的服务器上，GPDR / 个人情报保护法的要求我会按规范做。毕业交接时会完整交给下一届接手的学生或老师。"

### Q10: 这个系统维护谁来做？
> "我毕业之前我自己维护 + 带一个学弟学妹跟着学。毕业前会把所有运维文档、账号密码、服务器凭证、Android App 签名证书打包交接。我会设计整套交接流程保证连续性。"
