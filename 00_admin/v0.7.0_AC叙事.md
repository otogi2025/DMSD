## 4. 学到了什么(自己認識)

### 4.1 多 AI 会话并行 = 工程团队微缩

把 1 个 itsuki + 3 个 Claude Code 会话当成"4 人小团队"管理:
- 文件锁定边界 = git 分支策略
- WIP.md §🔄 = 站会
- raw 各占 § 编号 = 个人 log
- commit message 前缀 = 责任归属

**这种思路完全可以迁移到正式工作团队**(每个工程师占一块,主写区不重合,集成时做 merge 判断)。AC 价值高 — 中学生独自把多 AI 协作做成"团队工程"。

### 4.2 ✅ 等定义判定标准 = 项目方法论决策权(不是 CC 自定)

CC 是执行器,itsuki 是方法论决定者。"✅ 设计完成"的标准本身就是"我们项目认为什么算完成"的元决策,属于 itsuki 拍板范围。

**这次失败 = 提醒未来遇到判定标准 / 沟通方式 / 元思考时,先问不假设**。

### 4.3 ⭐⭐⭐ 信息源选择 — 文字 vs 物理事实

老师 LINE 文字 = 当时记忆的版本(可能漏 / 误)
实物表 = 实际运营的版本(权威)

**链式推理的起点错了,后面全错**。CC 之前 chain 推测全被推翻就是因为起点是 LINE 而不是实物表。

→ **教训**: 涉及"事实"的问题,**优先看物理证据**(实物 / 截图 / 数据库 schema),而不是 chat 文字。文字适合记录"决策"和"意图",不适合记录"事实"。

### 4.4 单源真值原则的二阶应用

v0.6.0 学到"档案体系治理"(整理一次不够,要建立规范)。
v0.7.0 应用:
- 起手不要新建 REQUIREMENTS.md(既存 LOG 已覆盖)
- BACKEND_DESIGN_LOG 新建做"对称"(iOS / Web 已有 LOG → backend 也应有,文件命名一致)
- 实装清单 append 到 §11(不另起文件)

### 4.5 沟通规则 #6 = 让 AI 主动适配人类节奏

之前每次堆术语 itsuki 都要纠正一次。规则 #6 落地后,**未来不用每次说,CC 自己会展开**。

→ 这是 v0.6.0 "AI 主动识别元思考" 模式的延续(从被动响应触发到主动识别模式)。

## 5. 失败的地方 / 还能更好(失敗・改善余地)

"#21 老龄 R2 一本道 UX" — 4 个术语堆叠,itsuki 看不懂。

轨道 C 起手按 prompt 字面执行,没先读 iOS LOG / Web LOG → 新建重复文件。

**改进**: 新建任何文件前,**先 grep 既存档案体系**,看是否已经有同类档案。这是 v0.6.0 学到的"档案体系治理",这次又犯一次。

### 5.4 实物 evidence 应该早一点要

CC 在轨道 C 起草时才发现 chain 推测错。如果在 v0.6.0 起草 §7.2 时就先问 itsuki "你有实物表吗?",可以省掉一轮重写。

**改进**: 涉及 stakeholder 实际运营的 spec(承认 chain / 时刻表 / 流程),**优先要实物 evidence**,不要靠 chat 推测。
