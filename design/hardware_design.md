## 1. 总览

Tomoshibi 点呼系统的硬件体系由 4 类物理设备构成：

| 类别 | 数量 | 位置 | 核心职责 |
|---|---|---|---|
| **点呼机** | 4 台 | 宿舍楼层（具体位置 TBD）| 读 NFC + 发 HTTP + 接 WebSocket + 播报 + 亮灯 |
| **NFC 卡** | ~120 张 + 备用 | 每学生 1 张 | 路径 A 的签到凭证（UID 绑学生账户）|
| **动态 NFC 贴纸** | 4 个（每台点呼机 1 个）| 贴在点呼机外壳 | 路径 B（iPhone / Android）的签到入口（2026-06-02 反转为「手机写入身份数据的中转邮箱」，详 §2.3）|
| **老师端设备** | 1 台 | 管理室/现场 | 打开管理网站 → 点呼开始/结束 + 看座位表 |

### 架构原则（4-15 拍板）

- **thin client / thick server**：点呼机只搬运数据，业务判断全在后端
- **服务器是唯一判定者**：是否准时、是否在时间窗、是否缺席 —— 全由后端判定；判定用的时间戳是**点呼机打的 `swipe_time`**（NTP 校准），不是后端 `server_now`（2026-06-02 反转，详见 §2.3 + `flow_design.md`）
- 点呼机只负责：NFC 读写 + 打时间戳 + WebSocket/HTTP 收发 + 声光反馈（不做判定）

## 2. 点呼机（4 台）

### 2.1 主板：Raspberry Pi 3 Model A+ ✅（2026-04-21 推翻 Pi 4B 2GB）

**选型决策**：4-21 [Mac-demo-sprint] 会话（raw §16:00-16:15）
- 触发：itsuki 查淘宝实际市场价 Pi 4B 2GB ¥500 RMB/台（CC 原估价 ¥300 偏低），判定"太贵"
- 回炉对比 5 个方案（Pi 4B / Pi Zero 2 W / Orange Pi Zero 2W / 二手 Pi 3B / ESP32）
- 发现 Pi 3A+ 反而最合适（反直觉结论）

| 项目 | 规格 |
|---|---|
| 型号 | Raspberry Pi 3 Model A+ |
| CPU | Broadcom BCM2837B0 (4× Cortex-A53 @ 1.4GHz) |
| RAM | **512MB** LPDDR2（紧但够）|
| 联网 | **双频 2.4 + 5GHz Wi-Fi** + Bluetooth 4.2 |
| 以太网 | 无（无需）|
| USB | 1 个 USB 2.0 |
| GPIO | 40-pin（I²C / SPI / UART / PWM 全支持）|
| 音频 | **3.5mm 模拟音频口**（直接接小喇叭）|
| 操作系统 | Raspberry Pi OS (Debian based) |
| 开发语言 | Python 3 |
| 尺寸 | 65×56 mm |
| 采购价 | **¥6480 日元（日本 Amazon，demo 1 台）** / **估 ¥180 RMB（淘宝，部署 3 台）** |

**为什么 Pi 3A+ 反而最合适（反直觉结论）**：
- ❌ Pi 4B 2GB（¥500 RMB）：严重 over-spec（点呼机 thin client 用不到 2GB + 4 核 Cortex-A72）
- ❌ Pi Zero 2 W（¥180）：无 3.5mm 音频要外接 USB 音频卡（零基础挑战）
- ❌ Orange Pi Zero 2W：国产，软件生态弱，教程少踩坑多
- ❌ 二手 Pi 3B：故障率 + 老板子
- ❌ ESP32：无 Linux + 无 Python 完整 + 本地 TTS 几乎做不到（大坑）
- ✅ **Pi 3A+**：**最便宜含音频口**的官方 Raspberry Pi + **双频 WiFi**（比 Pi 3B 的单频 2.4GHz 更强）+ Raspbian 软件 100% 兼容（教程海量）

**USB/以太网都用不到的论证**：
- PN532 NFC 读卡器：I²C 接口接 GPIO，**不占 USB**
- ST25DV16K 动态贴纸：I²C 接口接 GPIO，**不占 USB**
- 点呼机 headless 部署（SSH 远程登录）：**不插鼠标键盘**
- 宿舍用 WiFi：**不需要以太网**
- → 1 个 USB 够用 + 以太网可省

**512MB RAM 的风险评估**：
- Raspbian Lite 空载 ~100MB
- Python + 主程序 ~50MB
- ~~pyttsx3 TTS ~30MB~~ → 已废：音频改后端预生成 wav 下发，点呼机只 `aplay` 播放（更省内存）
- NFC 驱动 + 网络栈 ~50MB
- 系统缓存/buffer ~100MB
- **总计 ~330MB，余量 ~180MB**（"紧但够"）
- **硬约束**：未来如果加人脸识别 / 视频流 / 本地大缓存 → 不够
- **但**：v1.0 范围内不做这些（thin client 原则）

**核心职责（thin client 约束下）**：
- 读 PN532 的卡 UID（路径 A）
- 通过 I²C 读 ST25DV16K 的 Mailbox 邮箱（路径 B；2026-06-02 反转：旧「写 NDEF URL」已废）
- 给数据盖 NTP 校准时间戳 → HTTP POST 签到到后端（点呼机连后端，手机不联网）
- WebSocket 订阅后端的播报 / 亮灯 / 删音频指令（带断线自动重连）
- 播放后端预生成的 wav 姓名语音（`aplay` → 3.5mm 小喇叭；不本地合成）
- 点亮 LED（绿/红）

**历史决策链**（完整留痕）：
- **4-15**：itsuki 砍 Pi 4B 4GB → Pi 4B 2GB（砍过度配置第 1 次）
- **4-20 议题 A**：拍板 Pi 4B 2GB × 4 = ¥1200 RMB（CC 估价偏低）
- **4-21**：itsuki 查实际市场价 ¥500/台 → 回炉 → **Pi 3A+ × 1（Demo 阶段）**（砍过度配置第 2 次）

**AC 叙事价值**：两次主动下压 AI 过度配置建议 + 按真实需求（thin client）量体裁衣。

### 2.2 NFC 卡读头：PN532 V3 模块 ✅（2026-05-08 itsuki 复核 + CC 上网查证后定型）

| 项目 | 规格 |
|---|---|
| 芯片 | NXP PN532 |
| 模块 | **PN532 V3 红板**（淘宝通用版,带 I0/I1 跳线 + DIP 开关切模式）|
| 接口 | **SPI / I²C / UART 三选一**（板上跳线切换）|
| 推荐接法 | **SPI**（I2C 在 Pi 上经验上不稳,SPI 最可靠 — 见 `dev/rollcall_device/ROLLCALL_DEVICE_DESIGN_LOG.md` §10-D4 待 itsuki 拍板）|
| 兼容卡型 | MIFARE Classic / Ultralight / **NTAG2xx 全系（含本项目 NTAG215）** ✅ |
| 读取距离 | 2-5cm 典型 |
| 供电 | 3.3V / 5V 兼容（从 Pi GPIO 取）|
| 接 Pi 接口（SPI 模式）| MOSI / MISO / SCK / SS / GND / VCC = 6 根杜邦线 |
| 采购价 | **¥26.7 RMB**（淘宝）|

**选型理由**：
- PN532 是 NFC 读卡器界的事实标准（vs 较新的 RC522 — RC522 不支持 P2P / NFC 标签写入）
- V3 红板比 Waveshare PN532 NFC HAT 便宜约 60% 且功能等同（HAT 直插 GPIO,但模块版用杜邦线开发期更灵活）
- 已查证 Waveshare 官方文档明确支持读 NTAG215 → 跟本项目学生卡选型对齐 ✅

**为什么不用 HAT**：
- HAT 直插 GPIO,但点呼机还要接 ST25DV16K（I²C）+ LED + 风扇,GPIO 占用规划上需要混合接,排针式模块 + 面包板 + 杜邦线更灵活
- 学习层面：模块 + 跳线让 itsuki 看清每根线干嘛,HAT 黑盒度高（AC 叙事:「我亲手接的每一根线」）

### 2.3 动态 NFC 贴纸：ST25DV16K ✅（上线版）/ NTAG215 静态（4-28 demo 阶段）

**选型决策**：4-20 议题 A（raw §16:00 方案 B 定型）

**⚠️ 2026-04-21 demo 阶段降级说明**：
- ST25DV16K 淘宝空运 7-10 天，4-28 demo 前到不了
- **Demo 阶段替代方案**：用 NTAG215 静态贴纸 + iOS Shortcuts Automation（NFC 触发自动调签到 API）。具体配置 = 在静态 NTAG215 上写固定签到 URL，iPhone 碰一下触发 iOS 快捷指令自动发请求。
- **影响**：Demo 阶段 URL 固定（可复制代签，不演示这个漏洞）；用户体验（iPhone 碰一下）100% 对齐上线版
- **⚠️ 上线版工作模式 2026-06-02 已反转**（手机从「读」改「写」，itsuki 拍板）→ 见下方「核心工作模式」。原「nonce 每 10 秒刷新」逻辑作废，防代刷机制待重新设计
- Demo 日后 ST25DV16K 到货 → 迁移零用户侧改动（换贴纸物理即可，iOS Shortcuts Automation 不需改）


| 项目 | 规格 |
|---|---|
| 型号 | ST25DV16K（STMicroelectronics）|
| 模块厂商 | 极客创享（淘宝）/ Adafruit / SparkFun 等 |
| EEPROM 容量 | 16 Kbit（2KB）|
| 接口 | I²C + Qwiic/STEMMA（4-pin JST-SH 即插即用）|
| 读取距离 | 2-5cm（典型）|
| 写入寿命 | 100 万次 @ 25°C |
| 数据保留 | 40 年 |
| 供电 | 3.3V（从 Pi GPIO 取）|
| 采购价 | ¥25 RMB/个（中国淘宝）|

**为什么选 ST25DV（2026-06-02 反转后理由更新）**：
- iOS 不开放普通 App 把 iPhone 模拟成「一张被读卡器读的卡」（HCE = Host Card Emulation 主机卡模拟，iOS 只给钱包/门禁特批 App）→ 没法让 iPhone 直接被 PN532 读 → 需要一个「手机能写、树莓派能读」的双界面芯片做中转
- ST25DV 正是双界面：一面 NFC（手机隔空写）+ 一面 I²C（树莓派有线读），且带 Mailbox（邮箱缓存 — 256 字节临时存储区）支持手机→树莓派快速传递
- 静态 NTAG215 只能被读、不能当中转邮箱 → 反转后用不上
- ⚠️「iOS HCE 受限」CC 未实测，下单/写码前 itsuki 找懂 iOS NFC 的人再确认一次
- 〔历史·旧方案理由〕原选 ST25DV 是为了「I²C 每 10 秒刷新 EEPROM 换 nonce、手机读到的 URL 10 秒失效」防 URL 复制代签 — 6-02 手机改「写」方后此理由作废，保留作 AC 假设崩证据链

**为什么选 16K（不是 4K / 64K）**：
- 〔反转后〕Mailbox 邮箱固定 256 字节，手机一次写的 payload（student_id + event_id + 可选签名 + version）远小于此 → 容量对邮箱不是约束
- 16K = 2KB EEPROM 留余量（未来扩展）；价格相同（¥25）→ 选最大容量

**核心工作模式 ✅（2026-06-02 itsuki 拍板架构反转 — 手机从「读」改「写」）**：
- Pi 3A+ 通过 I²C 总线连 ST25DV16K（4-21 主板从 Pi 4B 改 Pi 3A+ 后顺改）
- 开机时 Pi 的 Python 代码初始化 ST25DV：打开 Mailbox 功能 + 配置 GPO 引脚中断（收到 NFC 写入就把电平拉低 = 硬件门铃）
- 学生 iPhone App 把学生身份数据通过 NFC 写进 ST25DV 的 Mailbox（256 字节邮箱缓存）
- ST25DV 收到数据 → GPO 引脚电平跳变 → Pi 监听到中断 → 通过 I²C 读走 Mailbox 数据 → 发清空指令复位
- Pi 给数据盖上经 NTP（网络时间协议，自动跟标准时间服务器对时）校准的时间戳 → 发后端
- **树莓派不再每 10 秒写 nonce**（旧方案逻辑作废）

> **⚠️ 架构反转对防代刷的影响（2026-06-02 — CC 初判翻车、itsuki 当场纠正后修正）**：
> CC 初判「反转砍掉一层防御、留三缺口（含防重放 nonce 断链）」→ itsuki 用架构常识推翻：**手机根本不联网，只有点呼机跟后端通信**。重新厘清：
> 1. 旧 nonce + URL 那套，是为「手机联网、把签到 URL 远程 POST 后端」设计的防远程代签。新方案手机不联网 → 没有「手机 POST 后端」这回事 → **这套防御不再需要（是简化，不是缺口）**。架构反转让攻击面变小。
> 2. 复制学号 / 借卡 / 借手机本质都是「拿别人凭证替刷」，**必须到现场**（NFC 近场几厘米）→ 被「现场播报姓名 + 老师看脸」防（itsuki 4-12 既定设计）+ v2.0 人脸识别自动化。这类攻击路径 A 实体卡同样有，不是反转新增。
> 3. 实体卡 NTAG215 的 UID 可克隆是老问题（TODO 已列 NTAG424 DNA 替换），跟反转无关。
> 4. **真正要做的传输安全（跟反转无关、本来就要做）**：点呼机↔后端用 HTTPS（带加密的网络传输）+ 点呼机持设备密钥认证 → 防有人冒充点呼机或截获重发请求。「防重放」属于这一层、点呼机参与，不是手机侧。
> 5. 可选增强（优先级低，攻击要到场被看脸防）：手机写的数据带签名防造假学号，v1.1 可议。
> → 连带文件本轮未改（旧 nonce 方案在新架构多余、待简化，非紧急）：`flow_design.md` / `NFC防代刷_后端立项施工计划.md` / `system_features.md` / `ROLLCALL_DEVICE_DESIGN_LOG.md`

### 2.4 反馈设备 ✅（2026-05-08 itsuki 复核 + CC 上网查证后定型）

#### 2.4.1 LED 状态灯

> **2026-06-04 itsuki 拍板更新（日本本地实际采购 + 驱动方案）**：① 不用「LED 模块套装」，改买**裸 5mm LED ×4 色 + 220Ω 电阻 + 面包板**（秋月本地货）；② 驱动从「3.3V GPIO 直驱 / 高电平点亮」改为 **5V 驱动 / 低电平点亮（A 方案）**。原因：绿/蓝/白 LED 工作电压 Vf≈3.1-3.2V（绿 OSPG5111A 查证秋月官方页 g112117 = 3.1V），3.3V GPIO + 220Ω 只给约 0.5-0.9mA 几乎不亮；改 5V 驱动后约 8.6mA 全亮。接线细节见 `dev/rollcall_device/点呼机接线说明.md §4`。

| 项目 | 规格 |
|---|---|
| 元件 | **裸 5mm 砲弾型 LED ×4 色 + 220Ω 限流电阻 + 400 孔面包板**（秋月本地货）|
| 型号 | 红 OSR5JA5E34B / 绿 OSPG5111A / 蓝 OSUB5111A-ST / 白 OSW54K5B61A |
| 接 Pi（**A：5V 驱动 / 低电平点亮**）| 长腿(正极)→220Ω→**5V 针(pin2/4)**；短腿(负极)→**GPIO 信号针**（红=17 / 绿=27 / 蓝=22 / 白=23）。代码低电平=亮 |
| 状态映射 | 蓝=待机 / 绿=签到成功 / 红=失败 / 白=系统启动中 |
| 采购价 | 秋月：红 ¥10 / 绿 ¥40 / 白 ¥250(10入) / 蓝 ¥180(10入) / 220Ω ¥150(100入) |

### 6.0 点呼机内部物理布局（2026-06-03 加 — 防双芯片同频干扰）✅

PN532（读实体卡）和 ST25DV（收手机）都发 13.56 兆赫无线电，紧贴会互相干扰。布局铁律：
- **两芯片物理间距 ≥ 10 厘米**：树莓派居中，PN532 一翼、ST25DV 另一翼，各距中心约 5 厘米。
- 外壳成品长约 **15-18 厘米**，左「实体卡区」右「手机区」分流；杜邦线（15-20cm）够用。
- 详见 `flow_design.md §3` + `ROLLCALL_DEVICE_DESIGN_LOG.md` 程序架构。
