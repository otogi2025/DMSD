# Session Wrap Skill — DMSD 会话收尾完整流程

> **2026-05-04 改名背景**：本 skill 原名 `ac-record`，但 §5.5 已经包含 9 节收尾动作（不只是 AC dump，还有 git / WIP / TODO / commit 起草）。itsuki 反问后拍板：收尾 skill 不只是 AC 相关，还有文件联动 / 设计同步 / memory 维护等。改名 `session-wrap` 反映实际作用。
>
> **核心理念**：收尾 = 让下次会话能干净接上 + 当下决定不漏到风里。具体分两层：
> 1. **AC 素材层**：宁多勿少，最后再筛（任何 1% 可能用到的素材都记录，月度回顾时再筛选）
> 2. **工程层**：文件联动 / git / 设计同步 / 跨 repo / memory / WIP / TODO 全过一遍
>
> **⭐ 主要工作模式（2026-05-04 itsuki 拍板）**：itsuki 说「**收尾**」/「**总结一下今天**」/「**记一下今天发生的事**」 → CC 立刻执行 §5.5.0 全量扫描算法，**从会话第一条消息开始扫到最后**，找出所有候选素材 dump。**不要等关键词，不要只看最后一段**。详见 §0.4。
>
> **来源**：基于合格者报告分析（小松潜水无人机 / 间瀬校内 LAN / 匿名 B 未踏→Alice_Maker）+ DMSD 实战提炼，2026-05-04 由 v3 升级到 v4 做成 skill / 同日改名 session-wrap 扩展工程层。

## §0 三条根本性原则

### 0.1 叙事策略：raw 阶段记真实，月度筛选时归功

**raw/ 阶段格式（dump 时 CC 写）**：

> "AI 提出方案 X。我评估后[采纳 / 拒绝 / 改造为 X']，理由是 Y。"

2 种判断归属情况：

| 情况 | raw 写法 |
|---|---|
| AI 提方案，itsuki 采纳 | "AI 提出 X。我评估后采纳，因为 Y" |
| AI 提方案，itsuki 改造后采纳 | "AI 提出 X。我改成 X' 后采纳，因为 Y" |

**为什么这样**：
- AC 评的是判断力 / 学习能力，AI 推荐 → itsuki 评估采纳本身就是判断
- raw 是 git 可见的，写「AI 提的我评估采纳」既诚实又强调判断
- 月度筛选时（写自我推荐书 / AC 叙事文档），可以改写为更突出 itsuki 判断的版本（"私はXXの理由でYYを採用した"）

**绝对不做（2026-05-04 itsuki 拍板）**：
- ❌ raw 不写「我未完全理解就采纳」类自我贬低标记 — raw 是 git 可见的，这种标记**本身就变成翻车证据**。itsuki 的逻辑：自己面试前会评估懂不懂，不需要 dump 系统帮他"标记"，真不懂会主动问 / 学。
- ❌ raw 不写「我设计了 X」「我决定 X」抹掉 AI 提案痕迹 — 失去判断过程的证据

### 0.2 最大化捕捉

每次会话结束 CC 必须 dump 所有候选素材到 `05_logs/raw/`，**包括看起来"没什么大事"的日常工作**。

理由：
1. AC 评委要看的是"持续在动手"的轨迹，碎片累积起来就是叙事
2. 月度回顾时筛选，比当场判断"这条值不值得记"更准确
3. **当时觉得没用的，后来可能成为关键** — 比如「今天学会 git push」配合「3 月之前我都用文件覆盖管理代码」back story → 「我对版本管理认知的根本转变」

如果一次会话真的纯执行类工作（rm/mv/重启），明确标"今日仅执行类工作" — 这本身也是记录，方便月度回顾时看出活跃度。

### 0.3 CC 主动发现的也算 itsuki 的素材

CC 看到 itsuki 不知道的问题（技术 / 流程 / AC / 学习方法 / 自我管理）→ 不只当场告诉他，**还要主动 dump 到 raw/ 当成素材**。

理由：即使是 CC 发现的，过程也算 itsuki 的（他有了"通过工具发现问题"的能力 + 他做了"采纳/拒绝/修改"的判断）。

特别重要：**"原本不知道，通过 CC 才知道"** 这类素材 — 这是 itsuki 独有的成长路径（详见 §3 模式 5）。

### 0.4 ⭐ 主要工作模式 = 收尾全量扫描（2026-05-04 itsuki 拍板）

> itsuki 现实情况：**自然对话里几乎不说"拍板/反思/学到/纠正"这类词**。所以「关键词触发」对他不是主要工作模式，**「收尾时 CC 全量扫描整个会话上下文」才是主要工作模式**。

**两种工作模式分工**：

| 模式 | 触发 | CC 行为 |
|---|---|---|
| **⭐ 主模式 — 收尾全量扫描** | itsuki 说「收尾」/「总结今天」/「整理一下今天」/「dump 一下今天」 | CC **从会话第一条消息开始按时间顺序过一遍**，对照 §2 5 级清单 + §1 模式 5 + §4 6 经典模式，找出所有候选素材，按 §5.5.0 全量扫描算法 dump |
| **次模式 — 对话中即时 dump** | 关键词命中 / CC 主动发现重要素材 | 当下片段立刻 dump 那一段，**不必等收尾**（避免错过细节） |
| **⭐ 今日总结模式（2026-05-21 itsuki 立项加）** | itsuki 说「今日总结」/「今天总结」/「写日记」 | CC **先**跑主模式全流程产出当前会话总结，**再**读今天所有会话总结的 md 合并写「今日总结」md。详见 §5.5.14.3 |

**铁律**：
- ❌ CC **不能**只 dump 最后一段对话就交差 — 收尾的本质是**对整个会话负责**
- ✅ CC 收尾时**必须从会话第一条用户消息扫到最后一条**，全量识别候选素材
- ✅ itsuki 不说关键词不等于没素材 — CC 自己识别（详见 §1 模式 5 触发词 + §4 6 经典模式）

## §1 itsuki 的素材 DNA — 模式 5（认知改变型）

> **这是 itsuki 最强的、独有的素材类型 — 必须重点挖掘**

### 1.1 为什么这是 itsuki 独有

合格者报告里，大部分学生是「我自己一步步学到的」。**itsuki 是「我通过 AI 协作学到的」** — 这个独特路径需要专门叙事。

模式 5 的力量：把"我以前不会"变成"我现在的方法论" — 不是炫耀终点知识，而是展示**通过工具实现自我升级**的能力。

### 1.2 触发关键词（CC 听到立刻挖深）

itsuki 嘴里出现以下词 → CC **必须**当场追问 + dump：

- 「以前我...」「之前我都是...」「我原本是...」
- 「我之前以为...」「我以前不知道...」
- 「原来这样啊」「居然是这样」「现在才知道」
- 「这个我没想到」「这个角度没考虑过」

### 1.3 追问 4 句话（挖完整素材）

听到上面任一关键词 → CC 必须问完这 4 句：

1. **「之前你具体怎么做的？」** — 还原错误/低效做法
2. **「什么时候 / 通过什么发现是错的？」** — 转折契机
3. **「正确的做法是什么？」** — 新方法论
4. **「现在为什么这样做更好？」** — 深层理解

### 1.4 经典示例（合格者级别）

> 之前我用「复制文件夹+改名」的方式管理代码版本，每改一次新建一个文件夹叫 "DMSD_v2_新版本_最终版_真的最终版"。结果几个文件夹之间的 diff 记不清，文件夹大小爆炸。
>
> 通过 AI 了解到 Git 后，我开始用 commit 记录每次修改，用 tag 标记版本，用 branch 做实验性改动。这让我意识到，软件开发的"版本管理"不是单纯的文件备份，而是一套关于"如何让代码状态可追溯、可回滚、可分支"的方法论。
>
> 现在我已经习惯用「小 commit + 清晰 commit message」的方式工作，并把这个习惯也用到了项目文档管理上。

这一段就是合格者级别：
- ✅ 具体的"之前的错误做法"（教授知道你来自哪里）
- ✅ 清晰的认知转变契机（AI）
- ✅ 从具体做法上升到方法论的层次
- ✅ 有迁移应用（用到了文档管理）

### 1.5 itsuki 的元认知金句（2026-05-04 拍板）

> **「这种事情没有体验，别人提醒我也不会知道」**

含义：他不仅不知道 X，他**不知道存在 X 这个东西要去问** → CC 必须主动扫描 + 主动提（详见 memory `feedback_proactive_diagnose_unknown_unknowns.md`）。

每次 CC 主动扫描发现 itsuki unknown unknowns → 立刻提 + dump 到 raw → 模式 5 又多一条。

## §2 什么值得记录 — 5 级清单

### 2.1 1 级 — 必须记录（核心 AC 素材，每条都不能漏）

#### 2.1.1 任何"发现问题→解决问题"循环

完整循环 4 要素：
- 注意到了什么不对劲（症状）
- 分析了什么原因（哪怕错了）
- 试了什么方法
- 结果如何（成功/失败都要）

例：「实装时发现签到接口在并发下会写入重复数据」/「跑回测时 PF 高得不正常，查了发现是前视偏差」

#### 2.1.2 任何技术判断的"为什么选 A 不选 B"

合格者报告里出现频率最高的写法。每次技术选择记下：
- 候选方案有哪些
- 各自优缺点
- 为什么最后选这个

例：「为什么 FastAPI 不 Flask」「为什么 NFC 不 QR」「为什么 PostgreSQL 不 MySQL」

哪怕你的"判断"是"AI 推荐了所以用了"，也要记 — 但要按 §0.1 第 1 / 2 / 3 种格式区分清楚。

#### 2.1.3 任何失败 / 卡点 / 推翻重做

合格者报告中失败素材占比 **>50%**。失败素材必须按 4 要素记：
1. 失败的事实（具体到什么程度）
2. 具体技术原因（不是"我能力不够"，而是"OOP 没掌握导致代码意大利面化"）
3. 当时尝试过的解决方法
4. 教训 / 下一步怎么改

#### 2.1.4 "原本不知道，通过 AI / 外部才知道"的认知改变

→ **见 §1 模式 5 详细规则**

#### 2.1.5 和 AI 意见不一致或纠正 AI

itsuki 反驳 / 修正 / 坚持不同方案 → 必须记。

理由：直接证明 itsuki 不是被 AI 牵着走，而是有自己的判断。

例：「AI 提议方案 A，itsuki 坚持 B 并说出了理由」/「AI 写了段代码，itsuki 指出 bug」/「AI 说应该这样，itsuki 查了资料发现 AI 错了」

#### 2.1.6 关键设计决策

任何影响系统架构的决策。哪怕事后改了，也要记下当时为什么这么决定。

例：数据库表结构变更 / API 设计选型 / 认证方式选择 / 前后端分离策略

### 2.2 2 级 — 强烈推荐（次核心）

- **学到的新概念 / 新工具 / 新语法** — 哪怕基础知识，配合 back story 变成成长叙事
- **工程方法论的转变** — 不是技术，是"做事方式"的改变（"先写代码再改" → "先写文档定义清楚再写代码"）
- **与他人的技术性对话** — 老师 / 同学 / 网友 / 社区任何技术讨论
- **自我管理 / 学习方法的改进** — 元层面"我怎么学习/工作"
- **推翻自己之前的判断** — "我之前以为 A 是对的，现在发现 B 才对"

### 2.3 3 级 — 可以记录（边缘素材，1% 可能用到）

- 阅读 / 视频学习记录
- 项目周边活动（CTF / 技术交流会 / 开源讨论）
- 灵感 / 未来想法（标 `[未来]`）
- 资源工具的发现和评价

### 2.4 4 级 — 看起来没用但要记（潜在素材）

- 日常工作的小决定（变量命名 / 文件位置 / 错误信息文案）
- 困惑和纠结（没解决的问题、想不清楚的点）
- 时间管理 / 状态记录（工作量证据）

### 2.5 5 级 — 不需要记录

- 寒暄 / 闲聊
- 和项目完全无关的话题
- 纯执行命令（rm / mv / 重启），除非执行后出问题

## §3 怎么记 — 格式

### 3.1 文件位置

```
05_logs/raw/
├── 2026-05-04.md          ← 一天一会话 / 一个主题
└── 2026-05-04_治理.md     ← 一天多会话时加主题词
```

### 3.2 raw 命名规则

| 命名 | 何时用 | 例 |
|---|---|---|
| **日期版** `YYYY-MM-DD.md` | 一天一会话 / 一主题 | `2026-04-17.md` |
| **主题版** `YYYY-MM-DD_主题.md` | 一天多会话 / 需要区分 | `2026-04-20_v0.3.1发布执行.md` |

**判断规则**：
1. 开场默认用日期版
2. 发现同日已有 raw → 当前会话和那个是**同一会话延续**吗？
   - 是 → **append**
   - 否 → 开主题版
3. 主题词选**本会话核心产出**（如 `v0.3.1发布执行` / `NFC架构讨论`）

### 3.3 单条素材推荐字段（必填 2 项 + 推荐字段）

> **模板原则**：核心叙述 + **必填 2 项**（itsuki 原话 + AC 价值），其他字段按需。长会话允许按 § 自由叙述，不强制每条都套模板。

**最简版（短素材）**：

```markdown
## HH:MM [标签] 一句话主题

（自由叙述背景 / 经过 / 关键判断）

**itsuki 原话**：
> "..."

**AC 价值**：（这条对应核心问题 #X，展示了什么能力）

#AC候选 #标签
```

**完整版（重要素材 / 长篇 dump）**：

```markdown
## HH:MM [标签] 一句话主题

### 背景 / 触发
（讨论是怎么起来的，之前的 context）

### 经过
（具体发生了什么，按时间顺序）

### 关键判断 / 学到的东西
（核心内容 — 为什么这样选 / 学了什么 / 推翻了什么）

### itsuki 原话 ⭐ 必填
> "..."（不润色，原话引用，可多句）

### AC 价值 ⭐ 必填
- 对应核心问题：#X #Y
- 展示了什么：（具体能力 / 特质）
- 可能用在自我推荐书的哪个部分

### 后续 / 未解决
（如果有未完成的部分，留待后续补充）

#AC候选 #标签1 #标签2
```

### 3.4 标签体系

**主类标签**（每条至少一个）：

`[问题解决]` `[技术判断]` `[失败]` `[认知改变]` `[分歧]` `[设计决策]` `[学习]` `[方法论]` `[访谈]` `[自我管理]` `[推翻]` `[资源]` `[周边]` `[未来]` `[小决定]` `[困惑]` `[状态]`

**辅助标签**：

- `#AC候选` — CC 默认给所有 1-3 级素材打这个
- `#AC強候補` — itsuki 月度回顾时手动升级
- `#待补充` — 需要 itsuki 后续补完整理解
- `#交易系统` `#DMSD` 等项目标签

### 3.5 5 个 AC 核心问题（打标签用）

合格者报告分析得出的 6 个核心评价维度（itsuki 项目相关 5 个）：

1. **問題発見** — 我注意到了什么没人解决的问题
2. **技術判断** — 我做了什么选择，为什么不选其他方案
3. **問題解決** — 我具体做了什么、遇到什么障碍、怎么破的
4. **失敗と修正** — 哪里失败了、原因、怎么改
5. **自己認識** — 学到什么、能力边界在哪、认知改变

每条素材标对应核心问题号（可多个）。

### 3.6 详细度 — 按"思考层数"分级

| 层数 | 触发条件 | 关键词识别 | 目标篇幅 |
|---|---|---|---|
| 1 层（事实）| 做了 X | "做了"「commit 了」 | 100 字 |
| 2 层（理由）| 做了 X，因为 Y | "因为"「为了」 | 300 字 |
| 3 层（取舍）| 做了 X 而非 Z，因为 Y | "选 X 不选 Z"「权衡了」 | 500-800 字 |
| 4 层（反悔）| 原想做 X，发现 W，改做 Y | "原本想"「发现」「改成」 | 1000-1500 字 |
| 5 层（元思考）| 这次让我意识到我之前对 XX 理解不对 | "我意识到"「整个理解都不对」「重新想」 | 1500-2500 字 |

**判断标准是思考深度，不是事件大小**。一个看起来小的事件如果引发 5 层思考（"通过 Git 我意识到自己之前对版本管理的整个认知都是错的"），就该写 1500 字+。

### 3.7 itsuki 原话的处理

**绝对不润色**。原话再不通顺、再口语化、再有语病，都保留原貌。

理由：
- 原话是 itsuki 思维的真实 snapshot，月度回顾时能看出认知变化
- 写自我推荐书时直接拿原话改写，比拿润色过的"假 itsuki"语言更真
- 教授读自我推荐书会感受到「真人在思考」vs「AI 润色出来的标准答案」

**可以**：在原话旁加 `[CC 注：上下文是 XX]` 补充背景。

**不可以**：把"啊那个我觉得就是说"改成"私が考えるに"。

### 3.8 推测的处理

CC 观察到但不 100% 确定的部分用 `[推测]` 标记，让 itsuki 事后校正。

例：`itsuki 採用了方案 A。[推测：可能是因为他之前提到不熟悉方案 B 所需的库，但他没明说]`

**零推测 < 标记推测** — CC 完全不猜让 itsuki 自己补，最后会出现大段空白。CC 猜错了 itsuki 能校正 — 比 CC 不猜好。

## §4 经典素材模式（按合格者报告整理）

合格者报告里反复出现、教授高度认可的写法模式。CC 看到符合的内容要特别详细记。

### 模式 1：问题→尝试→解决（最基础）

合格者小松潜水无人机：
> 玻璃打孔会碎 → 学了边浇水边打孔的技术 → 解决  
> 打孔后渗水 → 树脂固定 + CAD 仿真 → 解决

**记录要点**：每个具体技术障碍单独成段，不混着写。

### 模式 2：假设崩了→继续调查→真因（最高级）

合格者間瀬校内 LAN 调查：
> 现象（网慢）→ 别人结论（带宽不够）→ 自己假设（中间链路慢）→ 调查（全 1Gbps，假设崩）→ 没放弃 → 真因（监控软件 UDP 碎片化）

**记录要点**：把「假设崩了但没放弃」的转折单独标出来 — **这是教授最爱的瞬间**。

### 模式 3：失败→分析→下个项目吸取教训（跨项目）

合格者匿名 B 的未踏 → Alice_Maker：
> 未踏二次落选 → 具体原因（没专注一个方向）→ 下个项目 Alice_Maker 聚焦"理想 AI 通话伙伴"

**记录要点**：失败和下个决定要明确画出因果链。

### 模式 4：v1→v2 版本演化（同一个东西迭代）

itsuki 的交易系统 V5→V8 / DMSD 的 RollCall spec v0.1→v0.2→v0.3 就是这个模式。

**记录要点**：每个版本之间的"为什么要升级"必须明确。

### 模式 5：原本不知道→通过 XX 知道→现在的做法

→ **详见 §1 全文**。这是 itsuki 主线模式，必须重点挖。

### 模式 6：技术判断的"取舍三角"

每次"为什么选 A 不选 B"时，记完整的判断结构：
- 备选方案的优缺点列表
- 决定性的判断标准（性能 / 成本 / 学习曲线 / 团队规模等）
- 最终选择和理由

合格者小松：「为了安価地长距离传输数据，选择了 LPWA 的一种 LoRaWAN」 — 一句话里包含了选择标准（安価 + 长距离）和具体选项。

## §5 CC 操作手册

### 5.1 会话开始

1. 检查 `05_logs/raw/YYYY-MM-DD.md` 是否存在，**不存在则创建空文件**
2. **不主动问** itsuki「上次有没有没记下来的事」— 按 CLAUDE.md「不主动催进度」铁律
3. 如果 itsuki 自己想补，他会主动说

### 5.2 对话中触发捕捉（次要模式 — 主要模式见 §5.5.0 全量扫描）

> ⚠️ 重要前提：itsuki 自然对话很少出现关键词，所以「对话中即时 dump」是**辅助机制**，不是主要工作流。**真正的素材识别在 §5.5.0 收尾全量扫描时做**。

任何符合 §2 中 1-4 级的内容出现 → CC 直接 dump 到当日 raw 文件，**默认不问同意**。

收尾时（§5.5.0）给 itsuki 列「今天 dump 了哪 N 条」清单，让他事后否决 / 删除 / 改写。

**例外 — 高敏感场景必须当场问**：
- 涉及 itsuki 个人隐私 / 他人评价 / 学校敏感事件 → 当场问
- 涉及 iCloud `03_素材_候选/` `04_素材_成品/` 写入 → 必须当场授权（按 §6 权限速查）

**为什么这个模式是辅助**：
- itsuki 不会主动说「我刚才拍板了 X」 — 他只会说「就这样吧」
- itsuki 不会说「我学到了 Y」 — 他可能说「原来这样啊」（这种间接表达）
- → 关键词匹配漏率高，**必须靠收尾时 CC 全量扫描兜底**

### 5.3 主动追问触发清单

挖掘"itsuki 没意识到自己说了什么有价值"的素材。CC 听到以下 → 主动追问：

| itsuki 说 | CC 立刻追问 | 挖什么 |
|---|---|---|
| "以前我..." | 「以前你具体怎么做的？什么时候改的？为什么改？」 | 模式 5 金矿 |
| "我之前以为..." | 「之前的理解是怎么形成的？什么让你改变看法？」 | 推翻判断素材 |
| "原来这样啊" | 「之前怎么理解的？现在的理解差在哪？」 | 学习素材 |
| 选了某技术没说理由 | 「为什么选这个？还考虑过别的吗？」 | 技术判断素材 |
| 调试 bug | 事后追问：「最后怎么定位的？试了哪些方向？」 | 问题解决素材 |

### 5.4 写代码时的强制说明

CC 写出以下代码时**必须停下来告诉 itsuki**：
- itsuki 没接触过的库 / API
- 非平凡模式（装饰器 / async / 元类 / 并发原语 / 复杂类型 / 设计模式）
- 跨多文件改动

话术：
> 「这段用到了 X。你熟悉这个吗？  
> 不熟的话我先讲一遍。  
> 等你能用自己的话解释了，我们记一笔到当日日志。  
> （标签：[学习] 或 [认知改变]）」

记录时让 itsuki 口述一遍自己的理解，CC 转写到正文。

### 5.5 会话结束 — 16 节详细动作（§5.5.0 全量扫描 2026-05-04 加，§5.5.14 daily-archive 2026-05-21 加，§5.5.15 decision-draft 2026-05-22 加）

#### 5.5.0 ⭐⭐⭐ 全量扫描算法（每次收尾必跑，比 5.5.1 dump 更前一步）

**触发**：itsuki 说「收尾」/「总结今天」/「整理一下今天」/「记一下今天发生的事」/「今天的事 dump 一下」 → CC 立刻执行下面 7 步。

**步骤**：

```
Step 1: 把整个会话上下文从第一条用户消息到当前最后一条，按时间顺序过一遍
        （CC 收尾时本来就持有完整上下文，只是要主动全量扫描，不只看最后一段）

Step 2: 对每段对话/事件，分类判断 — 这是几级素材？
        a. 1 级（必须记）：发现问题→解决 / 技术判断 A 不 B / 失败 / 模式 5 / 纠正 CC / 关键设计决策
        b. 2 级（强推）：学新概念 / 工程方法论转变 / 技术对话 / 自我管理改进 / 推翻自己
        c. 3 级（可记）：阅读学习 / 周边活动 / 灵感 / 工具发现
        d. 4 级（看似无用要记）：日常小决定 / 困惑纠结 / 时间状态
        e. 5 级（不记）：寒暄 / 无关 / 纯执行
        → 1-4 级**全部进候选清单**，5 级丢弃

Step 3: 对每个候选素材，识别属于哪个模式（§4 六模式）：
        - 模式 1: 问题→尝试→解决
        - 模式 2: 假设崩了→继续→真因（最高级）
        - 模式 3: 失败→吸取教训→下个项目
        - 模式 4: v1→v2 版本演化
        - 模式 5: 原本不知道→通过 X 知道→现在的做法（itsuki 主线）
        - 模式 6: 技术判断的取舍三角
        → 标在素材头部，决定篇幅按 §3.6 思考层数分级

Step 4: 检查 CC 主动发现的问题（§0.3）— 有没有 CC 看出 itsuki 不知道的事？
        → 这种也是素材，按 0.3 主动 dump

Step 5: 按 §3.2 决定 raw 文件名（日期版 / 主题版）
        → 默认 YYYY-MM-DD.md，今天已有同会话延续的 raw → append；新主题 → 主题版

Step 6: 按时间顺序 dump 全部候选素材到 raw（§3.3 推荐字段格式）
        → 必填 2 项：itsuki 原话 + AC 价值
        → 长素材按 §3.6 思考层数决定篇幅
        → §3.7 原话不润色

Step 7: 给 itsuki 列「我从今天对话扫到 N 条素材」清单：
        ┌────────────────────────────────────────┐
        │ 今天 dump 了 X 条到 raw/2026-MM-DD.md：│
        │ 1. §A 标题 [模式X] [思考层数Y]          │
        │ 2. §B 标题 [模式X] [思考层数Y]          │
        │ ...                                    │
        │                                        │
        │ itsuki 看一眼，要否决 / 删除 / 改写哪条直接说│
        └────────────────────────────────────────┘
```

**铁律**：
- ❌ CC **绝不能**只 dump 最后一段对话就跳到 §5.5.1 — 那叫"敷衍收尾"
- ❌ CC **绝不能**因为某段对话"看起来无聊"就跳过 — §0.2 「宁多勿少」+ 4 级素材规则
- ✅ 全量扫描完成后，再走 §5.5.1 ~ §5.5.7 剩下的收尾动作
- ✅ 扫描发现重大遗漏（之前没 dump 但应该 dump 的）→ 补 dump，不假装"已经记过了"

#### 5.5.9 git 仓库状态收尾确认（2026-05-04 itsuki 拍板加，从 session-start skill 挪过来）

> **背景**：原本是 session-start skill 的内容（启动时跑），itsuki 拍板挪到结尾 — 启动时 CC 不需要这些信息，但**收尾时**正合适：确认 commit 干净 / 决定要不要 push / 看有没有别会话残留。

收尾时跑这 4 项 git 状态检查（已经做过 5.5.6 commit 的话部分项可以跳过）：

```bash
# A. 工作树状态
git status

# B. 未 push commit 数
git log --oneline origin/main..HEAD

# C. stash 是否挂着活
git stash list

# D. 残留垃圾文件嫌疑（按需跑）
git status --porcelain | grep -E '\.(bak|bak[0-9]|DS_Store)$|/File\.txt$'
```

报告格式：

```
📋 git 仓库状态收尾报告

- branch: main / 别 branch ⚠️
- 已修改未 staged: N 个 — [是不是别会话改的？要不要 stage]
- untracked: N 个 — [残留垃圾列出来 / 正常文件不列]
- staged 但未 commit: N 个 — [是不是忘 commit 了]
- 未 push commit: N 条（最新 [hash] [一句话]）— [按 commit/push 协作分工等 itsuki 拍板要不要 push]
- stash: N 条 — [是不是挂着的活忘了]

→ 疑似遗留 / 需确认：[列污染项]
→ push 决定：等 itsuki 指令
```

铁律：
- **不主动 push** — push 是 itsuki 拍板动作（memory `feedback_commit_push_tag_division.md`）
- **不主动 discard / 删 untracked** — 可能是别会话的活
- 仅报告状态 + 列待决项

### §7.5.2 状态字段写法规范

- **✅ 做了** — 必须给具体证据（文件路径 / 提交哈希 / 报告摘要）
- **⏸ 不触发** — 必须**显式说明**为什么不触发，**不允许默默跳过**
- **❌ 漏** — 必须说理由 + 是否补做（"现在补 / 记 TODO 后做"）

### §7.5.3 反模式

- ❌ 没跑第 N 项就报告"收尾完成"（默默跳过）
- ❌ 跑了但没在报告里说（itsuki 看不到 = 等于没做）
- ❌ 判断"N/A 不用做"就不显式说明（itsuki 不知道你跳了）
- ❌ 说"漏了"但没解决方案（不说"现在补"或"记 TODO"）

### §7.5.4 为什么这条规则存在

LLM 自觉性 = 工程不可靠组件（跟 cc-comm-rules v0.4.0 同根问题）。靠 CC 自己判断哪些 N/A 哪些漏 = 跳过。

**机制层修正**：强制每项都显式说状态 = 不让 CC 有"判断 N/A 跳过"的裁量空间。
